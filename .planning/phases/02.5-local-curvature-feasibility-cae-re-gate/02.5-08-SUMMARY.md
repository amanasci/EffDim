## The mathematics, and where it deviates from the plan's literal instruction

The plan's `<action>` transcribes RESEARCH Pattern 4's illustrative snippet, which builds an
explicit `(out_dim, out_dim)` normal projector and the full `II` tensor before tracing. That
conflicts with this phase's standing invariant that a `(D, D)` projector is never materialized,
and at the real `out_dim = 768` the snippet costs 151 MB (projector) + 78 MB (`II`) per 32-row
batch of pure waste.

Since `P_N` acts only on the ambient index and the `g`-trace only on the two chart indices, the
two commute: `tr_g(P_N Hess) = P_N tr_g(Hess)`. The implementation therefore traces first and
projects second, applying `P_N` by the `chart_dim × chart_dim` solve `P_N a = a - J alpha` with
`g alpha = J^T a`:

```
raw   = einsum("bjk,bojk->bo", g_inv, Hess)              # unprojected g-trace
alpha = solve(g, einsum("boi,bo->bi", J, raw))           # d x d solve, never (D, D)
H     = raw - einsum("boi,bi->bo", J, alpha)
```

This is an optimisation of the *same* mathematics, so it is proved rather than asserted:
`test_chart_curvature_dxd_solve_matches_explicit_projector` transcribes Pattern 4's snippet
verbatim as an independent reference and requires agreement to `rtol=1e-9, atol=1e-12`.

`g_inv` comes from `torch.linalg.solve` against a batched identity rather than `torch.linalg.inv`,
per the plan's stated preference, and `torch.linalg.cond(g)` is returned alongside so a
near-singular pullback metric at a non-immersion point is visible rather than silently inflating
the field (threat T-02.5-20).

**Convention held.** `H = tr_g(II)` throughout, no `1/d` and no `d`. The factor-of-`d` = 20 trap
described in both notes is closed by an explicit regression guard at `chart_dim = 4`, chosen so
that `d`, `(d+2)/d` and `1` are all separable — at `d = 2` a `d`-fold error and the
already-fixed `(d+2)/d` error are not distinguishable.

## The measured finding: `vmap(hessian(...))` is not bit-reproducible across batch widths

The plan's Task 2 acceptance criterion requires `chart_curvature_field` to produce **bit-identical**
`H_norm` at `batch_size=8` and `batch_size=64`. As first implemented it did not: the fields agreed
to `5.3e-15` but not bitwise.

Isolated rather than papered over. Measured on a `silu` `ChartAutoEncoder`, comparing a row
computed in a batch of 24 against the same row computed in a batch of 8:

| operation | bit-identical across batch width? | max abs difference |
|---|---|---|
| `vmap(jacrev(f))` | yes | `0.0` |
| **`vmap(hessian(f))`** | **no** | **`1.7e-18`** |
| `einsum` for `g` from identical `J` | yes | `0.0` |
| `torch.linalg.solve` | yes | `0.0` |
| `torch.linalg.cond` | yes | `0.0` |

Only the doubly-nested Hessian transform moved; torch selects different batched-matmul kernels by
batch size. Propagated through the metric solve and the normal projection, `1.7e-18` grew to
`5.3e-15` in `H_norm`.

Two further measurements decided the fix. At a **fixed** width, a row's result is bit-identical
(a) regardless of which other rows share its chunk, and (b) regardless of whether the chunk is
filled with real rows or with repeated padding. So fixing the autodiff width at `VMAP_CHUNK = 32`
and padding the short final chunk restores exact reproducibility across any caller-side batching,
at a cost of at most one padded chunk per call.

This was treated as a bug to fix rather than an over-strong assertion to relax, because a
bit-identity check weakened to a tolerance is no longer a check for the row-reordering bug it was
written to catch. A reordering bug is invisible to every aggregate statistic this phase computes —
Spearman and quantile-bin concordance would both simply drop, looking like a weak estimator.

`VMAP_CHUNK` also sets peak memory: `32 × 768 × 20² × 8 B = 78.6 MB` for the Hessian at the sealed
architecture, with true peak a small multiple of that.

## The amplitude checks — the part not in the plan file

Added per `02.5-NOTE-randomized-trace.md` Addendum C and
`02.5-NOTE-high-d-curvature-approaches.md` Section 2d, both of which post-date the plan.

`H` is vector-valued, so amplitude attenuation and orientation error are **distinct** failure modes
and are never collapsed into a single scalar. `curvature_fidelity_report` returns all three
families separately:

1. **direction** — per-point cosine similarity between `H_F` and `H_true`
2. **magnitude** — `||H_F|| / ||H_true||` as **both** median and per-point CV
3. **calibration slope** — least squares `a`, `b` on the norms, checking `a ≈ 1`, `b ≈ 0`

Two tests pin why this is not redundant with the rank statistics:

- **The note's worked example, constructed exactly.** A decoder attenuating every magnitude by
  `0.7` scores `spearman_gate_statistic == 1.0` — a perfect score — while the report returns
  median ratio `0.7`, CV `0.0`, slope `0.7`, cosine `1.0`. A norm-preserving coordinate swap does
  the reverse: cosine drops, the entire amplitude family reads `1.0`. Neither failure mode can hide
  behind the other.
- **Why median and CV are both required.** Two synthetic fields with medians `≈ 0.905` and CVs
  `0.24` vs `1.30` reproduce Section 1a's measured separation between *attenuated but calibratable*
  (`d=2`: median 0.905, CV 0.250) and *destroyed* (`d=20`: CV 2.250, non-monotone median). The
  medians alone cannot separate them; the CV separates them decisively.

Points where `||H_true|| ≈ 0` carry no direction and no meaningful ratio, so they are excluded and
counted in `n_excluded` rather than dividing by something near zero.

## The randomized path, correctly demoted

Implemented per the note's "What 02.5-08 should do", as a **convergence check on the exact path,
gated on nothing** — not as a candidate estimator. The function name carries the word `nongating`
so misuse is visible at the call site rather than only in a docstring.

Measured on a `silu` decoder at `chart_dim = 3`, median relative error against the exact path,
averaged over 8 seeds:

| `K` | mean-over-seeds median relative error |
|---|---|
| 4 | 0.561 |
| 16 | 0.278 |
| 64 | 0.140 |

A clean `1/sqrt(K)`: each 4× in `K` halves the error. Unbiasedness confirmed separately — averaging
200 independent `K=4` estimates gives median relative error `0.042`, so the spread at low `K` is
variance around the right value, not a bias at the wrong scale. That distinction is exactly what a
mis-paired probe normalization would break, since a factor-of-`d` error would *not* shrink with
more probes.

Averaging over seeds is load-bearing in the test: at one fixed seed the sequence is **not** monotone
(`K=8` landed worse than `K=4` on one draw). That is the nature of a Monte-Carlo estimator, not a
defect, and asserting monotonicity at a single seed would have produced a flaky test.

**Antithetic probes: refused, and pinned as bit-identity.** `B` is a symmetric bilinear form, so
`B(-v,-v) = B(v,v)` *exactly* — `torch.equal` returns `True`, not merely `allclose`. The antithetic
partner is correlated at `+1`, so any K-probe budget spent on pairing is halved for nothing.
`test_chart_curvature_antithetic_probes_are_exactly_redundant` exists so the claim cannot rot into
folklore and fails loudly if someone later adds an antithetic path believing it helps.

**Hutch++: refused in writing** at the point where someone would reach for it. It estimates the
scalar trace of a *matrix*; `II: T_zM × T_zM -> N_zM` is vector-valued, so at codimension > 1 there
is no single scalar matrix whose trace it computes. Making it work would require constructing a
normal basis, which is precisely what the `d × d` solve exists to avoid at `D = 768`.

## Deviations from Plan

### Auto-fixed issues

**1. [Rule 1 — Bug] `chart_curvature_field` was not bit-identical across batch sizes**
- **Found during:** Task 1 GREEN
- **Issue:** The plan's own acceptance criterion (`batch_size=8` and `batch_size=64` produce
  bit-identical `H_norm`) failed at `5.3e-15`. Root cause isolated to `vmap(hessian(f))` selecting
  different batched-matmul kernels by batch width; `jacrev`, `solve` and `cond` were unaffected.
- **Fix:** `VMAP_CHUNK = 32` fixes the autodiff width; short final chunks are padded by repeating
  the last row and the padding is discarded. Verified by measurement that a row's result at fixed
  width is independent of which rows (real or padding) share its chunk.
- **Commit:** `1ca876d`

**2. [Rule 2 — Missing critical functionality] Autograd graph retained across the whole field**
- **Found during:** Task 1 GREEN
- **Issue:** `H_vec` carried `grad_fn`, so a 10,000-row field would have retained the full autodiff
  graph of every chunk. Curvature here is a measured value, never an optimization objective.
- **Fix:** outputs detached per chunk.
- **Commit:** `1ca876d`

### Deliberate deviations, with rationale

**3. `chart_mean_curvature` returns a dict, not a bare tensor.** Task 1 requires `cond(g)`
"returned alongside" and Task 2 requires asserting `J`/`Hess` shapes "by inspecting the returned
diagnostics". A bare tensor satisfies neither. Shapes are returned as tuples, so a 768-dimensional
Hessian is never retained merely to report its shape.

**4. The `(D, D)` projector in the plan's `<action>` is not implemented as written.** Replaced by
the mathematically identical trace-then-project `d × d` solve, per this phase's standing invariant
against materializing a `(D, D)` normal projector. Equality with the plan's literal formulation is
proved by test, not assumed.

**5. Module symbols beyond the plan's `must_haves`.** `curvature_fidelity_report`,
`directional_second_derivative`, `randomized_trace_mean_curvature_nongating` and
`randomized_trace_convergence_check` are mandated by `02.5-NOTE-randomized-trace.md` (Addendum A/C
and "What 02.5-08 should do") and `02.5-NOTE-high-d-curvature-approaches.md` Section 2d, both of
which post-date the plan file. All six plan-named symbols are present and unchanged in intent.

**6. Task 2's GREEN commit touches `chart_curvature.py`, though Task 2's `<files>` lists only the
test file.** The note-mandated functions have to live in the module. Task 2's `<files>` was written
before those notes existed. Both files are within the plan's frontmatter `files_modified`.

**7. Test count under `-k "chart_curvature"` is 9, not the plan's stated 3.** The plan's three named
tests are all present under their exact specified names. The six additional tests are the
note-mandated ones (trace convention, projector equivalence, amplitude/direction separation,
median-vs-CV separation, antithetic redundancy, randomized convergence). Reported rather than
concealed; a reader checking that acceptance criterion literally will see 9.

**8. `batch_size` in `chart_curvature_field` is numerically inert.** The plan asked it to bound peak
memory. Peak memory is now bounded by `VMAP_CHUNK` instead, which is the necessary consequence of
deviation 1 — the width cannot both be caller-tunable and give bit-identical results.
`batch_size` remains as Python-loop granularity and is documented as inert.

**9. `float64` is enforced by raising rather than by casting.** The plan says "run in float64
throughout"; silently casting a float32 model would hide a caller error at exactly the place second
derivatives are most fragile.
