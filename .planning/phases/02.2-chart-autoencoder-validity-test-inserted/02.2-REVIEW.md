# Phase 02.2: Code Review Report

**Reviewed:** 2026-08-04T21:45:10Z
**Depth:** standard
**Files Reviewed:** 4

## Summary

Reviewed `cae.py` (the pure-torch CAE implementation), its test suite, and the two
diagnostic runners that trained and evaluated the pre-registered fit that produced the FAIL
verdict (T1 distortion = 0.297 vs <0.15; T3 worst-case reconstruction ratio = 3.59 vs
<0.90).

Per the domain brief, I specifically traced the code paths most likely to produce a
**spurious** failure rather than a genuine one:

- **T1 (`fit_global_scale` / `embedding_distortion`):** The squaring convention
  (`geo_pairs_r2` holds *unsquared* distances) matches Phase 02.1's own runner
  (`geometry_probes_run.py:285` does the identical `** 2`), and is independently verified by
  `test_distortion_uses_global_embedding_not_chart_coords`, which checks the near-isometric
  fixture recovers `median_abs_rel < 1e-12`. The scale is fit strictly on train-train pairs
  and applied to all pairs — no leakage. `z_main` is confirmed to be the initial encoder's
  global output (`embed_dim=40`), never chart-local coordinates. I found no indexing,
  normalization, or squaring defect here.
- **T3 (held-out reconstruction vs. matched-capacity controls):** `reconstruction_stats`
  applies the identical `sum-over-dims / out_dim` normalization (768 in every case) to the
  CAE, ReLU control, both plain-AE controls, and both MDS-decoder controls — no
  per-dimension-vs-total mismatch. `train_idx`/`holdout_idx` are asserted bit-identical
  across all eight loaded fit artifacts before any metric is computed
  (`cae_evaluate_run.py:145-165`), and `x_holdout_t` is built identically in both the
  training and evaluation runners. I found no split-leakage or index-misalignment bug. One
  real (but disclosed) asymmetry worth flagging for the record: the CAE's `train_cae` loss
  jointly optimizes reconstruction + cross-entropy + a Lipschitz penalty, and the CAE
  reconstructs at test time via **argmax-probability** chart selection
  (`ChartAutoEncoder.reconstruct`), not the oracle min-error chart the training loss
  rewards — while the plain-AE/MDS-decoder controls optimize pure reconstruction with no
  competing objective. That gap is architecture-inherent (and is the paper's own eq. 19
  methodology), not a code defect, but it is a plausible non-bug explanation for why a
  16-chart CAE with far more total parameters than its "matched-capacity" controls (same
  hidden width/depth per side, but replicated 16x for chart encoders/decoders — disclosed in
  `cae_evaluate_run.py`'s `assumptions` list) still reconstructs holdout rows worse.

No evidence of a spurious-failure-causing bug was found in the reviewed files. The findings
below are unrelated robustness/quality gaps, several of which are edge cases that did not
trigger in the run that produced the FAIL verdict (the run completed and produced finite,
sensible numbers throughout).

## Warnings

### WR-01: `chart_survival` has no NaN guard, and a single NaN spectral norm corrupts every chart's accounting silently

**File:** `notebooks/pu_manifold/cae.py:787-821`
**Issue:** `_chart_decoder_logmass` (line 772) can return `NaN` if `_robust_spectral_norm`
ever returns `NaN` for a layer (its own docstring, line 244-250, documents that LAPACK's SVD
has already been observed to fail on a real trained weight matrix — the float64 fallback
mitigates the *convergence* failure mode but not a `NaN`-producing one). `chart_survival`
then does:
```python
log_mass_max = float(logmass.max())      # NaN if ANY chart's logmass is NaN
mass_ratio = np.exp(logmass - log_mass_max)   # NaN for EVERY chart, not just the bad one
surviving_indices = [i for i in range(n_charts) if mass_ratio[i] >= prune_tol]  # all False
pruned_indices = [i for i in range(n_charts) if mass_ratio[i] < prune_tol]      # all False
```
`np.ndarray.max()` propagates `NaN`, so one bad chart poisons `log_mass_max` and therefore
every chart's `mass_ratio`. Because NaN comparisons are always `False`, affected charts
vanish from **both** `surviving_indices` and `pruned_indices` — `n_charts_surviving +
len(pruned_indices)` silently stops summing to `n_charts_initial`, with no exception raised.
This is inconsistent with the project's own established discipline elsewhere
(`verdict_from_metrics` explicitly rejects non-finite gating metrics with a `ValueError`,
line 1081-1085) — `chart_survival` has no equivalent guard, and `surviving_indices_main`
feeds directly into `select_overlap_pairs` for the T2 gate.
**Fix:**
```python
logmass = np.array([_chart_decoder_logmass(dec) for dec in model.chart_decoders], dtype=np.float64)
if not np.all(np.isfinite(logmass) | np.isneginf(logmass)):
    raise ValueError(
        f"chart_survival: non-finite (NaN) log-mass for chart(s) "
        f"{np.flatnonzero(np.isnan(logmass)).tolist()} -- cannot determine survival"
    )
```

### WR-02: `embedding_distortion`'s dimension guard only catches one specific misuse, not general mismatches

**File:** `notebooks/pu_manifold/cae.py:997-1008`
**Issue:** The guard is:
```python
if z.shape[1] == chart_dim and chart_dim != embed_dim:
    raise ValueError(...)
```
This only raises when the supplied array's width happens to equal `chart_dim` exactly. It
never checks that `z.shape[1] == embed_dim` (the actually-required condition). Any other
wrong-shaped array — e.g. a concatenated multi-chart array, a truncated embedding, or a
transposed array — passes through silently and produces a distortion statistic over
meaningless pairwise distances. The docstring's stated contract ("Distortion must be
computed on the global embedding only") is only partially enforced.
**Fix:**
```python
if z.shape[1] != embed_dim:
    raise ValueError(
        f"embedding_distortion: supplied array has feature dimension {z.shape[1]}, "
        f"expected the model's embedding dimension {embed_dim}"
    )
```
(the existing chart_dim-specific message can be kept as a more specific sub-case for a
better error string, but the general check must not be skipped.)

### WR-03: `select_overlap_pairs` crashes with a confusing `IndexError` instead of its documented `ValueError` when fewer than 2 charts survive pruning

**File:** `notebooks/pu_manifold/cae.py:860-900`
**Issue:** When `len(surviving_indices) < 2` (e.g. aggressive pruning leaves 0 or 1 surviving
chart), `p_surv = p[:, surviving]` has fewer than 2 columns. `top2_local = order[:, :2]`
silently truncates to that width (numpy slicing tolerates an out-of-range stop index), so
`top2_local[:, 1:2]` becomes a zero-width array, and the subsequent
`np.take_along_axis(...)[:, 0]` on that zero-width result raises a raw `IndexError: index 0
is out of bounds for axis 1 with size 0` — not the clear, intentional `ValueError` the
function otherwise raises for "too few qualifying rows" (line 889-895). The function's own
docstring states halting is "the honest behaviour," but this particular halt path produces
an unexplained stack trace rather than a diagnostic naming the actual problem
(insufficient surviving charts, not insufficient qualifying rows).
**Fix:**
```python
surviving = np.asarray(sorted(surviving_indices), dtype=np.int64)
if surviving.shape[0] < 2:
    raise ValueError(
        f"select_overlap_pairs: only {surviving.shape[0]} chart(s) survived pruning -- "
        "at least 2 surviving charts are required to form an overlap pair."
    )
```

## Info

### IN-01: `verdict_from_metrics` validates `metrics[gate]` but not `thresholds[gate]`

**File:** `notebooks/pu_manifold/cae.py:1077-1091`
**Issue:** Every gating metric is checked for presence/finiteness with a descriptive
`ValueError` (lines 1077-1085), but `threshold = thresholds[gate]` (line 1091) is a bare
dict access — a missing threshold key raises an unguarded `KeyError` instead of the same
class of descriptive error. Still fails loudly, just inconsistently.
**Fix:** Add the same presence check for `thresholds` alongside the existing `metrics` loop.

### IN-02: Per-epoch training statistics are an unweighted mean of per-batch means

**File:** `notebooks/pu_manifold/cae.py:486-496`, and the identical pattern in
`_train_decoder_protocol:687`
**Issue:** `epoch_mean_total = epoch_total / n_batches` averages batch-level means, not
row-level means; the final (usually smaller) batch of an epoch is weighted equally to full
batches. This doesn't affect gradient updates (each batch's `.backward()` is exact), only
the logged/early-stopping-driving statistic, and the skew is small at
`BATCH=64`/`n=8000`, but it is an avoidable minor inaccuracy in the plateau-detection input.
**Fix:** Accumulate `sum` and `count` of rows rather than `sum` of batch means, or weight
each batch's contribution by `xb.shape[0]`.

### IN-03: T3's gating comparison hardcodes specific latent/`p` values rather than deriving them from named constants

**File:** `notebooks/diagnostics/cae_evaluate_run.py:333-334, 342`
**Issue:**
```python
ratio_vs_plainae20 = mse_cae / mse_plainae20
ratio_vs_mdsdec8 = mse_cae / mse_mdsdec8
recon_margin_value = max(ratio_vs_plainae20, ratio_vs_mdsdec8)
```
`20` and `8` are literal suffixes baked into variable names, duplicating (rather than
deriving from) `PLAIN_AE_LATENTS[0]` and `MDS_BASELINE_P[0]` in `cae_train_run.py`. If
either tuple's ordering or values were ever amended, this gating logic would silently keep
comparing against the old hardcoded pair instead of tracking the pre-registered constants.
**Fix:** Reference `PLAIN_AE_LATENTS[0]` / `MDS_BASELINE_P[0]` (or name the gating pair
explicitly, e.g. `GATING_PLAINAE_LATENT = 20`) instead of embedding the literal in the
variable name and dict lookup.

### IN-04: `to_native` does not handle a raw `np.ndarray`

**File:** `notebooks/pu_manifold/cae.py:1030-1049`
**Issue:** `to_native` recurses into `dict`, `list`/`tuple`, `torch.Tensor`, `np.floating`,
`np.integer`, `np.bool_`, but a bare `np.ndarray` falls through to the final `return obj`
unchanged, and `json.dumps` would then raise `TypeError: Object of type ndarray is not JSON
serializable`. Every current call site happens to pre-convert arrays to lists before
reaching `to_native` (e.g. `_survival_summary`'s `[float(v) for v in ...]`), so this doesn't
currently trigger, but it's a latent trap for the next caller who forgets to pre-convert.
**Fix:** Add an `isinstance(obj, np.ndarray)` branch that recurses via `.tolist()`.

### IN-05: Duplicated per-chart squared-error computation between `ChartAutoEncoder.forward()` and `chart_loss()`

**File:** `notebooks/pu_manifold/cae.py:210` and `:229`
**Issue:** `e = ((x.unsqueeze(1) - y_charts) ** 2).sum(dim=-1)` is computed identically in
both `forward()` (populating `out["e"]`, which is then discarded by every call site that
calls `chart_loss` separately) and again inside `chart_loss`. Not a correctness bug, but the
duplication is a maintenance hazard if the formula ever needs to change in one place and not
the other.
**Fix:** Have `chart_loss` accept the already-computed `e` (or have callers pass `out["e"]`
through) instead of recomputing it.

### IN-06: `train_cae` never validates `cfg["n_charts"]` against `model.n_charts` before FPS pre-training

**File:** `notebooks/pu_manifold/cae.py:393-434`
**Issue:** `effective_cfg.setdefault("n_charts", model.n_charts)` only supplies a default
when the key is absent; if a caller passes an explicit `cfg["n_charts"]` that disagrees with
the actual model's chart count, `farthest_point_sample`/`fps_pretrain_loss` will index
`z_charts_all[idx, seed_chart_index]` with `seed_chart_index` up to `n_charts_cfg - 1`,
raising an `IndexError` deep inside pre-training rather than a clear
config/model-mismatch error at the top of `train_cae`. All production call sites in
`cae_train_run.py` pass a consistent value, so this did not trigger here.
**Fix:** Assert `effective_cfg["n_charts"] == model.n_charts` immediately after resolving
`effective_cfg`.

### IN-07: `PlainAutoEncoder`'s "matched capacity" is width/depth-matched only, not parameter-count-matched

**File:** `notebooks/pu_manifold/cae.py:576-582`; instantiated at
`notebooks/diagnostics/cae_train_run.py:143-157`
**Issue:** The docstring frames `PlainAutoEncoder` as testing "whether the atlas bought
anything over one chart at matched capacity," and `cae_evaluate_run.py`'s `assumptions` list
does disclose the actual operationalisation ("same hidden width (250), the same layer count
per side (3)"). But at `N_CHARTS_INIT=16`, the CAE instantiates 16 separate 3x250 chart
encoders plus 16 separate 3x250 chart decoders (`ChartAutoEncoder.__init__`,
`cae.py:172-180`), giving it roughly an order of magnitude more total trainable parameters
than the single-encoder/single-decoder `PlainAutoEncoder` control it's being gated against.
This is disclosed, not hidden, and if anything argues the measured T3 shortfall is a
genuine finding rather than an artifact of a capacity-starved CAE — but the term "matched
capacity" on its own (without reading the assumptions list) could mislead a reader into
believing total parameter counts are comparable.
**Fix:** No code change required; consider renaming the docstring's "matched capacity" to
something more precise (e.g. "matched per-layer width/depth") to avoid the term being read
as a parameter-count claim.
