## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] LAPACK SVD non-convergence in the Lipschitz penalty / pruning statistic**
- **Found during:** Task 2, first CAE seed fit (`cae_seed_20260803`), first attempt
- **Issue:** `torch.linalg.matrix_norm(layer.weight, ord=2)` (called every training step by `lipschitz_penalty`, and after training by `chart_survival`'s pruning statistic) raised `torch.linalg.LinAlgError: linalg.svd: The algorithm failed to converge because the input matrix is ill-conditioned or has too many repeated singular values` on a real trained chart-encoder weight matrix. Plan 02.2-03's unit tests use small random matrices and never hit this LAPACK edge case.
- **Fix:** Added `_robust_spectral_norm(weight)` to `notebooks/pu_manifold/cae.py`: try the SVD in the tensor's native dtype first; on `LinAlgError`, retry the identical decomposition in float64 (a different, more numerically stable LAPACK code path) and cast the result back to the original dtype so gradients keep flowing through the same-dtype graph. Both `_chart_encoder_spectral_product` and `_chart_decoder_logmass` now route through it.
- **Files modified:** `notebooks/pu_manifold/cae.py`, `notebooks/pu_manifold/tests/test_cae.py`
- **Verification:** Added `test_robust_spectral_norm_falls_back_to_float64_on_svd_nonconvergence` (monkeypatches `torch.linalg.matrix_norm` to force the float32 path to raise, confirms the float64 fallback returns the correct spectral norm and is invoked exactly once). Full suite: 43/43 pass. The re-run `cae_seed_20260803` fit then completed cleanly (36 epochs, wallclock 1984.9s, early-stop-plateau).
- **Committed in:** `06023a9`
- **Impact on pre-registered protocol:** None. No constant in Section 4 changed; this is a numerical-precision fallback around an existing exact computation, not a different formula or threshold.

**2. [Rule 3 - Blocking, execution-harness recovery, no code change] Silent death of a manually-detached background training process**
- **Found during:** Task 2, the initial three-seed batch launch
- **Issue:** The first launch attempt used a manually-detached `nohup ... &` background process (not the execution harness's own tracked background-job mechanism). It died silently after ~13 minutes with no traceback, no OOM signal, and zero `cae_seed_*` artifacts written -- most likely because the manual detachment did not survive process-group churn across tool-call boundaries and was not tracked/protected by the harness the way a harness-managed background job is.
- **Fix:** Every subsequent fit (the single-seed retry, and the batch of two remaining seeds plus five controls) was launched through the harness's own `run_in_background` mechanism instead of manual `nohup`/`&` detachment. A subsequent full-batch run (orchestrator-driven, using `PYTHONFAULTHANDLER=1` for extra diagnostic safety) also died mid-`cae_seed_20260805` for unexplained reasons and was re-invoked once more; the sidecar-manifest cache meant every already-completed fit was a pure cache hit on that re-invocation, so no compute was wasted and no numbers changed.
- **Files modified:** None -- this is purely an execution/orchestration recovery, not a code or protocol change.
- **Verification:** All eight registry entries independently verified present and correct on disk (see coverage table D1-D7 above); re-invoking the full registry after the last successful run showed `cache_hit=True` for all eight entries.
- **Impact on pre-registered protocol:** None. No seed, threshold, or architecture constant was altered by any of the retries; the cache-key contract (`_protocol_cfg`) guarantees a re-run under an unchanged cfg either replays the cached artifact or recomputes it identically.
