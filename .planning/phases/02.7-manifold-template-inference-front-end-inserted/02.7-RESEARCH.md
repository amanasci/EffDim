## Summary

This phase has one real engineering risk and it is compute, not algorithm design: **an unthresholded `ripser(..., maxdim=2)` call on a genuine 2-manifold blows past a 90-second wall clock somewhere between `n=400` and `n=500`, and the cost curve is steep enough (roughly `n^4`) that no single point cloud budget serves the whole phase comfortably.** This was measured directly in this session, not estimated: `S^2` at `n=200/300/400` costs `1.85s/8.59s/26.55s`, and `n=500` did not finish inside a 90-second alarm. `T^2` is cheaper at matched `n` (its larger diameter spreads the expensive high-simplex-count regime over more of the filtration) but still reaches `74.66s` by `n=800`. D-08 pins one `n_ph` identically across the Euclidean arm, the geodesic arm, and every cell of D-15's benchmark grid — so this one number has to survive the phase's hardest cell (`D=768`, high noise, `H_2`), and D-02's bootstrap confidence band multiplies every one of those `ripser` calls by `B` (Fasy et al.'s own precedent: `B=30`). The honest read, stated plainly per the brief's own instruction: **`n_ph` in the 250–350 range is the most that is comfortably tractable for `H_2` at this phase's compute budget, and whether that `n_ph` has the statistical *power* to reliably resolve `H_2` on `S^2`/`T^2` against sampling noise (as opposed to merely completing before the alarm fires) has not been measured by anyone yet — the analogous H1 power check exists for this project's PU embeddings (`n=383`, detects a cycle down to 3.3x the manifold's thickness) but no H2 analogue was ever built, on cost grounds, by the team that ran it.** This is A-05's predicted risk, now given a number.

Everything else in the phase is well-supported by code already sitting in this repository. `scipy.sparse.csgraph.shortest_path` — the exact call D-05's kNN-graph geodesic needs — is already imported and used in the frozen `geometry.gmst_dimensionality`, proving the route works in this venv; but that same frozen function's `graph + graph.T` symmetrization has a **verified, measured bug** (it doubles edge weights at every mutual-nearest-neighbour pair) that the new D-05 code must not copy — `graph.maximum(graph.T)` is the fix, verified this session against the same fixture. `persistence_probe.py`'s reusable surface is exactly what CONTEXT.md says it is, confirmed by reading the source: `persistence_diagram(D, maxdim)` takes a square symmetric float64 distance matrix and is metric-agnostic by construction, so the geodesic arm plugs in with zero adapter code — but it has no `thresh` parameter, defaults to the full (potentially very expensive) filtration, and its `finite_pairs` helper will silently discard genuine long-lived features if a caller ever adds `thresh` without also reconsidering that filter (a new, previously unrecorded hazard, found this session). Seven of the eight frozen dimensionality estimators accept `precomputed_knn_dist_sq` and can be sliced onto anchor-point neighbourhood subsets exactly as D-12 describes, using the *same* precomputed array as the global estimate; the eighth, `gmst_dimensionality`, has no such parameter and no `k` argument at all, so it cannot participate in D-12's "bit-identical provenance" local mechanism and cannot literally be swept "at every `k`" as a literal reading of D-09 might suggest.

**Primary recommendation:** Pin `n_ph = 300` (Euclidean and geodesic arms identical, every benchmark cell identical, per D-08); before ratifying it in D-16's blind commit, run one throwaway feasibility script (not the ratified rule, not statistically informative about detection thresholds — purely a wall-clock/memory check) at `n=300`, `D=768`, worst-case noise, for all four templates, and record the actual numbers, because this session's measurements were taken at `D=3` and the interaction with a random-orthogonal-lift-plus-warp at `D=768` is unverified. Budget for `H_2`'s cost to dominate the phase's entire wall-clock envelope; size D-15's grid and D-02's `B` around that constraint, not the other way round.

### Pattern 1: The kNN-graph geodesic distance matrix (Q3)

**What:** Build a symmetric, all-pairs geodesic distance matrix from a point cloud, suitable for `persistence_probe.persistence_diagram`.
**When to use:** D-05's spectral/kNN distance arm, every benchmark cell and the PU probe.
**Verified this session** (`.venv/bin/python`, `scipy 1.18.0`, `scikit-learn 1.9.0`):

```python
# Source: verified this session against src/effdim/geometry.py:gmst_dimensionality's own
# route (frozen precedent, same imports), with the symmetrization bug fixed (see Pitfall below)
from sklearn.neighbors import kneighbors_graph
from scipy.sparse.csgraph import shortest_path, connected_components

graph = kneighbors_graph(data, k, mode="distance")   # real Euclidean weights, NOT squared
graph = graph.maximum(graph.T)                        # symmetrize -- NOT graph + graph.T (verified bug, see below)

n_components, labels = connected_components(graph, directed=False)
sizes = np.bincount(labels)
largest_label = sizes.argmax()
largest_mask = labels == largest_label
dropped_fraction = 1.0 - sizes[largest_label] / len(data)   # D-07's required read-out

# Geodesic PH on the largest component ONLY (D-07 -- no bridging):
sub_graph = graph[largest_mask][:, largest_mask]
D_geo = shortest_path(sub_graph, directed=False, method="D")   # Dijkstra; 1.275s measured at n=2000,k=10
assert np.allclose(D_geo, D_geo.T)   # persistence_diagram requires exact symmetry
```

Measured cost at `n=2000, k=10`: `shortest_path` (Dijkstra) completes in **1.275s** `[VERIFIED: measured this session]` — cheap relative to the `ripser` call that follows it. `connected_components` is effectively free at this scale.

### Pattern 2: Local `d_hat` via anchor-neighbourhood slicing (D-12), seven of eight estimators

**What:** Get a spatially-localized dimension estimate without touching `geometry.py` or duplicating any estimator.
**When to use:** D-12's dispersion probe, feeding abstain condition (b).
**Verified against source this session** (`src/effdim/geometry.py`):

```python
# All of mle_dimensionality, two_nn_dimensionality, danco_dimensionality,
# mind_mli_dimensionality, mind_mlk_dimensionality, ess_dimensionality,
# tle_dimensionality accept precomputed_knn_dist_sq: Optional[np.ndarray].
# Compute the GLOBAL knn-distance array ONCE -- the same array the global d_hat used:
dist_sq_global = geometry.compute_knn_distances(data, k)   # (n, k), SQUARED distances

for anchor_idx in anchor_indices:
    local_idx = neighbourhood_of(anchor_idx, radius_or_k)   # spatial patch around the anchor
    local_d_hat = geometry.mle_dimensionality(
        data[local_idx],                       # only used for its n_samples check
        precomputed_knn_dist_sq=dist_sq_global[local_idx],   # SAME array, sliced -- no recomputation
    )
```

This keeps the local estimate "bit-identical in provenance" to the global one, exactly as D-12 requires — it is a row-slice of the identical precomputed array, not a second computation.

**GMST is the exception** — verified this session: `gmst_dimensionality(data, geodesic=False, random_state=42)` has **no `precomputed_knn_dist_sq` parameter and no `k` parameter at all** (it takes only `data`, `geodesic`, `random_state`; when `geodesic=True` it internally fixes `k_geo = min(10, size - 1)`). It cannot be sliced onto a precomputed array like the other seven, and a literal reading of D-09 ("all eight run... at every `k` in the sweep") does not apply to GMST as written, since GMST has no `k` to sweep. For D-12's local probe, GMST must instead be called directly on the raw local-subset coordinates (`geometry.gmst_dimensionality(data[local_idx])`) — still frozen, still no duplication, but a structurally different call pattern than the other seven, and its provenance is *not* bit-identical to its own global call (it recomputes its own internal kNN structure on the smaller subset rather than reusing anything). **Flag this explicitly in the plan rather than silently treating GMST like the other seven.**

### Pattern 3: The immersion Jacobian rank check without a coordinate-singularity trap (D-14, Q5)

**What:** Verify that `lift ∘ warp` restricted to the canonical manifold is a genuine immersion at sampled points, without a spurious rank-drop caused by the *parametrization* rather than the manifold.
**Why it matters `[ASSUMED — standard differential geometry, not verified against a specific citation this session]`:** the canonical spherical-angle parametrization of `S^2`, `(θ,φ) -> (sinθcosφ, sinθsinφ, cosθ)`, has a genuine coordinate singularity at the poles (its own Jacobian drops rank there even though `S^2` itself has no singularity) — autodiffing the *whole* composite map through that parametrization would misreport a rank-2 immersion as rank-1 near the poles, for a reason that has nothing to do with whether `lift ∘ warp` is well-behaved.

**Recommended construction, by template:**
- **`S^1`**: `p(t) = (cos t, sin t)`, analytic tangent `v(t) = (-sin t, cos t)` — no singularity anywhere; safe to autodiff directly.
- **`T^2`** (standard torus embedding, `R > r > 0`): `((R + r cos v) cos u, (R + r cos v) sin u, r sin v)` — Jacobian never drops rank for any `(u, v)` as long as `R > r > 0`; safe to autodiff directly.
- **`S^2`**: avoid the angle parametrization for the rank check. Sample points via a normalized Gaussian (`u = g / ||g||`, `g ~ N(0, I_3)`), which has *no* coordinate chart at all to be singular — then compute the **tangent space directly** as any orthonormal basis of `u^⊥` (e.g. via `torch.linalg.qr` on `[u, e1, e2]` and dropping the first column), and check the rank of `d(lift ∘ warp)(u) @ tangent_basis` (a `D x 2` matrix) rather than the rank of an angle-parametrized composite map. This is well-posed everywhere on `S^2`, including at what would be the "poles" of a spherical-coordinate chart.
- **`B^d` (ball/disk)**: no canonical-embedding step needed beyond the identity (`B^d` already sits in `R^d`); the rank check is simply the rank of `d(lift ∘ warp)` restricted to `R^d`'s own coordinate directions.

**Rank tolerance:** use `torch.linalg.matrix_rank` (SVD-based) at float64, consistent with this project's existing float64 discipline (`_assert_float64` pattern in `chart_curvature.py`/`decoder_curvature.py`). Verified working this session: `torch.func.jacrev` on a toy `R^2 -> R^5` map returns exact singular values at float64 with no special handling needed.

## Common Pitfalls

### Pitfall 1 [HIGHEST PRIORITY — Q1/A-05, measured this session]: unthresholded `ripser(..., maxdim=2)` does not scale past `n≈400-500` for a genuine 2-manifold

**What goes wrong:** A single `H_2` diagram computation that looks identical in code to the phase's already-working `H_0`/`H_1` calls (02.6's `persistence_probe.py`) takes dramatically longer and grows far faster with `n`, because computing `H_2` requires enumerating 3-simplices, and a Vietoris-Rips filtration's simplex count explodes combinatorially as the filtration approaches completion.

**Measured this session** (`.venv/bin/python`, `ripser 0.6.15`, no `thresh`, `maxdim=2`, noisy samples with `noise=0.05`):

| n | `S^2` time | `S^2` n_H2_bars | `T^2` time | `T^2` n_H2_bars |
|---|---|---|---|---|
| 200 | 1.85s | 3 | 1.14s | 22 |
| 300 | 8.59s | 6 | 3.54s | 31 |
| 400 | 26.55s | 4 | 8.86s | 43 |
| 500 | **TIMEOUT >90s** | — | 18.75s | 45 |
| 600 | — | — | 29.90s | 60 |
| 800 | — | — | 74.66s | 62 |

`[VERIFIED: measured this session, single-threaded, 20-core/62GB machine, no other CPU contention at time of measurement]`. `S^2` is the more expensive template at matched `n` — likely because its smaller diameter (unit sphere, diameter ≈2) spends a larger fraction of the filtration's range in the expensive near-complete-complex regime than `T^2`'s larger diameter (≈6 at `R=2, r=1`) does. **Cost is template-dependent, not uniform across the four-template library** — size `n_ph` against the worst template (`S^2`), not an average.

**Why it happens:** `ripser`'s cost for degree-`k` persistence scales with the number of `(k+1)`-simplices that must be enumerated before the filtration completes; for `maxdim=2` this means 3-simplices, and a dense-enough point cloud produces these combinatorially as `n` grows.

**How to avoid / mitigate:**
1. Pin `n_ph` low enough that the worst-case (`S^2`, high-noise, `D=768`) unthresholded call completes in a tolerable per-call time — this session's data suggests `n_ph ≤ 300–400` for single-digit-to-tens-of-seconds per call, with real risk that `D=768` and immersion-warp noise behave worse than the flat-`R^3` fixture measured here (untested; **run a Wave-0 calibration at the actual `D=768`/noise before ratifying `n_ph`**).
2. Alternatively, use `ripser(..., thresh=<value>)` to cap the filtration radius — measured this session to cut cost substantially (S^2 at `thresh=1.3`: `n=600` in 14.0s vs. no-`thresh`'s `n=500` already timing out) but this **requires fixing the `finite_pairs` interaction described in Pitfall 2 below**, and choosing `thresh` incorrectly can silently truncate the exact feature the front end needs to detect (see Pitfall 2).
3. Do not assume the PU quick task's H2 timing figures (`~14.2s at n=383`, `~0.19s` for H1) transfer to this phase's synthetic templates — that number was measured on a near-degenerate, ball-like PU embedding, which is a *much* cheaper case for `ripser` than a cloud with genuine, spread-out `H_2` structure. This session's `S^2`/`T^2` numbers are the relevant ones for D-15's benchmark.

**Warning signs:** a benchmark run that silently hangs on one cell for minutes with no output; memory climbing past several GB on a single `ripser` call (observed: an early, less-controlled test of this same measurement grew to >7GB resident before being killed).

### Pitfall 2 [NEW FINDING, VERIFIED THIS SESSION]: `thresh` + `finite_pairs` silently discards genuine long-lived features, not just H0's structural infinity

**What goes wrong:** `persistence_probe.finite_pairs()` filters *every* row of a diagram whose death value is infinite, on the stated assumption that only `H_0`'s single true infinite bar (the whole point cloud, as one component) is ever infinite. That assumption is **only true when `ripser` is called with the default `thresh=inf`** (full filtration). `ripser.py`'s own documentation (`ripser.scikit-tda.org`, confirmed via WebFetch this session) states: *"classes will not be born if their birth time is under [sic] the threshold, and other classes will have infinite death times if their ordinary death time is above the threshold."* So a `thresh`-truncated diagram can carry **multiple** infinite-death bars per degree — including a genuine long-lived `H_2` void whose true death time simply exceeds `thresh`.

**Why it happens:** `finite_pairs` was written for `persistence_probe.py`'s original `maxdim=1` use case, where H0's one true infinite bar is the only infinite value ever encountered (no `thresh` was ever passed at any existing call site — confirmed by reading every call in `persistence_probe.py`).

**How to avoid:** if this phase's code adds a `thresh` parameter (recommended as one mitigation for Pitfall 1), it must **not** reuse `finite_pairs` unmodified on the resulting diagram without first confirming (a) the chosen `thresh` is comfortably larger than the true death time of any feature the decision rule needs to detect, or (b) a `thresh`-aware variant is written that distinguishes "genuinely eternal" (only possible for `H_0`) from "we stopped looking before it died." Getting this wrong makes a genuine `S^2`/`T^2` feature silently read as absent — exactly the "wrong template with no way to detect it" failure D-03's whole abstain design exists to avoid.

**Warning signs:** a template benchmark cell reporting a Betti vector of `(1,0,0)` (ball) for a cloud that was generated *as* `S^2`/`T^2`, at a rate that looks too high to be explained by noise alone.

### Pitfall 3 [VERIFIED, MEASURED THIS SESSION]: the frozen `gmst_dimensionality`'s `graph + graph.T` symmetrization doubles mutual-neighbour edge weights

**What goes wrong:** `geometry.gmst_dimensionality`'s `geodesic=True` branch builds its kNN graph with `graph = kneighbors_graph(subsample, k_geo, mode='distance'); graph = graph + graph.T`. Verified this session on a 20-point fixture: for any pair `(i, j)` that are *mutual* nearest neighbours (both directions present in the directed kNN graph), `graph[i,j] == graph[j,i] == true_distance` **before** the addition, and `(graph + graph.T)[i,j] == 2 * true_distance` **after** it — the summation double-counts the edge instead of leaving it unchanged. `scipy.sparse.csgraph.shortest_path` then computes a geodesic distance using the doubled weight, measured this session: the "shortest path" between two directly-adjacent mutual neighbours came back as `2.914` against a true Euclidean distance of `1.457` — a 2x inflation on exactly the edges that should be *cheapest* to traverse correctly.

**Why it happens:** `kneighbors_graph`'s directed output stores each direction's edge independently; when both directions happen to already hold the identical (symmetric) distance value, naive addition sums two equal numbers instead of picking one.

**How to avoid:** use `graph.maximum(graph.T)` (element-wise maximum, not sum) to symmetrize — verified this session to recover the exact true distance (`1.457245873756325`, matching `scipy.spatial.distance.pdist` to full float64 precision) at the same mutual-neighbour pair.

**This bug is in frozen code (`src/effdim/geometry.py`) and must not be fixed there** (`src/effdim/` is frozen this milestone) — but D-05's **new** geodesic-graph code for this phase must not copy the same pattern. This also means `gmst_dimensionality(data, geodesic=True)`'s own internal geodesic numbers should not be treated as equivalent to D-05's own faithfully-built geodesic distances; they are a different (and, for mutual-neighbour edges, measurably biased) computation.

**Warning signs:** a k-sweep where increasing `k` (which increases the fraction of mutual-neighbour pairs) produces geodesic distances that grow *less* smoothly than expected, or a geodesic/Euclidean distance ratio that looks implausibly large at small `k`.

### Pitfall 4: `geometry.compute_knn_distances` cannot build the D-05 geodesic graph — it discards indices and returns squared distances

**What goes wrong:** `compute_knn_distances(data, k)` returns only `distances_sq[:, 1:]` — a `(n, k)` array of **squared** distances with **no accompanying neighbour indices**. This is exactly the right shape for feeding the frozen estimators' `precomputed_knn_dist_sq` argument (D-09/D-12's use case), but it is the **wrong contract** for D-05's kNN graph, which needs to know *which* points are connected (indices), not just how far the `k`-th neighbour is, and needs **real**, not squared, distances as edge weights.

**How to avoid:** use `sklearn.neighbors.kneighbors_graph(data, k, mode="distance")` for D-05's graph construction (as `gmst_dimensionality` already does, and as Pattern 1 above shows) — this returns real Euclidean distances plus the correct sparse index structure in one call. Reserve `geometry.compute_knn_distances` for its actual designed purpose: feeding the frozen estimators' `precomputed_knn_dist_sq` for D-09's global and D-12's local `d_hat`. These are two different needs solved by two different existing calls; do not try to make one serve both.

**Warning signs:** an `AttributeError`/`TypeError` when trying to extract neighbour indices from `compute_knn_distances`'s return value, or (more dangerously) a geodesic graph silently built from squared distances if the conversion is forgotten — CONTEXT.md's own flagged "unit trap."

### Pitfall 5: D-02's confidence band and D-08's "independent draws" are two different statistical procedures that both call `ripser` repeatedly, and conflating them undercounts compute

**What goes wrong:** D-08's "several independent draws, Betti spread reported" means drawing multiple *fresh* point clouds from the immersion generator (a new noise/sampling realization each time) and reporting how much the *decision* varies across draws. D-02's bootstrap confidence band is a **different** procedure applied *within* a single one of those clouds: resample that cloud's own `n_ph` points with replacement, `B` times, to determine which of *that specific cloud's* bars are statistically significant. Both are required, both call `ripser` repeatedly, and their costs multiply rather than substitute for each other: `(draws) x (1 main call + B bootstrap calls per draw) x (2 metrics) x (grid cells)`.

**How to avoid:** be explicit in the plan about which loop is which. D-02's bootstrap resample operates on the *distance matrix's row/column indices* (verified this session, see Q2 below) — it is metric-agnostic and requires no adapter for the geodesic arm, but it does require rebuilding a `(B, n_ph, n_ph)`-scale sequence of `ripser` calls **per draw, per metric** on top of D-08's own draw count.

**Warning signs:** a compute estimate that only counts one of the two loops (common mistake: sizing for "how many draws" while forgetting each draw's confidence band is itself dozens of extra `ripser` calls).

## Code Examples

### D-02's bootstrap confidence band (Q2, Fasy et al.), metric-agnostic by construction

```python
# Source: Fasy, Lecci, Rinaldo, Chazal, Singh, Wasserman, "Confidence sets for persistence
# diagrams," Ann. Statist. 42(6):2301-2339 (2014), arXiv:1303.7117. Algorithm and default
# B=30/alpha=0.05 cross-checked against R TDA::bootstrapDiagram's documented defaults.
# [CITED: WebSearch + WebFetch this session]
import numpy as np

def bootstrap_band(D: np.ndarray, degree: int, B: int = 30, alpha: float = 0.05, seed: int = 0):
    """D: square symmetric distance matrix (Euclidean OR geodesic -- purely index-based,
    so this is unchanged for either metric). Returns c_alpha; a bar with
    life = death - birth < 2 * c_alpha is not distinguishable from noise at this confidence."""
    n = D.shape[0]
    rng = np.random.default_rng(seed)
    original_dgm = persistence_probe.persistence_diagram(D, maxdim=degree)[degree]

    boot_distances = []
    for _ in range(B):
        idx = rng.integers(0, n, size=n)          # WITH replacement, same size n
        D_boot = D[np.ix_(idx, idx)]                # pure index resample -- metric-agnostic
        boot_dgm = persistence_probe.persistence_diagram(D_boot, maxdim=degree)[degree]
        boot_distances.append(persim.bottleneck(original_dgm, boot_dgm))

    c_alpha = float(np.quantile(boot_distances, 1.0 - alpha))
    return c_alpha   # band = 2 * c_alpha
```

**Confirms the concrete algorithm asked for in Q2:** resample WITH replacement (not a smaller subsample — that is Fasy's *alternative* method, also valid under D-02's "bootstrap/subsample" wording but a genuinely different procedure with different regularity assumptions), same size `n` as the original cloud, `B=30` replicates by the R package's own documented default, `alpha=0.05` for a 95% band, statistic is bottleneck distance between each replicate's diagram and the *original* (not pairwise between replicates), final value is the `(1-alpha)` quantile of the `B` bottleneck distances, and the band applied to the original diagram is `2 * c_alpha`. **Confirmed metric-agnostic**: the resampling operates on `D`'s row/column indices via `D[np.ix_(idx, idx)]`, which is identical code whether `D` came from `cloud_distance_matrix` (Euclidean) or the geodesic route in Pattern 1 — no adapter needed, as CONTEXT.md's Q2 asked to confirm.

**Compute multiplier, stated plainly:** this is `B+1` `ripser` calls per `(cloud, metric, degree)` combination. At `n_ph=300`, `degree=2` (H2), using this session's `S^2` measurement of ~8.6s per call, one confidence band costs roughly `31 x 8.6s ≈ 4.4 minutes` for a single cloud's single metric's `H_2` significance test alone. This must be budgeted explicitly against D-15's grid size.

### Reading a Betti vector from a `ripser` diagram (Q4)

```python
# Source: verified this session against notebooks/pu_manifold/persistence_probe.py
dgms = persistence_probe.persistence_diagram(D, maxdim=2)   # [H0, H1, H2], each finite_pairs-filtered

# H0: finite_pairs already removed the ONE true infinite component death.
# beta_0 (component count) is NOT "len(dgms[0]) + 1" read off the diagram alone in general --
# use scipy.sparse.csgraph.connected_components(graph_at_the_significance_scale) directly,
# which is what D-07 already computes for the geodesic arm's own component read-out. For a
# clean read against the SAME significance convention used for H1/H2, count how many H0 bars
# in dgms[0] survive D-02's bootstrap band (life > 2*c_alpha); beta_0 = (that count) + 1.
significant_h0 = np.sum((dgms[0][:, 1] - dgms[0][:, 0]) > 2 * c_alpha_h0)
beta_0 = significant_h0 + 1

significant_h1 = np.sum((dgms[1][:, 1] - dgms[1][:, 0]) > 2 * c_alpha_h1)
beta_1 = significant_h1

significant_h2 = np.sum((dgms[2][:, 1] - dgms[2][:, 0]) > 2 * c_alpha_h2)
beta_2 = significant_h2
```

**Watch:** `finite_pairs` already dropped `H_0`'s one true infinite bar before this code ever sees `dgms[0]`, so `dgms[0]`'s row count is `n_ph - 1` at most (one fewer than the point count), not `n_ph`.
