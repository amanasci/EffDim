## Summary

This phase does not need new curvature machinery. Every piece of infrastructure the four-read-out Swiss-roll admission gate requires — the analytic Swiss-roll `H`, the raw-point baseline, the exact-autodiff decoder-curvature differentiation pattern, the seed-spread convention, and the verdict/gate plumbing — was already built, tested, and used once (on the CAE) in Phase 02.5. `notebooks/pu_manifold/curvature_probe.py` and `notebooks/pu_manifold/chart_curvature.py` are the artifacts of record; `notebooks/02.5_swiss_roll_chart_curvature_check.ipynb` is the reference notebook shape. This phase's job is to (a) run that same admission check against two substrates that already exist in the repo but have never had their *curvature* tested (plain `cae.PlainAutoEncoder`, and `cae.PlainAutoEncoder` trained under `topoae.train_topoae`), (b) resolve, with a citation rather than a hedge, whether TopoAE++ is even attemptable at the PU regime's working dimension, and (c) scope what a from-scratch RTD-AE / Witness AE / GRAE implementation would actually cost if the two free candidates are not enough.

The two free candidates are structurally different from the CAE in exactly the way that matters. 02.5-09 diagnosed the CAE's curvature failure as **atlas fragmentation**: the trained surface is smooth within each chart but joined to its neighbours by near-straight chords at chart boundaries, and second derivatives see every one of those joins (`rho_chart` tracked the number of live charts almost perfectly: 3 charts -> 0.8665, 5 -> 0.4250, 8 -> -0.0604/-0.1444). Neither `PlainAutoEncoder` nor a `PlainAutoEncoder` trained with the added topological loss has any chart boundary at all — the decoder is one smooth MLP end to end. This does not guarantee curvature fidelity (Section 2d/Addendum C's "compressed amplitude" failure mode is a live risk for any smooth decoder, chart or not), but it does mean the *specific, measured* mechanism that killed the CAE cannot recur in the same form. That is a testable hypothesis, not a result — which is exactly why the admission notebooks have to be run, not assumed.

Both free candidates also already have sealed PU-side fits sitting in the cache, ready for whichever follow-on phase runs the real gate: `cae_ctrl_plainae20_43cf438bc944c509.npz` / `..._plainae40_...` (Phase 02.2's matched-capacity control, C2-smooth SiLU) and sixteen TopoAE fits across the `{8,16,20,24,32,40}` ladder (Phase 02.4, also SiLU). If either clears its Swiss-roll admission gate, the follow-on phase does not need to retrain anything on PU data to run its own gate — it needs only to differentiate what is already on disk, exactly the D-10 reuse pattern Phase 02.5 established for the CAE. Nothing analogous exists yet for RTD-AE, Witness AE, or GRAE: each would need its own from-scratch implementation, its own faithful-to-paper audit, its own Swiss-roll admission notebook, *and* its own from-scratch PU fit before a follow-on gate could even begin. That asymmetry is the strongest argument in this document for a cheap-first, stop-early screening order.

TopoAE++ is a clean **NO-GO**, on two independent grounds, both citable rather than assumed. Mathematically, the paper's own fast algorithm is explicitly restricted to `R^2` ("For visualization purposes, in the following we take `Z = R^2`"; the fast exact-PH-in-the-plane algorithm relies on relative-neighbourhood-graph minmax triangulations whose defining lemma is stated "in the plane" [Clémot, Digne & Tierny, arXiv:2502.20215]) — there is no stated or implied path to `d = 40`, or even to the PU regime's own working dimension of ~20-25. Practically, its reference implementation (`github.com/MClemot/TopologicalAutoencodersPlusPlus`) depends on CGAL, Qt5, ParaView, and the Topology ToolKit (TTK) — a C++/visualization stack with no Python-pip installation path, incompatible with this milestone's notebook-only, `pyproject.toml`-frozen posture regardless of the dimensionality question. Do not budget an implementation task for it this phase.

**Primary recommendation:** Build two new Swiss-roll curvature admission notebooks reusing `curvature_probe.py`/`chart_curvature.py`'s existing machinery unchanged (plain AE and TopoAE-trained-PlainAutoEncoder), each at four seeds minimum with the full per-seed four-axis table reported exactly in 02.5-09's format; rule out TopoAE++ this phase without implementing it; and gate any RTD-AE/Witness AE/GRAE implementation behind an explicit "the two free candidates did not admit" finding, since building any of the three costs a phase-sized effort and two of the three have real dependency/licensing/provenance costs this milestone has not paid before.

### Pattern 1: A decoder-curvature map with no chart routing (new, minimal)

**What:** `chart_curvature.chart_decoder_map(model, chart_idx)` composes two hops (`chart_decoders[chart_idx]` then `embedding_decoder`) specifically because the CAE has that two-stage structure. Neither `PlainAutoEncoder` nor a TopoAE-trained `PlainAutoEncoder` has a chart stage — `model.decode(z)` is the entire decoder. The differentiated map is therefore *simpler* than the CAE case, not merely different.

**When to use:** For both free candidates' admission notebooks.

**Example:**
```python
# Source: mirrors notebooks/pu_manifold/chart_curvature.py's Pattern 4
# (chart_decoder_map / _chunked_jacobian / chart_mean_curvature), with the
# chart-routing indirection removed -- not a new derivation, a strict
# simplification of already-reviewed code.
import torch
from torch.func import jacrev, hessian, vmap
from pu_manifold import cae as cae_mod
from pu_manifold.chart_curvature import (
    assert_c2_activation, VMAP_CHUNK, _pad_to_chunk, CURVATURE_CONVENTION,
)

def plain_decoder_map(model: "cae_mod.PlainAutoEncoder"):
    """Return decode_one(z): (latent_dim,) -> (out_dim,) through the model's
    single decoder MLP -- no chart routing, no argmax discontinuity."""
    def decode_one(z: torch.Tensor) -> torch.Tensor:
        return model.decode(z.unsqueeze(0)).squeeze(0)
    return decode_one

def plain_decoder_curvature(model: "cae_mod.PlainAutoEncoder", z: torch.Tensor) -> torch.Tensor:
    """z: (batch, latent_dim) float64. Returns (batch, out_dim) mean curvature
    vectors under CURVATURE_CONVENTION = 'trace', identical convention to
    chart_curvature.chart_mean_curvature."""
    assert_c2_activation(model)  # SAME guard, reused unchanged
    decode_one = plain_decoder_map(model)

    parts_J, parts_H = [], []
    for start in range(0, z.shape[0], VMAP_CHUNK):
        real = z[start:start + VMAP_CHUNK]
        padded = _pad_to_chunk(real)
        parts_J.append(vmap(jacrev(decode_one))(padded)[: real.shape[0]])
        parts_H.append(vmap(hessian(decode_one))(padded)[: real.shape[0]])
    J = torch.cat(parts_J, dim=0)      # (batch, out_dim, latent_dim)
    Hess = torch.cat(parts_H, dim=0)   # (batch, out_dim, latent_dim, latent_dim)

    g = torch.einsum("boi,boj->bij", J, J)
    g_inv = torch.linalg.inv(g)
    proj = torch.eye(J.shape[-1], dtype=J.dtype)[None] - torch.einsum(
        "boi,bij,bpj->bop", J, g_inv, J
    )
    II = torch.einsum("bop,bpjk->bojk", proj, Hess)
    H = torch.einsum("bij,boij->bo", g_inv, II)   # g-trace, CURVATURE_CONVENTION="trace"
    return H
```

**Critical pitfall to avoid:** do not wrap `model.forward` (which returns `{"z": ..., "y": ...}` and re-derives `z` internally) under `jacrev`/`hessian` — that would differentiate through the *encoder* as well and measure the curvature of the encoder-composed round-trip map, not of the decoder's own image manifold. Use `model.decode` directly, exactly as `chart_curvature.py`'s own docstring warns for `cae._decode_through_chart`.

### Pattern 2: The four-read-out report is already generic — reuse it unchanged

**What:** `chart_curvature.curvature_fidelity_report(H_est, H_true)` takes only `(n, D)` arrays; it has no CAE-specific logic anywhere in its body (confirmed by reading the full function — Section "Code Examples" reproduces its docstring). It already implements exactly the four axes the phase description's success criterion 3 requires: direction (median cosine similarity), magnitude (median ratio **and** CV, both required — see the function's own worked argument for why one alone hides a failure mode), calibration (slope/intercept/R²), plus `curvature_probe.spearman_gate_statistic` for rank.

**When to use:** For every candidate, without modification. This is the single largest cost-saving fact in this document: the phase description's success criterion 3 is not new work, it is a function call.

### Anti-Patterns to Avoid

- **Averaging the four seeds before reporting.** 02.5-09's own finding is that the CAE's mean Spearman across seeds would have hidden a seed that beats the raw-point baseline entirely (seed 2: `rho=0.8665`) behind two seeds that look structureless. Report the full per-seed table, exactly as `02.5-09-SUMMARY.md`'s table does, for every candidate.
- **Reimplementing `curvature_fidelity_report` "for the plain AE case."** It has no chart-specific logic. Reimplementing it introduces a second, potentially divergent, copy of the exact function this phase's admission depends on.
- **Editing `chart_curvature.py` to add a `chart_idx=None` branch.** Tempting, but couples a sealed, tested module (Phase 02.5's artifact) to this phase's needs. A new sibling module is this codebase's own established pattern at every prior model insertion (`curvature_probe.py` beside `curvature.py`, `topoae.py` beside `cae.py`, `chart_curvature.py` itself beside both).
- **Treating a high Spearman as sufficient admission.** `02.5-NOTE-randomized-trace.md`'s worked example (`y = 0.7 a x^2` vs `y = a x^2`) and the CAE's own measured calibration slope of `-0.1856` are both concrete demonstrations that rank alone is not evidence of amplitude fidelity. All four axes must clear, or the admission argument must say explicitly which one(s) it is choosing to accept a weakness on and why.
- **Implementing TopoAE++ "just the loss, not the fast algorithm."** The paper's zero-loss guarantee is proven to fail for `PH^d, d >= 1` under a *naive* extension (its own Section 3 counter-example); the fast algorithm is not an optional speed optimization bolted onto an otherwise-portable loss, it is the paper's actual proposed fix for that failure, and it is planar by construction. A "just the loss" implementation would be reimplementing exactly the broken naive extension the paper itself demonstrates does not work.

## TopoAE++ Feasibility Gate — resolved: NO-GO

**Question:** does TopoAE++'s fast algorithm apply at the PU regime's working dimension (`d ~ 20-25`, or even the CAE's own `chart_dim=20`/`embed_dim=40`), or is it planar-specific?

**Answer: planar-specific. NO-GO, on two independent grounds.**

**1. Mathematical restriction, quoted directly from the paper [CITED: arxiv.org/abs/2502.20215, cross-verified via both the abstract page and the HTML full-text rendering — MEDIUM confidence, direct quotation from the authoritative source].** The paper states its own scope explicitly: *"For visualization purposes, in the following we take `Z = R^2`"* — the method is defined for a 2-dimensional latent space, not a general `d`. Its headline contribution, the fast exact-persistent-homology algorithm, is stated as being *"for the exact computation of PH for Rips filtrations in the plane"* and, more specifically, *"a new fast algorithm that computes PH for the Rips filtration of a two-dimensional point cloud."* The algorithm's core geometric lemma is stated with the planar restriction built in: *"In the plane, an edge that intersects an RNG edge kills no `PH^1` class of positive persistence"* (the paper's own Lemma 3) — the relative-neighbourhood-graph (RNG) and minmax-triangulation machinery this lemma depends on are 2D computational-geometry constructs with no stated `d`-dimensional generalization. There is no discussion anywhere in the abstract or full text (searched explicitly) of scaling the fast algorithm to higher-dimensional latent spaces; the paper's own counter-example proving TopoAE's zero-loss property breaks for `PH^d, d >= 1` is presented as the *motivation* for restricting to the 2D case where an exact fast algorithm is tractable, not as a stepping stone toward a higher-`d` version.

**2. Reference implementation, independently confirmed [CITED: github.com/MClemot/TopologicalAutoencodersPlusPlus].** The repository's own dependency list — cmake, ninja-build, Boost, OpenGL, CGAL, Qt5, LibTorch (C++, not the Python `torch` package), ParaView, and the Topology ToolKit (TTK) — is a C++ visualization-and-computational-geometry stack with no `pip install` path. This is incompatible with this milestone's "no new package without a legitimacy checkpoint" posture regardless of the dimensionality question, and it is a categorically different kind of dependency cost than anything in the "Reference Implementations" table below (which are all installable Python packages, however heavy).

**Recommendation:** do not budget an implementation task for TopoAE++ this phase, under any screening outcome. If PH^1 loop-preservation at the PU regime's own working dimension is ever wanted, that requires research this paper's own authors did not attempt (a genuine `d`-dimensional generalization of their fast algorithm) — out of scope for a screening phase, and arguably out of scope for this milestone entirely given the recorded finding that PU topology beyond connectedness is bounded and largely unmeasured for `beta_2` (ROADMAP's own effect-size framing).

## The Four-Read-Out Admission Metric — fully specified, already implemented

This generalizes `02.5-RESEARCH.md`'s Pattern 1/4 and `02.5-NOTE-randomized-trace.md`'s Addendum C into an exact specification, citing the code that already computes each piece.

**Analytic ground truth.** `curvature_probe.swiss_roll_analytic_H(t) = (t^2 + 2) / (1 + t^2)^1.5` — the trace-convention (`H = tr(II)`, not the averaged `H/d`) mean curvature of `sklearn.datasets.make_swiss_roll`'s surface, derived from the surface being a ruled generalized cylinder over the generator's own Archimedean-spiral arc parameter `t`: one principal curvature is identically zero (the ruling/`y` direction), the other is the planar spiral's own curvature `kappa(t) = (t^2 + 2*t'^2... )` reducing to the stated closed form at `r(t)=t, r'(t)=1, r''(t)=0`. `curvature_probe.swiss_roll_analytic_H_scaled(t, global_std)` rescales it by CLAUDE.md's mandatory single-global-scalar preprocessing (`H_scaled = H_raw * global_std`, since curvature has units of inverse length and the point cloud is divided by `global_std`). **For the mean curvature *vector*** (needed for cosine similarity, not just the norm), 02.5-09 derived the direction in-notebook from the same ruled-cylinder structure — the curvature vector lies entirely in the roll's `x`-`z` plane — and pinned its norm against `swiss_roll_analytic_H_scaled` to `8.88e-16`. Any new admission notebook should reuse that same derivation (it is fixture construction, which CLAUDE.md places in the notebook, not model code) rather than re-deriving it from scratch.

**Raw-point baseline.** `curvature_probe.centroid_mean_curvature` (or `centroid_mean_curvature_both_densities`) at `k=30, d=2` on the identical fixture reproduces `rho=0.6712` exactly, seed-independent (the raw-point estimator has no torch seed — its own numpy random state is fixed by the fixture's own `random_state`). **Caveat carried forward from 02.5-09's own reported finding, not to be dropped silently:** this baseline itself only cleared 3 of its own notebook's 4 sanity lines (it missed a `>0.90` bar in the module's own original Swiss-roll check) — so "beats the raw-point baseline" is a real but *weaker* bar than "recovers the analytic answer," and any admission argument built on beating it should say so explicitly, exactly as `02.5-09-SUMMARY.md`'s own "Reported, not absorbed" section already flags.

**The four axes, and the failure mode each one catches (`chart_curvature.curvature_fidelity_report`'s own docstring, quoted for provenance):**

| Axis | Computation | Failure mode it catches |
|---|---|---|
| 1. Direction | `median(cosine_similarity(H_est_i, H_true_i))` per point | A decoder whose curvature points the wrong way even if magnitude is fine — orientation error |
| 2. Magnitude | `median(‖H_est‖/‖H_true‖)` **and** `CV(‖H_est‖/‖H_true‖, ddof=1)`, both required | Amplitude attenuation/inflation. Neither number alone suffices: 02.5-RESEARCH.md's own Section 1a table shows `d=2` giving a clean median 0.905 at CV 0.250 ("attenuated but calibratable") versus `d=20` giving CV 2.250 at a non-monotone median ("destroyed") — the *pair* distinguishes these, either alone does not |
| 3. Calibration | least-squares `‖H_est‖ = a·‖H_true‖ + b`; check `a ≈ 1`, `b ≈ 0`, and `R²` | A rank statistic cannot see `a = 0.5` (a decoder that compresses every magnitude by a constant scores a perfect rank correlation); calibration can. The CAE's own measured slope was `a = -0.1856` at `R² = 0.0533` — essentially no information, invisible to Spearman alone |
| 4. Rank | `scipy.stats.spearmanr` via `curvature_probe.spearman_gate_statistic` | Whether the estimate orders points correctly at all — the axis every prior stage-1/stage-2 gate in this milestone has gated on, retained here for continuity, but explicitly **not sufficient alone** (item 3's point) |

**Points excluded:** `curvature_fidelity_report` excludes points with `‖H_true‖ <= min_true_norm` (default `1e-12`) from all three of its own statistics — a flat point has no curvature to get right, and including it would silently contribute a division by near-zero. Excluded-point count is reported (`n_excluded`), not hidden.

## Faithful-to-Paper Audit Protocol — generalized from the CAE precedent

The phase description's own framing ("the CAE audit found two [deviations]... one of them hid the effect an experiment was built to find") refers specifically to the quick task `20260809-cae-undertraining-test` (`.planning/quick/20260809-cae-undertraining-test/SUMMARY.md`), not to the original Phase 02.2 pre-registration — worth stating plainly since the two documents found different things. Combined with Phase 02.4's own five documented TopoAE fidelity gaps (found by literally diffing `topoae.py` against `github.com/BorgwardtLab/topological-autoencoders`), these give a reusable checklist:

1. **Diff against a reference implementation, if one exists — line by line, not equation by equation.** Phase 02.4's four (later five) fidelity gaps were found by comparing `topoae.py` directly against the authors' own repository, not by re-deriving the loss from the paper's equations a second time: a missing jointly-trained `latent_norm` scale, a missing per-batch `d_x/d_x.max()` ambient normalization, a spurious `/batch_size` division, a missing `1/2` factor on each directional loss term, and (found later, deliberately left unfixed and recorded) a sum-vs-mean divergence on the reconstruction term. None of these would have been caught by checking that the implemented loss "looks like" the paper's equation — each is a scale or normalization detail invisible without the diff.

2. **Verify every threshold/criterion's mathematical *form*, not just its value, against the paper's literal statement.** The CAE's pruning criterion is the sharpest example in this project: the paper specifies pruning by an *absolute* decoder-weight-norm tolerance; the implementation (`cae.chart_survival`) thresholds each chart's mass as a *ratio to the largest chart's mass*. These are not the same rule with different constants — a ratio-based criterion is invariant to uniform shrinkage of every chart together, so a chart that has won **zero of 3000 points** and contributes nothing can sit at full weight mass indefinitely, because the only force acting on it (weight decay) shrinks the reference chart by the same proportion. The quick task measured this directly: 24 fits, six training-hyperparameter arms, four seeds each, **the criterion never once fired** — not because no chart was ever dead (one measurably won zero points at two independently retrained seeds), but because the criterion is structurally incapable of detecting that condition.

3. **Verify training budget/schedule against what the paper's own experiments actually used, and report the gap as a measured cost, not an assumption.** The same quick task found the sealed CAE fit under-trained for reconstruction relative to a 100-epoch control (3.2x relative-error improvement, 0.1576 -> 0.0485) — but, importantly, also found that *more training did not fix the pruning-criterion defect or the curvature failure*: no arm at any epoch budget reached the raw-point curvature baseline. This is the general lesson: an epoch-budget deviation and a structural-criterion deviation can look like the same symptom (a metric coming in worse than expected) while having completely different remedies, and only measuring both separately reveals which is which.

4. **Construct at least one adversarial fixture designed to make a broken criterion fail, and confirm the implemented rule actually fires on it.** The quick task's decisive evidence was not a passive audit of the code — it was an executor-side experiment that deliberately created a dead chart (via `argmin_alpha e`/`argmax_alpha p` occupancy tracking) and then checked whether `chart_survival` detected it. A criterion that has never been tested against the condition it exists to detect has not been verified, regardless of how many times it has run without error.

5. **Name every deviation explicitly, with its measured or argued cost — never silently.** Both precedents in this project (CAE's SiLU-for-ReLU substitution measured at `-1.283e-06` reconstruction cost; TopoAE's gap #5 explicitly left unfixed with its invariance argument recorded) follow this discipline. A new candidate's audit document should read like `02.2-FINDINGS.md` Section 5 or `02.4-PREREGISTRATION-AMENDMENT-02.md`: a list of every place the implementation diverges from the paper, each with either a measured cost or an argued reason the divergence does not matter.

**Applying this to the two free candidates:** neither needs a fresh audit this phase. `PlainAutoEncoder` is the paper's own eq. 22 reference architecture (per `cae.py`'s own docstring, already audited as part of Phase 02.2's CAE-03 control), and `train_topoae` carries Phase 02.4's own five-gap audit already on record, with gap #5 explicitly disclosed and left unfixed. **Applying it to any of RTD-AE/Witness AE/GRAE**, should Tier 2+ be reached: budget the audit as its own task, with a named reference implementation to diff against (Section "Reference Implementations") and at least one adversarial fixture per non-trivial criterion (analogous to item 4 above) before trusting any Swiss-roll admission result from a from-scratch implementation.

## Seed Protocol — what "spread reported" concretely means

**Statistic:** report the full per-seed, per-axis table — exactly the format `02.5-09-SUMMARY.md`'s own "Seed Sensitivity" section already used (torch seed | reconstruction rel. err | `rho` | median magnitude ratio | magnitude CV | calibration slope | max metric condition number), one row per seed, four seeds minimum, no averaging-only summary. This is a direct precedent already executed once in this milestone, not a new design.

**Spread statistic, proposed [Claude's Discretion — to be ratified, not assumed]:** `SPREAD = max(values) - min(values)` over the four seeds' Spearman rho (the rank axis, since it is the one already load-bearing in every prior gate in this milestone), reported alongside the mean/median.

**Disqualifying condition, proposed:** a candidate's Stage-A read-out is treated as **not admitted, drew well rather than passed** if either:
1. Any one of the four seeds falls below a stated floor on any of the four axes (not just the mean/median across seeds) — structural instability at even one seed is disqualifying on its own, mirroring this milestone's own repeated finding (Phase 02.5's stage-1 seed axis, the CAE's own seed lottery) that a single lucky seed is not evidence of a working method; or
2. `SPREAD` (item above) **exceeds the candidate's own margin to whatever floor is used for admission** — i.e., `SPREAD > (mean_rho - floor)`. This is a direct paraphrase of `02.5-NOTE-substrate-selection.md` Section 3's own stated rule: *"a substrate whose across-seed spread exceeds its margin to threshold has not passed, it has drawn well"* — and it is calibrated against a concrete, already-measured negative example: the CAE's own four-seed range was `0.8665 - (-0.1444) = 1.0109`, which exceeds any plausible margin to any plausible floor by a wide margin, consistent with the CAE's Stage-A disqualification standing regardless of exactly where the floor is set.

**Why this is proposed rather than asserted:** no CONTEXT.md exists for this phase (it was inserted and scoped directly in the ROADMAP, not discussed), so there is no locked decision to defer to here the way `02.5-CONTEXT.md`'s D-01/D-02 fixed stage 1's threshold-setting procedure. This document's job is to hand the planner a concrete, checkable proposal — consistent with this milestone's own established patterns (`SPEARMAN_ABSOLUTE_FLOOR`/`REGION_ABSOLUTE_FLOOR` in `02.5-PREREGISTRATION.md`, both derived from a noise-oracle ceiling calibration) — not to invent a new threshold-setting philosophy. The exact numeric floor is deliberately left open here; `curvature_probe.py`'s existing `SPEARMAN_ABSOLUTE_FLOOR = 0.50` is available for reuse if the planner judges the stage-1 calibration transfers (same fixture family, same trace convention), but that is itself a decision worth stating explicitly rather than inheriting silently.

## Promotion Rule — a checkable decision procedure

Proposed procedure for "at most one candidate promoted" (success criterion 5), stated so a reader can verify it was followed:

1. **Every screened candidate gets the full per-seed, four-axis table** (Section "Seed Protocol"), never an averaged-only summary.
2. **A candidate clears Stage A only if all three hold:** (a) it is not disqualified under either condition in "Seed Protocol" above; (b) its calibration slope is not close to zero (the CAE's own `a = -0.1856` at `R² = 0.0533` is the disqualifying reference point — a slope statistically indistinguishable from zero means magnitude carries no information, which the phase description's own success criterion 3 exists specifically to catch); and (c) it beats the raw-point baseline on at least the rank axis, with the caveat (Section "Four-Read-Out Metric") that the baseline itself is an imperfect reference, stated explicitly if invoked.
3. **If zero candidates clear:** "no promotion" is a complete, reportable outcome for this phase, consistent with this project's repeated standing posture that a negative result is a legitimate milestone outcome (Phase 2's `GATE_VERDICT=FAIL`, Phase 02.2's `CAE_VERDICT=FAIL`, Phase 02.4's `TOPOAE_VERDICT=FAIL`, Phase 02.5's `CURVATURE_VERDICT=FAIL` — none of these was treated as an error to route around). Recommend naming Ollivier-Ricci/intrinsic curvature (already the named live option in `02.5-PREREGISTRATION.md` Section 10 and `02.5-FINDINGS-AMENDED-01.md` Section 7) as the next step, rather than inventing a new fallback here.
4. **If exactly one candidate clears:** promote it, with the promotion argument stated against the recorded effect sizes (3.4x chart-vs-single on H0 retention; ~6% topological-loss axis) exactly as success criterion 5 requires — not merely asserted as "it passed."
5. **If more than one candidate clears:** prefer, in order — (a) a candidate requiring no new implementation and no new PU-side training over one requiring either (plain AE and TopoAE both qualify; RTD-AE/Witness AE/GRAE do not); (b) among tied-tier candidates, the one whose PU-side context (already-measured H0 retention, absence of an atlas-fragmentation-style mechanism, etc.) gives an independently argued reason to prefer it, stated explicitly rather than by default ordering. A genuinely new implementation should only be preferred over an already-built, already-PU-fitted candidate if its expected gain is argued to exceed the two named reference effect sizes explicitly — "a better topological loss" alone is, by this project's own recorded numbers, arguing inside the 6%.

**This procedure is a proposal, not a locked rule** — flagged the same way as "Seed Protocol" above, for the same reason (no CONTEXT.md exists for this phase). The planner and any subsequent `/gsd-discuss-phase` pass should treat steps 2(b)/2(c)'s exact numeric bars as open, and everything else as a checkable structure to ratify or amend.

## Common Pitfalls

### Pitfall 1: Treating "already has a Swiss roll notebook" as "already screened"

**What goes wrong:** `02.2_swiss_roll_cae_check.ipynb` and `02.4_swiss_roll_topoae_check.ipynb` both exist and both pass their own gates — but neither tests curvature. Reading their existence as evidence that plain AE or TopoAE are already admitted would be a category error identical to the one `02.5-NOTE-substrate-selection.md` Section 4 explicitly warns against ("reconstruction quality validates nothing about curvature").
**Why it happens:** the notebooks share a name pattern and a baseline model with the ones this phase needs to build, making it easy to conflate "this model has a Swiss roll notebook" with "this model has passed the specific check this phase needs."
**How to avoid:** confirm explicitly, per candidate, whether the existing notebook's read-out includes a curvature comparison against analytic `H`. As of this research, none of the existing notebooks except `02.5_swiss_roll_chart_curvature_check.ipynb` (the CAE's, which failed) do.
**Warning signs:** a plan or summary citing a reconstruction-only pass/fail line as evidence for this phase's admission gate.

### Pitfall 2: Assuming the CAE's failure mechanism transfers to non-chart substrates as a reason to skip Tier 1

**What goes wrong:** concluding "curvature through a learned decoder doesn't work" from the CAE result alone, and treating Tier 1 as pre-doomed.
**Why it happens:** the CAE is the only decoder substrate this milestone has tested for curvature so far, so its result is the only data point available, and it is tempting to generalize from n=1.
**How to avoid:** 02.5-09's own diagnosis is specific to atlas fragmentation — a mechanism that requires chart boundaries to exist. Plain AE and TopoAE have no chart boundaries. This is an argument for optimism about Tier 1, not evidence either way; the notebooks still have to be run.
**Warning signs:** a plan that skips Tier 1 and proceeds directly to a new implementation "because decoders don't preserve curvature," citing only the CAE result.

### Pitfall 3: Conflating "beats the raw-point baseline" with "recovers the analytic answer"

**What goes wrong:** treating Stage-A admission as cleared once a candidate's Spearman exceeds `0.6712` (the raw-point baseline), without checking that the baseline itself is a strong reference.
**Why it happens:** the baseline is the only other number available for comparison, and it is tempting to treat "beats the baseline" as sufficient.
**How to avoid:** 02.5-09's own reported finding is that the raw-point baseline itself only cleared 3 of 4 of its own notebook's original sanity lines. State this caveat explicitly whenever the baseline is invoked as a bar, per 02.5-09-SUMMARY.md's own "Reported, not absorbed" precedent.
**Warning signs:** an admission argument that cites only the rank-axis comparison against the baseline, without the calibration and magnitude axes alongside it.

### Pitfall 4: Building a new candidate's model class inside the Swiss-roll notebook

**What goes wrong:** CLAUDE.md requires the notebook to import model code unchanged; if the model does not exist yet in `notebooks/pu_manifold/` for a new-implementation candidate (RTD-AE, Witness AE, GRAE), there is a temptation to write it directly in the notebook "just this once."
**Why it happens:** it is the path of least resistance when no module exists yet.
**How to avoid:** any new-implementation candidate needs its model class and training loop written as a proper `notebooks/pu_manifold/` module first (mirroring `cae.py`/`topoae.py`'s own structure), with its faithful-to-paper audit against that module, before any Swiss-roll notebook imports it. CLAUDE.md's rule exists precisely to prevent "the notebook version" and "the real version" diverging.
**Warning signs:** a Swiss-roll notebook containing a `class` or `def train_*` definition for a candidate that has no corresponding file under `notebooks/pu_manifold/`.

```python
# Source: notebooks/pu_manifold/curvature_probe.py, lines 51-85 (read directly).
def swiss_roll_analytic_H(t):
    """Trace-convention H(t) = (t**2 + 2) / (1 + t**2)**1.5, from the Swiss roll's
    ruled-generalized-cylinder structure over its own Archimedean-spiral arc parameter."""
    return (t**2 + 2) / (1 + t**2) ** 1.5

def swiss_roll_analytic_H_scaled(t, global_std):
    """Rescaled for CLAUDE.md's centre-and-divide-by-one-global-std preprocessing:
    H_scaled(t) = H_raw(t) * global_std (curvature has units of inverse length)."""
    return swiss_roll_analytic_H(t) * global_std
```
