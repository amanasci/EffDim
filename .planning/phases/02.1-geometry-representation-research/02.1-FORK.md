# Phase 02.1 Fork Verdict — Coordinate-Producing vs Graph-Native

**Written and committed strictly after `02.1-PREREGISTRATION.md`** (`faefac1`), against the fork
test that document fixed before this verdict existed. See this plan's `<verify>` step for the
mechanical proof (`git merge-base --is-ancestor` plus `git cat-file -e` showing the
pre-registration commit's tree did not contain this document).

## Fork Verdict

**This phase proceeds down the coordinate-producing branch.** Of the six candidate families
`02.1-RESEARCH.md` names, four are coordinate-producing (hyperbolic Poincare/Lorentz,
mixed-curvature product manifold, pseudo-Euclidean/Krein, diffusion maps) and two are graph-native
(Ollivier-Ricci, Forman-Ricci). Applying the Fork Test pre-registered above, the coordinate-
producing families are the only ones that can supply DEC-01's decoder with something to fit
against — that is not a preference between the branches, it is what the fork test's definition
directly determines once each family's output type is checked against it. The graph-native
branch is not set aside for difficulty; it is set aside because it cannot satisfy the requirement
the coordinate-producing branch exists to satisfy, on grounds recorded concretely below.

## Applying the Fork Test to All Six Candidate Families

The pre-registered test: a candidate is coordinate-producing iff it yields, for each of the
10,000 points, a finite real coordinate vector from which a twice-differentiable map into R^768
can be fitted — precisely what DEC-01's "A reader can train a decoder mapping Isomap coordinates
to the original 768-d embedding, using a C2-smooth activation throughout the forward path" and
CURV-01..CURV-03's batched Jacobian/Hessian path consume. CURV-01 asks for "the first fundamental
form from the decoder Jacobian via `torch.func` autodiff, batched over all points"; CURV-02 for
"the second fundamental form as the normal-projected ambient Hessian of the decoder"; CURV-03 for
"the mean curvature vector field and its norm." All three presuppose a differentiable decoder,
which presupposes a coordinate domain to differentiate it over.

| Candidate family | Output | Coordinate vector per point? | Fork test result |
|---|---|---|---|
| Hyperbolic (Poincare ball / Lorentz hyperboloid) | A point in Poincare-ball or Lorentz coordinates per input point | Yes — a finite real vector (Poincare: unit-ball coordinates; Lorentz: hyperboloid coordinates, both differentiably related to a Euclidean chart) | **Coordinate-producing** |
| Mixed-curvature product manifold | A tuple of per-factor coordinates (hyperbolic x spherical x Euclidean factors), concatenable into one real vector per point | Yes — same reasoning as hyperbolic, extended across factors | **Coordinate-producing** |
| Pseudo-Euclidean / Krein-space retention | A `(p, q)`-signature real coordinate vector per point, from the top-`p` positive and top-`q` negative eigenvectors of the double-centred geodesic matrix | Yes — a finite real vector in R^(p+q); the indefinite bilinear form lives in how distances are computed *from* the coordinates, not in the coordinates' own type | **Coordinate-producing** |
| Diffusion maps | A real coordinate vector per point from the leading eigenfunctions of the diffusion operator | Yes — structurally the same output type as Isomap/classical MDS, just a different kernel | **Coordinate-producing** |
| Ollivier-Ricci curvature | A scalar curvature value per edge (optionally aggregated to a scalar per node) of the existing k*=15 graph | No — no coordinate vector at all, only a per-edge or per-node scalar annotation on the graph | **Graph-native** |
| Forman-Ricci curvature | A scalar curvature value per edge (combinatorial, faster to compute than Ollivier-Ricci) of the existing graph | No — same output type as Ollivier-Ricci | **Graph-native** |

Four of six families clear the test; the two that do not are exactly the two RESEARCH.md's
Entanglement item 1 names as the fork's graph-native side. This is the same split RESEARCH.md's
Summary and Architectural Responsibility Map already anticipated; this section is what makes it a
verdict rather than a description.

## Coordinate-Producing Branch

What it computes: for every one of the 10,000 points, a finite real coordinate vector in a
target space that is not required to be flat Euclidean R^k — a Poincare-ball point, a Lorentz-
hyperboloid point, a point in a product of curved factors, a `(p, q)`-signature pseudo-Euclidean
vector, or a diffusion-map coordinate. What it delivers to the analysis layer: exactly the input
type DEC-01 already expects, with the specific target space and its distance function
re-specified rather than assumed flat. Its relationship to the milestone's actual question: this
is the branch that lets curvature be measured *analytically*, via the decoder's own Jacobian and
Hessian (CURV-01/CURV-02), which is what CURV-03's mean-curvature-vector output specifically
requires. Every candidate in this family is evaluated on the pre-registered Distortion Statistic
(`DISTORTION`, `DISTORTION_SIGNED`) over the fixed 200,000-pair sample, and its own
Working-Dimension Rule elbow — never on an inherited or ad hoc criterion.

## Graph-Native Branch

What it computes: a scalar curvature value attached to each edge (Ollivier-Ricci, via an optimal-
transport comparison of neighbourhoods across an edge; Forman-Ricci, via a combinatorial
formula on the same edge) of the already-existing k*=15 neighbour graph. No embedding step, no
coordinate vector, nothing for a decoder to be fitted against. What it delivers to the analysis
layer: a per-edge or per-node scalar directly, bypassing the Representation and Decoder layers
entirely (per RESEARCH.md's Architectural Responsibility Map). Its relationship to the
milestone's actual question: Ollivier-Ricci and Forman-Ricci compute an **intrinsic** Ricci-type
quantity — a statement about how neighbourhoods overlap or fail to overlap along an edge — not
the **extrinsic** mean-curvature vector CURV-01..CURV-03 specifically ask for, which is a
statement about how a fitted surface bends away from its own tangent plane in the ambient space.
These are different mathematical objects, not the same quantity computed two ways. RESEARCH.md's
Open Question 1 flags the claim that Ollivier-Ricci curvature converges to Riemannian Ricci
curvature in a suitable continuum limit (cited from search-result summaries of "Continuum Limits
of Ollivier's Ricci Curvature on data clouds," arXiv:2307.02378) as `[CITED]`-strength only — that
paper was not read directly in this session (no browsing tool was available to this task), so its
exact regularity and sampling-density conditions remain unverified. This verdict does not lean on
that convergence claim in either direction: the fork test result above follows entirely from the
structural fact that Ollivier-Ricci and Forman-Ricci produce no coordinate vector, which is true
regardless of whether or how tightly either quantity converges to Ricci curvature in the limit.
Any later plan that wants to use the convergence claim as evidence for something else must read
the paper directly first, per RESEARCH.md's own recommendation.

## Graph-Native Branch Cost

Recorded here because cost is a fact the reader is owed, never the reason this branch loses:

- **Three packages**, none installed in the current environment: `networkx` (not installed at
  all), `GraphRicciCurvature`, `POT`. All three, along with the other four candidates in
  `02.1-RESEARCH.md`'s Package Legitimacy Audit, returned `SUS` from the legitimacy checker
  (`unknown-downloads` primarily, `no-repository` for two unrelated candidates). Each install
  would sit behind its own blocking `checkpoint:human-verify` gate per this phase's Scope
  Constants — none of the three is pre-approved by this verdict.
- **The graph this branch would operate on**: the already-validated k*=15 neighbour graph, exactly
  150,000 edges (`codiag_k15_43cf438bc944c509.npz`'s `edge_lengths` array length). Reusing it is
  mandatory if this branch is ever pursued, per the Shortlist Rule's note — recomputing at a
  different `k` would reopen the k-sensitivity question `02-REFIT-PREREGISTRATION.md` already
  closed across `k in {5, 10, 15, 30}`.
- **The transport cost**: Ollivier-Ricci curvature requires an optimal-transport comparison of
  neighbourhood distributions across every one of those 150,000 edges. Exact optimal-transport LP
  is intractable at this scale (per RESEARCH.md's State of the Art table); the Sinkhorn-
  approximate entropic-regularized solver `GraphRicciCurvature` implements internally via `POT`
  is necessary, not optional, at n=10,000 / 150,000 edges.
- **A fixture that does not yet exist**: before any curvature number from this branch could be
  trusted, a synthetic tree-and-expander fixture would need to be built — a weighted tree (known
  negative curvature by construction) and a near-regular/expander graph (known near-zero/positive
  curvature) at matched scale, to sanity-check the solver the way `02.1-RESEARCH.md`'s Validation
  Architecture GEOM-04 row specifies before any illustrative Ollivier-Ricci output is trusted. No
  such fixture is on disk; it is design-only at this point.

None of the above is a claim that this branch is difficult. It is a claim that it is not free,
recorded so a reader can weigh it against the fact that it cannot supply CURV-01..CURV-03's
extrinsic mean-curvature vector, on requirement-compatibility grounds, at zero additional cost to
that specific argument.

## What Phase 3 Inherits

**Coordinate-producing branch (the branch this verdict selects).** Every requirement in
DEC-01..DEC-05 and CURV-01..CURV-08 is inherited, with exactly the one amendment
`.planning/REQUIREMENTS.md`'s own DEC section header already carries: "Isomap coordinates" is
read throughout as "the coordinates of the representation chosen in Phase 02.1." No requirement
text changes; only the noun phrase's referent does.

| DEC-02 | Yes — no ReLU-family activation constraint is representation-independent |
| DEC-03 | Yes — held-out reconstruction quality is representation-independent |
| DEC-04 | Yes — aggregate + per-dimension metric reporting is representation-independent |

**Graph-native branch (not selected).** Had this branch won, DEC-01..DEC-05 would all be
inapplicable — there is no coordinate output to train a decoder on, so nothing decodes and
nothing reconstructs. CURV-01 and CURV-02 (first and second fundamental form from a decoder
Jacobian/Hessian) would be inapplicable for the same reason — there is no decoder. CURV-03 would
not merely change form; the quantity it asks for (an *extrinsic* mean curvature *vector*) does
not exist on this branch at all, and would be replaced by an *intrinsic* Ricci scalar/tensor per
edge or node — a different requirement, not a re-specified one. CURV-04 (metric tensor
conditioning) has no metric tensor to condition-check. CURV-05 (non-zero decoder second
derivatives) has no decoder. CURV-06/CURV-07's synthetic-control comparison would need
re-architecting entirely around graph-native synthetic controls (the tree-and-expander fixture
named in the cost section above) rather than the flat-plane/sphere/saddle manifolds CURV-06
specifies. CURV-08 (curvature only evaluated at/near actual coordinates) has no coordinates to
bound evaluation against; its analogue would be "curvature only evaluated on the actual k*=15
graph's edges, never a resampled or reweighted graph."

## What Phase 3 Re-opens

**Coordinate-producing branch (the branch this verdict selects).** Nothing in DEC-01..DEC-05 or
CURV-01..CURV-08 is re-opened. Phase 3 re-plans against this phase's chosen representation and
working dimension (per `02.1-04-PLAN.md`'s eventual handoff), but the requirement *set* and its
individual requirement *text* stand unchanged — this is a re-specification of Phase 3's input,
exactly as `02.1-RESEARCH.md`'s Summary and this phase's ROADMAP.md entry both anticipate.

**Graph-native branch (not selected).** All thirteen DEC/CURV requirements would need to be
re-opened: DEC-01..DEC-05 dropped entirely (no decoder exists on this branch), CURV-01/CURV-02
dropped (no Jacobian/Hessian to compute), CURV-03 rewritten from an extrinsic mean-curvature
*vector* to an intrinsic Ricci *scalar/tensor* per edge or node, CURV-04/CURV-05 dropped (no
metric tensor, no decoder derivatives), CURV-06/CURV-07 rearchitected around a graph-native
synthetic control, and CURV-08 rewritten around graph edges rather than coordinate support. This
is why the fork verdict is described in this plan's objective as gating "almost everything
downstream of it" — choosing this branch would not adjust Phase 3's plan, it would require an
entirely new requirement set for what was Phase 3, and the milestone's REQUIREMENTS.md
traceability table would need updating to match.

## Falsifier Status

Restated from `02.1-PREREGISTRATION.md`'s Falsifier section: this coordinate-producing verdict
would be overturned if plan `02.1-03`'s measured evidence shows both (a) the real manifold's
`DELTA_REL` sits far from the tree anchor — indistinguishable from, or closer to, the
flat-Euclidean anchor than the Delta-Hyperbolicity Reading Rule's threshold allows — **and**
(b) the pseudo-Euclidean `(p, q)` distortion ladder never drops `DISTORTION` materially below the
`q = 0` classical-MDS baseline (already known to fail at `m = 0.412071`) at any rung up to the
ceiling of 40. Neither condition has been tested yet — this verdict is written against the
Fork Test's structural definition, before any of this phase's own diagnostic evidence exists.
**Plan `02.1-03` is the plan that tests it**: its Krein-reconstruction/(p, q)-ladder probe and its
delta-hyperbolicity probe, run over the frozen Phase 2 cache, produce exactly the two numbers this
falsifier is defined against. If both trip, this verdict must be revisited before plan `02.1-04`'s
recommendation is written, and that revisiting is a documented amendment to this document, not a
quiet edit to the recommendation.
