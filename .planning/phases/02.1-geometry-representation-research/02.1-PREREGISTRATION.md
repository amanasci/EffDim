# Phase 02.1 Geometry Representation Research — Pre-Registration

**This document is written and committed before `02.1-FORK.md`, before any candidate survey,
before any probe code, and before any evidence in this phase has been examined.** Its purpose
is to fix every decision rule this phase will later apply — the fork test, the evaluation
criterion, the distortion statistic, the working-dimension rule, the delta-hyperbolicity
reading rule, the shortlist, and the falsifier — in advance, so that no candidate's evidence can
be selected for being convenient after the fact. This mirrors the discipline
`02-REFIT-PREREGISTRATION.md` established at commit `057b084` and that Phase 2's own report
treats as what separates a principled sweep from retrying until something passes. The mechanical
proof of this document's ordering relative to `02.1-FORK.md` lives in this plan's `<verify>`
block (`git merge-base --is-ancestor`), not in this paragraph's claim.

## Scope Constants

**Nothing outside the existing venv is installed by this phase.** The venv already carries
numpy 2.5.1, scipy 1.18.0, scikit-learn 1.9.0, torch 2.13.0+cpu, joblib, and pytest 9.1.1 — all
of this phase's work runs on that set. All seven candidate packages named in `02.1-RESEARCH.md`'s
Package Legitimacy Audit (`geoopt`, `geomstats`, `GraphRicciCurvature`, `datafold`, `pydiffmap`,
`hyperlib`, `POT`) returned `SUS` from the legitimacy checker. If this phase's own evidence stage
turns out to genuinely require one of them, the phase halts at a blocking `checkpoint:human-verify`
gate and the install is ratified there, before it happens — it is never a quiet `pip install`
inside a task. Reason: the `SUS` signal is a structural gate on this project's dependency surface,
not a comment on any one package's actual legitimacy, and treating it as advisory rather than
blocking would defeat the reason the checker exists. This forecloses any task in this phase from
installing a package on the argument that the checkpoint would obviously be approved anyway.

**Compute envelope.** Laptop-scale, no GPU, `n = 10,000`. The already-computed
10,000 x 10,000 geodesic distance matrix (`dist_matrix_` inside
`isomap_43cf438bc944c509.joblib`) is reused, never recomputed, by any task in this phase.
Reason: recomputing it would silently change provenance and disconnect this phase's evidence
from the exact fit Phase 2 audited. This forecloses re-fitting Isomap at any point in this phase.

**Fixed provenance key.** `fit_key = 43cf438bc944c509` is the single provenance key every reused
Phase 2 artifact in this phase is keyed against — the joblib, the eigenspectrum `.npz`, the

this phase computes against, or reports, a value from a differently-keyed artifact.

## Fork Test

*(RESEARCH.md Entanglement item 1 — the single largest entanglement in this phase, and the
reason this task exists before any other work.)*

A candidate is **coordinate-producing** iff it yields, for each of the 10,000 points, a finite
real coordinate vector from which a twice-differentiable map into R^768 can be fitted — which is
precisely what DEC-01's C2-smooth decoder and CURV-01..CURV-03's batched Jacobian/Hessian path
consume. A candidate that produces only per-node or per-edge scalars, with no coordinate vector
to differentiate a decoder against, is **graph-native**.

Reason this is the test rather than a neighbouring one (e.g. "does it preserve distances well,"
"is it popular in the literature"): those are quality questions the evaluation criterion below
answers *within* a branch. This test answers a *type* question — whether Phase 3's decoder can
even be built on top of the candidate at all — and a candidate that scores well on distance
preservation but produces no coordinate vector still cannot feed DEC-01. The test is therefore
derived from requirement text, not from method preference or historical popularity.

Failing the test does not disqualify a candidate. It relocates it: a coordinate-producing winner
re-specifies Phase 3's input and leaves DEC-01..DEC-05 and CURV-01..CURV-08 intact (with "Isomap
coordinates" read as "the coordinates of the representation chosen in Phase 02.1," per
REQUIREMENTS.md's own DEC section amendment); a graph-native winner replaces the extrinsic
mean-curvature vector CURV-03 specifically asks for with an intrinsic Ricci quantity and
therefore re-opens that requirement set rather than merely re-specifying its input. This
forecloses treating "graph-native lost" and "graph-native was worse" as the same claim — the
fork test is not a leaderboard, it is a routing decision with a stated, asymmetric downstream
consequence recorded in `02.1-FORK.md`.

## Evaluation Criterion

*(RESEARCH.md Open Question 2, resolved explicitly here rather than left implicit in whichever
comparison table gets built first.)*

**Two arguments, not one score.** Coordinate-producing candidates are compared on a single
computable number: relative squared-geodesic-distance distortion over the fixed 200,000-pair
sample Phase 2 already cached at `r2_pair_seed = 20260731`
(`mds_eigenspectrum_43cf438bc944c509.npz`'s `geo_pairs_r2`). Graph-native candidates are **not**
scored on that axis at all, because they do not attempt to preserve distances and any number
produced for them on that axis would be a category error dressed as a comparison. They are judged
on two qualitative grounds instead: whether they answer the question CURV-01..CURV-03 poses, and
the shape of their curvature distribution.

Reason: inventing a single number that spans both branches would require deciding, implicitly,
how much distance-preservation is worth relative to a graph-native candidate's intrinsic-Ricci
answer — a tradeoff with no principled exchange rate. Registering the incommensurability now,
before any candidate has been scored, removes the option of inventing a unified score later and
picking its weights to flatter whichever branch already looks better. This forecloses any later
plan from presenting a single ranked table across both branches.

## Distortion Statistic

    DISTORTION = median( |d2_rep - d2_geo| / d2_geo )

reported together with the **signed** median relative deviation

    DISTORTION_SIGNED = median( (d2_rep - d2_geo) / d2_geo )

both computed over the 200,000-pair sample at `r2_pair_seed = 20260731`, on **squared**
distances. Reason for squared distances: squared distance is what classical MDS and its
pseudo-Euclidean generalisation reconstruct exactly (the double-centred Gram matrix is built from
squared distances), so measuring distortion in that unit matches what the representation is
actually fit to minimise. Reason for the signed companion statistic: reporting only the absolute
value would hide systematic over- or under-estimation inside the median, and systematic bias is
exactly the kind of artifact a correction method could produce while looking good on the absolute
number alone. This forecloses reporting `DISTORTION` without `DISTORTION_SIGNED` alongside it in
any later plan.

## Working-Dimension Rule

*(GEOM-05.)* The working dimension is re-derived **per candidate**, from that candidate's own
distortion-versus-dimension curve, using the identical kneedle criterion Phase 2 recorded
verbatim in `gate_verdict_43cf438bc944c509.json`'s `elbow_criterion` field:

> "Maximum-curvature (kneedle) elbow on the Tenenbaum residual-variance curve (1 - R^2 between
> geodesic and embedded pairwise distances): both axes are normalized to [0, 1] by their own
> range, and the elbow is the point of greatest perpendicular distance from the chord connecting
> the curve's first and last normalized point. Swept over d = 1..40 (K_EFF, bounded by
> D_SWEEP_MAX=40 and N_POSITIVE=4971); ties broken to the lower d (ELBOW_TIE_BREAK='lower')."

For a pseudo-Euclidean candidate the working dimension is a **pair (p, q)** — positive and
negative directions — reported as a pair and never collapsed into a single integer. Reason: a
single collapsed integer would discard exactly the sign distinction the representation exists to
make, turning a pseudo-Euclidean result back into a de facto classical-MDS one.

`D_FROZEN = 5` is neither inherited nor declared wrong. It is re-derived under this rule for every
candidate this phase evaluates, and the two numbers — the re-derived value and 5 — are placed side
by side. Reason this is the rule rather than either extreme (silently inheriting 5, or asserting
it was simply wrong): `02-FINDINGS.md` §6.4 shows the elbow of 5 is the outlier against three
independent estimates (local PCA ~25, TwoNN ~19.5, median of 8 geometric estimators = 18) and is
consistent with the elbow having measured the flat embedding's failure rather than the geometry —
but RESEARCH.md is equally explicit that a curved target space can represent the same structure in
*fewer* dimensions than a flat one needs, so the 18-25 local intrinsic-dimension estimates do not
on their own refute 5 either. Re-deriving under a fixed, pre-registered rule is the only move that
resolves this without begging the question in either direction. This forecloses any later plan
from stating a working dimension without running this exact rule against that candidate's own
curve.

**The (p, q) ladder**, fixed now for the pseudo-Euclidean candidate's dimension sweep:

    P_LADDER = (1, 2, 3, 5, 8, 13, 18, 25, 40)
    Q_LADDER = (0, 1, 2, 3, 5, 8, 13, 25, 40)

Ceiling 40 on both, matching Phase 2's `d_sweep_max = 40` and the width of the cached
`eigvecs_top` block in `mds_eigenspectrum_43cf438bc944c509.npz`, so the ladder costs one
bottom-40 eigenvector solve and nothing more. `q = 0` is retained deliberately: it *is* the
classical-MDS baseline, and having it in the same table as every `q > 0` rung is what lets a
reader see directly what retaining the negative directions buys over the representation that
already failed the gate.

## Delta-Hyperbolicity Reading Rule

*(RESEARCH.md Pitfall 3, Assumption A7.)*

    DELTA_REL = 2 * delta / diam_sample

the standard Gromov relative four-point delta, where `delta` is taken at the maximum and the 95th
percentile over sampled quadruples and `diam_sample` is the maximum pairwise geodesic distance in
the same sample.

Constants, fixed now:

    DELTA_QUADRUPLES = 200_000
    DELTA_SEED = 20260801

Reading rule, fixed before the number is computed rather than thresholded in the abstract after
seeing it: the real manifold's `DELTA_REL` is reported next to two calibration anchors computed
by the *identical* estimator at matched `n` — a synthetic weighted tree metric, where the
four-point condition gives `delta` identically zero, and a synthetic sample from a flat
20-dimensional Euclidean space. If the real value sits at or below the tree anchor plus one tenth
of the gap to the Euclidean anchor, a single constant negative curvature is a defensible model and
a pure hyperbolic target is supported. Otherwise it is not, and the mixed-curvature/product or
pseudo-Euclidean branch is preferred. Reason: calibrating against two anchors computed by the same
estimator, rather than asserting a bare threshold, controls for the estimator's own bias at this
sample size and quadruple count — the same move Phase 2 made when it refused to attach pass/fail
bounds to `GEO_AMBIENT_RATIO` after the k=15 value was already known. This forecloses reading
`DELTA_REL` against any threshold invented after the number is computed.

## Shortlist Rule

At most three candidates are carried into this phase's evidence stage. Named now, before any
evidence is examined, on the fork test plus `02.1-RESEARCH.md`'s Standard Stack implementation
maturity — never on how well a candidate scores, since no candidate has scored anything yet:

1. **Pseudo-Euclidean / Krein-space retention** (coordinate-producing). Hand-rolled directly from
   the already-cached spectrum (`mds_eigenspectrum_43cf438bc944c509.npz`'s top-40 block plus one
   new bottom-40 eigensolve) — zero new dependencies, the most mature entry on this list by
   dependency count alone, and the one candidate whose evidence this phase can obtain without
   installing anything.
2. **Hyperbolic / mixed-curvature** (coordinate-producing; Poincare/Lorentz or a product manifold,
   the `geoopt` package per Standard Stack Core). PyTorch-native, matching the project's existing
   torch dependency for Phase 3. Evaluated first via the Delta-Hyperbolicity Reading Rule above,
   which requires no embedding fit and no install, before any embedding-fitting cost is spent on
   `geoopt` itself.
3. **Ollivier-Ricci graph-native curvature** (graph-native; `GraphRicciCurvature` + `POT` +
   `networkx` per Standard Stack Core — "the only actively-maintained Python package found for
   this specific computation" per RESEARCH.md). If this branch is ever pursued, reusing the
   already-validated k*=15 graph and its 150,000 edges is **mandatory** — recomputing at a
   different `k` would re-open the k-sensitivity question Phase 2 closed across
   `k in {5, 10, 15, 30}` (`02-REFIT-PREREGISTRATION.md` Rule A).

Diffusion maps and Forman-Ricci are surveyed in `02.1-02-PLAN.md`'s candidate table (GEOM-02
requires all six families covered) but are not carried into this phase's own evidence-gathering
tasks: diffusion maps' only actively-maintained package (`datafold`) is Supporting-tier and
strictly heavier than what the shortlist above already needs, and Forman-Ricci is a lower-cost
variant of the same package already covering the graph-native slot.

## Falsifier

*(A verdict without a stated falsifier is a preference, not a decision.)*

**What would overturn a coordinate-producing verdict:** if plan `02.1-03`'s measured evidence
shows both (a) the real manifold's `DELTA_REL` sits far from the tree anchor — indistinguishable
from, or closer to, the flat-Euclidean anchor than the reading rule's threshold allows, so no
single- or mixed-curvature hyperbolic model is supported — **and** (b) the pseudo-Euclidean
`(p, q)` distortion ladder never drops the `DISTORTION` statistic materially below what `q = 0`
(the classical-MDS baseline, already known to fail at `m = 0.412071`) achieves at any rung up to
the ceiling of 40, then no coordinate-producing candidate on the shortlist can represent this
geometry any better than classical MDS already failed to. That finding would mean the
coordinate-producing branch's central premise — that a curved-but-coordinatizable target exists
for this manifold — does not hold, and the verdict would need revisiting toward the graph-native
branch despite its higher cost.

**What would overturn a graph-native verdict** (stated for symmetry, so both branches carry an
equally concrete falsifier): if a coordinate-producing candidate's `DISTORTION` drops materially
below the residual classical-MDS failure at a tractable working dimension (under the
Working-Dimension Rule above), that would demonstrate the geometry *is* well-represented by
continuous coordinates, and a graph-native verdict — which discards the decoder architecture
entirely and re-opens CURV-01..CURV-03 at strictly higher cost (three SUS-flagged package
installs, a synthetic fixture, a Sinkhorn-approximate optimal-transport run over 150,000 edges) —
would not be justified over the cheaper, requirement-preserving alternative.

## Prohibited Moves

- **Revising any rule in this document after `02.1-FORK.md`, the survey, or any probe output
  exists.** Reason: this is the entire discipline this document exists to enforce; a rule edited
  after the evidence exists is indistinguishable from a rule that was always there unless
  ordering is proved mechanically, which is exactly what this plan's `<verify>` step does. If a
  rule genuinely must change later, that is a dated amendment section appended here with a stated
  reason and a recorded re-run — never a quiet edit.
- **Scoring graph-native candidates on the distance-distortion axis.** Reason: they do not attempt
  to preserve distances; a number produced for them on that axis is a category error dressed as a
  comparison, per the Evaluation Criterion above.
- **Treating a clean UMAP or t-SNE picture as evidence the flat-target problem is resolved.**
  Reason: both are probability-based or PSD-by-construction solvers that structurally cannot
  expose the negative-eigenvalue statistic this milestone measures — a clean 2D picture from
  either says nothing about whether the underlying geodesic metric is Euclidean-embeddable, and
  citing one as reassurance would smuggle the flat-target assumption back in through a different
  door.
- **Adopting a distance-matrix correction (Cailliez, Lingoes, eigenvalue clipping/flipping) as the
  project's representation without an explicit argument that it is principled here rather than
  cosmetic.** Reason: RESEARCH.md's Pattern 1 and Pitfall 2 are explicit that these methods force
  a passing gate on *any* input, curved or not, by construction — they are diagnostic-blind, and
  adopting one without that argument on the record would delete the very signal this milestone
  exists to measure.
- **Declaring `D_FROZEN = 5` wrong rather than re-deriving the dimension under the Working-
  Dimension Rule.** Reason: three clustering estimates (18-25) do not, on RESEARCH.md's own
  reasoning about curved target spaces needing fewer dimensions than flat ones, automatically
  refute 5 — only the re-derivation under a fixed rule settles it without begging the question.
- **Rebuilding the neighbour graph at any k other than 15.** Reason: k*=15 is the already-
  validated, plateau-selected fit of record; `02-REFIT-PREREGISTRATION.md` already tested
  `k in {5, 10, 30}` against it and found FAIL at every k with `m(k)` flat-to-slightly-increasing,
  closing the k-sensitivity question. Reopening it here, mid-representation-choice, would
  reintroduce a variable Phase 2 already controlled for.
