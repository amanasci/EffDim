## GEOM-01 — Flat-Target Class Membership

**What the flat-target assumption is, precisely:** a manifold-learning method's objective or
solver seeks an embedding into a Euclidean space and treats the input dissimilarities (distances,
neighbourhood weights, or probabilities) as if they were exactly realisable in that flat target —
as if the input distance matrix were Euclidean-embeddable at some finite dimension. Isomap and
classical MDS make this assumption explicitly, via the double-centred Gram matrix they
eigendecompose. Phase 2 measured that assumption failing on this data: 5,029 of 10,000 eigenvalues
of that Gram matrix are strictly negative, carrying `m = 0.412071` — 41% — of total absolute
eigenvalue mass, with `r = 0.052419` passing its own bound (no single dominant outlier; a long,
diffuse negative tail instead) and every negative eigenvalue's magnitude sitting 10–11 orders of
magnitude above the float64 noise floor — a measured, reproduced-four-ways fact, not exploratory
uncertainty.

**The finding this section exists to establish:** the flat-target assumption is shared far more
widely across manifold-learning methods than the diagnostic that exposed it. LLE, Hessian LLE,
LTSA, Laplacian eigenmaps, MVU, t-SNE and UMAP all target a flat Euclidean output space — the same
assumption Isomap makes — but none of their solvers can produce a computable negative-eigenvalue
statistic, for one of two distinct mechanisms. Their silence about this data's non-Euclidean
geometry is therefore structural, not evidential.

### Class-membership table

| Method | Defining objective / solver | Target space flat Euclidean? | Produces a computable Euclidean-validity diagnostic? | Why not, where it cannot |
|---|---|---|---|---|
| Isomap | Eigendecomposes the double-centred **graph geodesic** distance matrix `B = -1/2 J D_geo^2 J` via classical MDS on top of shortest-path distances | Yes | **Yes** — `B`'s eigenvalues are not forced positive by double-centring; they are negative exactly when `D_geo` is not itself Euclidean-embeddable | — (this is the method whose failure this milestone measured) |
| Classical MDS | Eigendecomposes the double-centred **input** distance matrix `B = -1/2 J D^2 J` directly | Yes | **Yes** — identical mechanism to Isomap, one layer up (no geodesic step) | — |
| LLE (Locally Linear Embedding) | Minimises reconstruction error of each point from a locally-linear combination of neighbours, then finds the low-dimensional embedding whose local reconstruction weights match; the embedding step solves an eigenproblem on a **sparse, PSD-by-construction** matrix `(I-W)^T(I-W)` | Yes | No | `(I-W)^T(I-W)` is a Gram-type product of a real matrix with its own transpose — positive-semidefinite by construction, for any input `W`, regardless of whether the underlying geometry is flat |
| Hessian LLE | Same local-linear-reconstruction family as LLE, but estimates the local Hessian of the embedding via each neighbourhood's local tangent coordinates, then solves an eigenproblem on the resulting quadratic form's null space | Yes | No | The local Hessian estimator's quadratic form is a sum of squared local curvature estimates — positive-semidefinite by construction, same mechanism family as LLE, applied locally rather than globally |
| LTSA (Local Tangent Space Alignment) | Fits a local PCA / tangent space at each neighbourhood, then aligns those local coordinate systems into one global embedding by minimising a global alignment error, itself a PSD quadratic form | Yes | No | Local PCA covariance matrices are Gram matrices of real data — positive-semidefinite by construction; the global alignment matrix built from them inherits the same property |
| Laplacian eigenmaps | Solves a generalized eigenproblem on the graph Laplacian `L = D - W` (or its normalized form), retaining the eigenvectors of smallest eigenvalue | Yes | No | The graph Laplacian is **positive-semidefinite by construction** for any graph with non-negative edge weights (`x^T L x = sum_edges w_ij (x_i-x_j)^2 >= 0`); no input geometry can make an eigenvalue negative |
| MVU (Maximum Variance Unfolding) | Solves a semidefinite program (SDP) that maximises the trace of a kernel/Gram matrix subject to local-distance-preservation constraints **and an explicit PSD constraint on the Gram matrix itself** | Yes | No | MVU's SDP constrains the Gram matrix to the positive-semidefinite cone as a hard optimisation constraint, not a soft regularizer — a negative eigenvalue is not merely unobserved in an MVU solution, it is **infeasible under the solver's own constraint set** [CITED — the semidefinite-program formulation is carried from Weinberger & Saul's original construction via RESEARCH.md's WebSearch-strength sourcing; not independently re-verified against the primary paper in this session, no browsing tool available] |
| t-SNE | Minimises KL divergence between a Gaussian-in-high-dimension neighbourhood probability distribution and a Student-t-in-low-dimension one | Yes | No | Never forms a Gram, Laplacian, or covariance matrix at all — it optimises a divergence between two probability distributions over neighbourhoods via gradient descent; there is no matrix whose eigenvalues could be inspected for a sign |
| UMAP | Minimises a fuzzy-set cross-entropy between a high-dimensional weighted neighbourhood graph and a low-dimensional one, via stochastic gradient descent | Yes | No | Same mechanism family as t-SNE — a probability/fuzzy-membership divergence optimised directly, no Gram-type object is ever constructed |

### The two mechanisms, separated

Two distinct routes to the same consequence (no negative-eigenvalue statistic exists to
inspect), and conflating them would understate how structural the blindness is:

1. **PSD-constrained by construction.** MVU's SDP constrains the Gram matrix to the
   **positive-semidefinite** cone directly; Laplacian eigenmaps' graph Laplacian is
   positive-semidefinite by construction for any non-negative edge weighting; LLE, Hessian LLE
   and LTSA's local Gram/covariance eigenproblems are positive-semidefinite by construction because
   they are built as products of a real matrix with its own transpose (or as local PCA covariance
   matrices). In every one of these five methods, the object the solver eigendecomposes cannot
   carry a negative eigenvalue **regardless of what the input geometry actually is** — flatness is
   built into the solver's own algebra, not discovered by it.
2. **Never forms a Gram matrix at all.** t-SNE and UMAP optimise a divergence between probability
   distributions (or fuzzy-set memberships) over neighbourhoods, via gradient descent on that
   divergence directly. There is no eigendecomposed matrix at any point in either pipeline — the
   question "is this matrix's spectrum partly negative" cannot even be posed against their solvers.

Isomap and classical MDS are the only two methods in this table whose solver forms a
double-centred Gram matrix **without** constraining it to be positive-semidefinite as part of the
optimisation — `B = -1/2 J D^2 J` is PSD if and only if `D` is exactly a Euclidean distance matrix,
which is precisely the property under test. That is the structural reason only these two methods
can expose the failure: they are the only ones whose solver's own algebra does not force the
answer before the input geometry is consulted.

### A second, within-family instance of the same blindness

Even within the one method family that *can* show the failure, the attribute a caller would reach
for by default cannot. `Isomap.kernel_pca_.eigenvalues_` — sklearn's own cached spectrum from its
internal `KernelPCA` step — is truncated to `n_components` (18, in this fit) and sorted by
eigenvalue descending, so it structurally cannot contain a negative eigenvalue either: Phase 2's
audit computed the **full** 10,000-value spectrum by hand from `dist_matrix_` for exactly this
reason (`02-FINDINGS.md` §3.2), because reporting the truncated attribute would have begged the
question. A reader who inspects only `kernel_pca_.eigenvalues_` on an Isomap fit — even this exact
fit — would see nothing wrong, for the same class of reason UMAP and t-SNE see nothing wrong: the
object being inspected has already discarded the part of the spectrum that would show it.

### Reading

Anchored to the measured numbers: of the full 10,000-eigenvalue spectrum, **5,029 are strictly
negative**, carrying `m = 0.412071` of total absolute eigenvalue mass — comparable in magnitude to
the positive part, not a small correction to it — while `r = 0.052419` passes its own bound,
meaning this is not one dominant outlier but a long, diffuse negative tail. Every negative
eigenvalue's magnitude sits roughly ten orders of magnitude above the float64 noise floor
(`7.174e-09` at k=15), so the negative mass is real structure, not rounding. This result was
reproduced across `k in {5, 10, 15, 30}`, across the paired HSC survey column, and across a ~90%
disjoint resample under a new seed with identical positive/negative eigenvalue counts. Only
classical MDS and Isomap — and only when the full spectrum is computed by hand rather than read
from a truncated attribute — can expose that this failure exists at all.

### Consequence

A clean-looking UMAP or t-SNE plot of this data — or a clean-looking `kernel_pca_.eigenvalues_`
read off this exact Isomap fit — would not be evidence that the flat-target problem is resolved.
It would mean the same failure had become **invisible rather than absent**: seven of the nine
methods in this table structurally cannot report a negative-eigenvalue statistic, whether or not
one is present in the underlying geometry, because their solvers are either **positive-semidefinite
by construction** or never form the kind of matrix whose sign could be inspected in the first
place. "Does not show negative eigenvalues" must be read as "does not measure the problem," never
as "does not have the problem." The honest test of any candidate representation, GEOM-02 below
included, is therefore not whether its output looks clean, but whether it carries a validity
diagnostic of its own that could have failed and did not — silence from a method with no such
diagnostic is not reassurance.

## GEOM-02 — Non-Flat-Target Candidates

**Organising fact, taken from the ratified fork rather than re-argued here:** the six candidates
divide along whether they produce, for each of the 10,000 points, a coordinate vector a decoder
can be differentiated against. `02.1-FORK.md` resolves this against the pre-registered Fork Test
and selects the coordinate-producing branch. This section describes all six candidates fully —
including the two the fork verdict set aside — because GEOM-02's requirement text asks for every
non-flat-target family with its own assumptions, cost, and Phase 3 demand, and because a future
reader who wants to reopen the fork needs the losing branch's numbers to do it with. It does not
re-decide the fork; see `02.1-FORK.md` for the verdict itself.

Every family below carries the same five labelled parts, in the same order, so the six are
genuinely comparable: **Assumptions**, **Cost at n = 10,000**, **Implementation maturity**,
**Fork side**, and **What it would demand of Phase 3**.

### Hyperbolic (Poincare ball / Lorentz hyperboloid)

**Assumptions.** A single constant negative curvature everywhere in the manifold. RESEARCH.md's
Pitfall 3 flags this as a strong and likely-wrong assumption for heterogeneous astronomical
morphology data — different galaxy morphologies and local densities plausibly carry different
local curvature, not one global value. The specific inference behind that flag is Assumption A7
in RESEARCH.md's Assumptions Log: astronomical embedding curvature is *plausibly* heterogeneous,
reasoned from the "diffuse tail, not one pathological edge" shape of Phase 2's own negative-mass
finding applied one level up, to curvature homogeneity — not a direct measurement. That is exactly
what plan `02.1-03`'s delta-hyperbolicity probe exists to test: `DELTA_REL` measured against a
tree anchor (delta identically zero, one constant negative curvature by construction) and a flat
20-dimensional Euclidean anchor, per the pre-registered Delta-Hyperbolicity Reading Rule.

**Cost at n = 10,000.** Fitting a Poincare-ball or Lorentz-hyperboloid embedding requires
Riemannian stochastic gradient descent over all 10,000 points from the existing distance matrix —
an iterative optimisation, not a one-shot eigensolve; its wall-clock class on a laptop CPU with no
GPU is the closest analogue to a full Isomap-style fit (Phase 2's Isomap fits measured
78.5–104.5 s each) repeated over some number of SGD epochs, plausibly several times that single-fit
cost depending on convergence, not a fixed, precomputable number. No dense array beyond what is
already on disk (the 800 MB 10,000×10,000 geodesic matrix) is newly materialised. The
Delta-Hyperbolicity Reading Rule's probe is cheap by contrast — `DELTA_QUADRUPLES = 200,000`
sampled quadruples read directly off the existing `dist_matrix_`, no fit required — and is
evaluated **before** any embedding-fitting cost is spent, per the Shortlist Rule.

**Implementation maturity.** `geoopt` 0.5.1, latest release 2025-06-19, SUS (`unknown-downloads`,
`no-repository`). PyTorch-native, matching the project's existing torch dependency for Phase 3.
Every SUS verdict recorded in this document is driven by an `unknown-downloads` signal gap in this
environment — the download-stats signal source is unavailable here, not a substantive finding
against any package — and the blocking `checkpoint:human-verify` gate still applies regardless,
because the protocol keys off the automated signal, not off anyone's confidence in the manual
corroboration RESEARCH.md's Package Legitimacy Audit already performed (`github.com/geoopt/geoopt`,
a NeurIPS-workshop paper). Per RESEARCH.md's `## Don't Hand-Roll`: the Poincare exponential and
logarithmic maps and Riemannian SGD must not be hand-rolled — they are numerically delicate near
the ball boundary (norm approaching 1) and a well-documented source of silent NaN/instability bugs
in from-scratch implementations. `geoopt` supplies this machinery; nothing here should be built
from scratch. The one exception RESEARCH.md names anywhere in its Don't-Hand-Roll table is sampled
Gromov delta-hyperbolicity itself — a plain distance-matrix reduction with no such delicate
machinery, but with a documented wrong way (naive `C(10000,4)` brute force instead of sampled
quadruples).

**Fork side.** **Coordinate-producing**, per `02.1-FORK.md`'s Fork Test table: a Poincare-ball or
Lorentz-hyperboloid point per input point is a finite real vector, differentiably related to a
Euclidean chart.

**What it would demand of Phase 3.** Unchanged: DEC-02, DEC-03, DEC-04, DEC-05, CURV-01, CURV-02,
CURV-03, CURV-04, CURV-05, CURV-06, CURV-07 — all representation-independent per `02.1-FORK.md`'s
`## What Phase 3 Inherits` table. Referent-amended only ("Isomap coordinates" -> this phase's
chosen coordinates): DEC-01, CURV-08. Needing rewriting: none.

### Mixed-curvature product manifold

**Assumptions.** Curvature is heterogeneous but decomposes into a small number of constant-
curvature factors (hyperbolic × spherical × Euclidean, in some signature) whose factor count and
per-factor curvature and dimension must be chosen. This is a strictly weaker, more flexible
assumption than pure hyperbolic's single global curvature — RESEARCH.md's Primary recommendation
prefers this family over pure hyperbolic for exactly the heterogeneity reason Pitfall 3 raises —
but it substitutes a model-selection problem (how many factors, which signature) for hyperbolic's
single-parameter assumption, and that choice is not itself derived from data by this survey.

**Cost at n = 10,000.** Same order of cost as pure hyperbolic — Riemannian SGD over the product
manifold's per-factor exponential/logarithmic maps, fitted from the existing distance matrix, no
new dense array beyond what is already on disk — plus the added, one-time cost of the factor-count
and signature model-selection step itself, which this survey does not attempt to price precisely
because it depends on how many candidate signatures are compared.

**Implementation maturity.** `geoopt` 0.5.1 (Core, same package as pure hyperbolic — it implements
product-of-manifolds directly) or `geomstats` 2.8.0, latest release 2024-09-09, SUS
(`unknown-downloads`, `no-repository`), if broader product-manifold statistics (Frechet mean,
geodesic regression) beyond what `geoopt` covers directly are needed. `geomstats` is Supporting-tier
per RESEARCH.md's Standard Stack: broader and more general, heavier dependency footprint, INRIA-
affiliated and JMLR-published per manual corroboration [CITED — not independently re-verified
against the live repo in this session]. Same `unknown-downloads`-driven SUS framing and blocking-gate
consequence as every other candidate in this document.

**Fork side.** **Coordinate-producing**, per `02.1-FORK.md`: a tuple of per-factor coordinates,
concatenable into one real vector per point, same reasoning as pure hyperbolic extended across
factors.

**What it would demand of Phase 3.** Identical bucketing to pure hyperbolic: unchanged — DEC-02,
DEC-03, DEC-04, DEC-05, CURV-01, CURV-02, CURV-03, CURV-04, CURV-05, CURV-06, CURV-07; referent-
amended only — DEC-01, CURV-08; needing rewriting — none.

### Pseudo-Euclidean / Krein-space retention

**Assumptions.** That the indefinite bilinear form itself is the right object to represent this
geometry in, and that the negative eigendirections of the already-computed double-centred Gram
matrix carry signal about genuine non-Euclidean structure rather than error to be discarded. This
is the representation that takes Phase 2's own finding most literally: 41% of absolute eigenvalue
mass is negative, and this family's assumption is that this is exactly the right amount of
negative mass to keep, not a defect to correct away. RESEARCH.md's Pattern 1 and the Prohibited
Moves section of `02.1-PREREGISTRATION.md` are explicit that treating this negative mass as
something to force away via Cailliez/Lingoes/eigenvalue-clipping — rather than retaining it — is
diagnostic-blind by construction and self-defeating for a project whose goal is to *measure*
curvature.

**Cost at n = 10,000.** The cheapest candidate in this document by a wide margin, because the
expensive part is already paid: the full eigenspectrum and the 10,000×10,000 geodesic distance
matrix are already on disk (`mds_eigenspectrum_43cf438bc944c509.npz`'s top-40 block). A
pseudo-Euclidean/Krein treatment costs **one additional bottom-40 eigensolve** — reusing the exact
split-eigensolve strategy Phase 2 already used for the top block (`scipy.linalg.eigh(subset_by_index=...)`,
avoiding a full 10,000×10,000 eigenvector materialisation) — rather than a new fit. The `(p, q)`
ladder itself, `P_LADDER = (1, 2, 3, 5, 8, 13, 18, 25, 40)` and `Q_LADDER = (0, 1, 2, 3, 5, 8, 13,
25, 40)` per `02.1-PREREGISTRATION.md`'s Working-Dimension Rule, costs nothing further beyond that
one eigensolve — every rung reads a slice of the same cached top/bottom eigenvector blocks.

**Implementation maturity.** Zero new dependencies. Hand-rolled directly from
`scipy.linalg.eigh` (1.18.0, already in venv) — the most mature entry in this survey by dependency
count alone, and the one candidate whose evidence this phase can obtain without installing
anything or crossing a `checkpoint:human-verify` gate. The more principled, actively-researched
alternative — Neuc-MDS (bilinear-form optimisation that chooses which eigenvalues to keep to
minimise stress, rather than simply keeping the top-`p`/top-`q` of each sign), NeurIPS 2024,
arXiv:2411.10889 — has **no maintained Python package** found in RESEARCH.md's research session;
treat as research-code-or-paper-only. The simpler top-`k`-per-sign version this survey costs above
is the lower-risk fallback RESEARCH.md's Standard Stack Alternatives table names, not a compromise
forced by missing tooling for the preferred method.

**Fork side.** **Coordinate-producing**, per `02.1-FORK.md`: a `(p, q)`-signature real coordinate
vector per point in R^(p+q); the indefinite bilinear form lives in how distances are computed
*from* the coordinates, not in the coordinates' own type, so the fork test's coordinate-vector
requirement is satisfied.

**What it would demand of Phase 3.** Same bucketing shape as the other coordinate-producing
families — unchanged: DEC-02, DEC-03, DEC-04, DEC-05, CURV-01, CURV-02, CURV-03, CURV-04, CURV-05,
CURV-06, CURV-07; referent-amended: DEC-01, CURV-08; needing rewriting: none — with one added
wrinkle GEOM-05 governs directly: the working dimension is a **pair** `(p, q)`, never collapsed
into a single integer, per the Working-Dimension Rule's explicit prohibition on discarding the
sign distinction the representation exists to make.

### Diffusion maps

**Assumptions.** What the kernel bandwidth commits you to about the meaning of "diffusion
distance" — a diffusion-map coordinate is only as meaningful as the bandwidth choice that defines
the underlying random walk on the data, and getting that bandwidth wrong silently changes what the
resulting coordinates measure without any error being raised. This is a different failure mode
from the other candidates: it does not fail loudly (no infeasible solve, no divergent SGD), it
fails by quietly answering a different question than intended.

**Cost at n = 10,000.** A kernel matrix build (dense, 10,000×10,000, same order of magnitude as
the 800 MB geodesic matrix already on disk) followed by a leading-eigenvector solve on the
resulting diffusion operator — structurally the same cost class as one of Phase 2's ~100 s dense
eigensolves, plus the kernel-construction and symmetric-conjugate stabilisation overhead on top.
No iterative optimisation of the hyperbolic/product-manifold kind is required — this is a one-shot
eigensolve, cheaper in kind than Riemannian SGD, more expensive than the pseudo-Euclidean/Krein
candidate above (which pays no new kernel-construction cost at all).

**Implementation maturity.** `datafold` 2.0.2, latest release 2026-03-13 — the most recently
released of every candidate package in this document — SUS (`unknown-downloads`). `pydiffmap`
0.2.0.1, latest release **2019-02-04**, also SUS (`unknown-downloads`); RESEARCH.md's State of the
Art table records it as deprecated/outdated (no release in seven years) and explicitly prefers
`datafold` wherever the diffusion-maps branch is pursued at all — recorded here per this document's
own requirement to carry that preference forward into the family it concerns. Per RESEARCH.md's
`## Don't Hand-Roll`: diffusion-map kernel bandwidth selection and symmetric-conjugate
eigendecomposition stabilisation must not be built from a naive Gaussian kernel plus row-normalize
plus `eigh` — getting the bandwidth wrong silently changes what "diffusion distance" means (the
same point raised under Assumptions above), and the symmetric-conjugate trick for numerical
stability is non-obvious and easy to omit if hand-rolled. `datafold` supplies both correctly.

**Fork side.** **Coordinate-producing**, per `02.1-FORK.md`: a real coordinate vector per point
from the leading eigenfunctions of the diffusion operator — structurally the same output type as
Isomap/classical MDS, just a different kernel.

**What it would demand of Phase 3.** Same bucketing as the other three coordinate-producing
families: unchanged — DEC-02, DEC-03, DEC-04, DEC-05, CURV-01, CURV-02, CURV-03, CURV-04, CURV-05,
CURV-06, CURV-07; referent-amended — DEC-01, CURV-08; needing rewriting — none. Not carried into
this phase's own evidence-gathering tasks per `02.1-PREREGISTRATION.md`'s Shortlist Rule — its only
actively-maintained package is Supporting-tier and strictly heavier than what the shortlist already
needs — but it remains a fully coordinate-producing, requirement-compatible candidate on paper.

### Ollivier-Ricci curvature

**Assumptions.** What the graph and its edge weights are assumed to represent — that the already-
validated k*=15 neighbour graph's edge structure and weighting convention (150,000 edges) is a
faithful enough discretisation of the underlying manifold for a per-edge optimal-transport
comparison of neighbourhood distributions to mean something geometric. Specifically for
Ollivier-Ricci: the continuum-limit conditions under which it is argued to converge to genuine
Riemannian Ricci curvature. RESEARCH.md's Open Question 1 flags this convergence claim as
**[CITED]**-strength only (arXiv:2307.02378, WebSearch-summary-only sourcing, not read directly in
either RESEARCH.md's or `02.1-FORK.md`'s sessions) and specifically uncertain for a ~20–25
dimensional manifold sampled at n = 10,000 — roughly 400–500 points per intrinsic dimension on
average, far sparser in effective per-dimension terms than the low-dimensional graph-curvature
demonstrations the convergence literature usually uses. `02.1-FORK.md` is explicit that its fork
verdict does **not** lean on this convergence claim in either direction — the fork test result
follows entirely from the structural fact that Ollivier-Ricci produces no coordinate vector,
independent of how tightly the curvature notion converges to Ricci curvature in the limit — and
this survey inherits that same posture: the convergence claim is recorded here as an assumption
this family carries, not as evidence for or against choosing it.

**Cost at n = 10,000.** Operates directly on the already-existing, already-validated k*=15
neighbour graph (mandatory reuse per `02.1-PREREGISTRATION.md`'s Shortlist Rule and
`02.1-FORK.md`'s Graph-Native Branch Cost section — recomputing at a different `k` would reopen
the k-sensitivity question `02-REFIT-PREREGISTRATION.md` already closed across `k in {5, 10, 15,
30}`), exactly **150,000 edges**. Ollivier-Ricci curvature requires an optimal-transport
comparison of neighbourhood distributions across every one of those 150,000 edges. Exact
optimal-transport is a linear program with `d_x * d_y` variables per edge — intractable at this
scale per RESEARCH.md's State of the Art table — so the Sinkhorn-regularised, entropic-approximate
solver `GraphRicciCurvature` implements internally via `POT` is **necessary, not optional**, at
n = 10,000 / 150,000 edges. No embedding fit is paid at all — this branch bypasses the
Representation and Decoder layers entirely per RESEARCH.md's Architectural Responsibility Map —
but a synthetic tree-and-expander sanity fixture does not yet exist and would need to be built
before any curvature number from this branch could be trusted (a weighted tree, known negative
curvature by construction; a near-regular/expander graph, known near-zero/positive curvature, at
matched scale), per RESEARCH.md's own Validation Architecture GEOM-04 row.

**Implementation maturity.** `GraphRicciCurvature` 0.5.3.2, latest release 2024-06-26, SUS
(`unknown-downloads` only — its `no-repository` signal resolved cleanly on manual WebFetch:
`github.com/saibalmars/GraphRicciCurvature`, 290 stars, 350 commits, Apache 2.0, fetched directly).
`POT` (Python Optimal Transport) 0.9.7.post1, latest release 2026-07-29, SUS — flagged `too-new` by
the legitimacy checker, which is a **false positive**: `too-new` reads the latest-*release* date,
not package age, and `POT` has been a mature, actively-used library in the Python scientific stack
since roughly 2016, used internally by `GraphRicciCurvature`'s own Sinkhorn path. `networkx` 3.6.1
is **not installed at all** in the checked environment — the graph container `GraphRicciCurvature`
requires as its input type. Three packages, all three currently absent or SUS-flagged, each behind
its own blocking `checkpoint:human-verify` gate before any install, per `02.1-PREREGISTRATION.md`'s
Scope Constants — none pre-approved by the fork verdict.

**Fork side.** **Graph-native**, per `02.1-FORK.md`'s Fork Test table: a scalar curvature value
per edge (optionally aggregated per node) of the existing graph — no coordinate vector of any kind.

**What it would demand of Phase 3.** Needing rewriting, all of it: DEC-01 through DEC-05 dropped
entirely (no coordinate output exists to train a decoder on, so nothing decodes and nothing
reconstructs). CURV-01 and CURV-02 dropped (no decoder Jacobian or Hessian to compute). **CURV-03
does not merely need amending: there is no decoder to differentiate, and Ollivier-Ricci curvature
is an intrinsic scalar/tensor quantity — a statement about how neighbourhoods overlap or fail to
overlap across an edge — which is a different mathematical object from the extrinsic mean-
curvature *vector* CURV-03 specifically asks for, a statement about how a fitted surface bends
away from its own tangent plane in the ambient space.** CURV-04 dropped (no metric tensor to
condition-check). CURV-05 dropped (no decoder second derivatives). CURV-06/CURV-07 would need
rearchitecting entirely around the graph-native tree-and-expander synthetic fixture named above,
rather than the flat-plane/sphere/saddle manifolds CURV-06 specifies. CURV-08 rewritten around
graph edges: "curvature only evaluated on the actual k*=15 graph's edges, never a resampled or
reweighted graph," per `02.1-FORK.md`'s own analogue.

### Forman-Ricci curvature

**Assumptions.** Same graph-representational assumption as Ollivier-Ricci — that the k*=15 graph's
edges and weights faithfully discretise the underlying manifold — but Forman-Ricci is a purely
combinatorial formula over each edge's local graph structure (degrees and shared-triangle counts
of its endpoints), not an optimal-transport comparison. It therefore carries **no continuum-limit
convergence claim of the kind Ollivier-Ricci's Open Question 1 flags** — RESEARCH.md records
Forman-Ricci as faster to compute than Ollivier-Ricci precisely because it substitutes a closed-
form combinatorial formula for a per-edge optimisation, at the cost of a less direct connection to
the differential-geometric notion of Ricci curvature that motivates using either variant here at
all.

**Cost at n = 10,000.** The cheapest candidate on the graph-native side, and cheaper than any
coordinate-producing candidate that requires an iterative fit. Same 150,000-edge k*=15 graph
(mandatory reuse, identical reasoning to Ollivier-Ricci above), but no per-edge optimal-transport
LP or Sinkhorn approximation is needed at all — Forman-Ricci is a closed-form combinatorial
formula evaluated once per edge, so its cost class is a single linear pass over 150,000 edges
rather than 150,000 entropic-regularised transport problems. The same not-yet-built synthetic
tree-and-expander fixture applies here too, for the same reason: no curvature number from this
branch should be trusted before a known-sign sanity check exists.

**Implementation maturity.** `GraphRicciCurvature` 0.5.3.2 (the same package as Ollivier-Ricci —
it implements both curvature notions on the same NetworkX graph object) and `networkx` 3.6.1, not
installed. Identical maturity profile and identical `checkpoint:human-verify` gating to
Ollivier-Ricci's entry above — no separate `POT` dependency is needed for Forman-Ricci specifically,
since it does not use optimal transport, which is itself part of why it is the lower-cost variant
of the graph-native slot RESEARCH.md's Standard Stack Alternatives table names it as.

**Fork side.** **Graph-native**, per `02.1-FORK.md`'s Fork Test table: a scalar curvature value
per edge of the existing graph, same output type as Ollivier-Ricci, no coordinate vector.

**What it would demand of Phase 3.** Identical bucketing to Ollivier-Ricci: DEC-01 through DEC-05
dropped entirely; CURV-01 and CURV-02 dropped; **CURV-03 replaced by an intrinsic combinatorial
curvature quantity, a different mathematical object from the extrinsic mean-curvature vector it
asks for**, not a re-specification of it; CURV-04 and CURV-05 dropped; CURV-06/CURV-07 rearchitected
around the graph-native synthetic fixture; CURV-08 rewritten around graph edges. The two
graph-native families' Phase 3 demand is identical in shape because both replace the same
requirement set with the same kind of intrinsic, per-edge quantity — they differ in cost and
convergence-claim strength (above), not in what they would require of Phase 3.
