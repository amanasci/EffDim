## Summary

This phase's own `02.6-FINDINGS-02.md` §12 already discloses two defects that escaped their
own test suites and surfaced only at the PU regime's real scale (the `torch.quantile` 2**24
cap in `derivative_bridge._agreement_stats`, and a training-budget asymmetry in the screening
runner). Both fixes and their regression tests are present, correct, and verified directly
against the running code — I confirmed `test_p90_matches_torch_quantile_below_the_cap`,
`test_p90_matches_numpy_linear_interpolation_above_the_cap`, and
`test_agreement_stats_handles_tensor_above_quantile_cap` genuinely exercise the repaired path,
and `torch.quantile`'s cap is real (verified independently is not necessary here since the
regression test itself proves it by catching `RuntimeError` on the unrepaired call).

Hunting specifically for a third defect of the same species (a guard or acceptance criterion
that quietly does less than it claims, invisible until a specific untested configuration is
hit), I found one: `derivative_bridge.py`'s three public finite-difference functions
(`finite_difference_jacobian`, `finite_difference_hessian`, `calibrate_fd_step`) call
`chart_curvature._assert_float64` with `decode_batch` (a bound method or closure) as the
`model` argument rather than the actual model object, which silently skips the
per-parameter float64 check that function is supposed to perform (§Warning WR-01). It is not
currently corrupting any recorded number — every call site in this phase's own runners
pre-casts models to `.double()` before reaching these functions — but it defeats a
documented safety contract with a worse failure mode than the one advertised, on public API
surface that is one direct call away from being exercised by a future caller (a new notebook,
a new runner) that has not done that pre-casting. I reproduced it directly against the
installed code (see WR-01).

Two further Warnings are reported: a relative-error statistic that is provably misleading in
the actual recorded data (WR-02), and a latent memory/reproducibility-boundedness gap in
`calibrate_fd_step` that is currently masked by a numeric coincidence rather than an
enforced invariant (WR-03).

**Security.** There is no network surface, no untrusted input path, no persistence layer,
and no secrets anywhere in this code — it reads local `.venv`-installed libraries, trains
models on synthetic and cached local data, and prints. I checked for the standard patterns
(hardcoded credentials, `eval`, shell/command construction, path traversal from
caller-controlled strings) and found none; the file-path handling in `derivative_bridge_run.py`
uses fixed, hardcoded stems, never user- or caller-supplied strings. There is nothing to
report on this axis, and I am not manufacturing a finding to fill it.

**Project constraints.** `src/effdim/` and `pyproject.toml` are untouched. The
`decoder_curvature.assert_c2_decoder` / `chart_curvature.assert_c2_activation` dispatch
described in the review brief is implemented correctly in the sealed module and used
correctly by `analytic_param.AnalyticParamDecoder` (sets `.activation`, takes the
delegation branch) and `AnalyticSwissRollDecoder` (no `.activation`, takes the structural
branch, correctly returns `"no-activation-modules"`). `cae.ChartAutoEncoder.forward`
returns no `"y"` key, and `decoder_substrate_ph_screen_run.py:242-243` correctly branches
on `model.reconstruct(x)` for the CAE and `model(x)["y"]` for the two plain-autoencoder
arms — the previously-recorded false claim is not reintroduced anywhere in this phase's new
code. No sealed module (`cae.py`, `topoae.py`, `chart_curvature.py`, `curvature_probe.py`,
`decoder_curvature.py`) is modified; `derivative_bridge.reduce_to_H_vec` is a byte-faithful
mirror of `chart_curvature.chart_mean_curvature`'s trace-first-then-project solve, confirmed
by direct comparison of the two implementations and pinned by
`test_reduce_to_H_vec_pins_plain_decoder_curvature_sphere`/`_trained_net`.

## Warnings

### WR-01: The finite-difference functions' float64 guard silently skips the model-parameter check

**File:** `notebooks/pu_manifold/derivative_bridge.py:156, 205, 308`
**Issue:** `finite_difference_jacobian`, `finite_difference_hessian`, and
`calibrate_fd_step` each call `_assert_float64(decode_batch, z)`, where `decode_batch` is a
bound method (`model.decode`) or a closure — never the model object. Reading
`chart_curvature._assert_float64`'s body:

```python
def _assert_float64(model, z_chart):
    if z_chart.dtype != torch.float64:
        raise ValueError(...)
    params = getattr(model, "parameters", None)
    if callable(params):
        for p in params():
            if p.dtype != torch.float64:
                raise ValueError(...)   # never reached from these three call sites
            break
```

A bound method or closure has no `.parameters` attribute, so `callable(params)` is `False`
and the per-parameter dtype check is unconditionally skipped. Each function's own docstring
claims otherwise (`finite_difference_hessian`: "Requires float64 input, checked by
``chart_curvature._assert_float64`` reused unchanged rather than by a new check") — true only
for the `z` half of that check, false for the model-parameter half.

I reproduced this directly against the installed module: calling
`derivative_bridge.finite_difference_hessian(model.decode, z, h=1e-4)` and
`derivative_bridge.calibrate_fd_step(model.decode, z)` with a `model` still in float32 and
`z` in float64 does **not** raise the documented, actionable `ValueError` (`"...Call
model.double()."`). It raises a bare PyTorch `RuntimeError` from inside the matmul several
frames down instead (`mat1 and mat2 must have the same dtype, but got Double and Float` /
`expected m1 and m2 to have the same dtype, but got: double != float`) — a worse debugging
experience than the guard is supposed to prevent, and not the message a caller following the
docstring's stated contract would expect.

This is not currently corrupting any measurement in this phase: `derivative_agreement`
(the only caller reached by the runner) separately calls `_assert_float64(model, z)` with
the real model *before* constructing `decode_batch`, and `bridge_one` /
`build_swiss_roll_models` / `load_pu_models` all `.double()` every model before any of
these functions are reached. But `calibrate_fd_step` and the two `finite_difference_*`
functions are public API, one direct call away (as `bridge_one` already demonstrates for
`calibrate_fd_step`, called *before* `derivative_agreement`'s own check) from a caller that
has not done that pre-casting — and no test in `test_derivative_bridge.py` exercises this
specific case (`test_finite_difference_hessian_refuses_float32` tests `z` being float32 with
a model that has no parameters at all — `_LinearDecoder` — so it cannot distinguish a working
guard from a silently-skipped one). This is the same species as the two defects
`02.6-FINDINGS-02.md` §12 already names: a check whose contract the test suite never actually
exercised in the one configuration where the difference is visible.

**Fix:** Since `decode_batch` carries no reference to the model, the check has to probe
behaviour rather than an attribute. Replace the reused-but-inapplicable `_assert_float64`
call in these three functions with a local check against `decode_batch`'s own output dtype:

```python
def _assert_decode_batch_float64(decode_batch, z_chart):
    if z_chart.dtype != torch.float64:
        raise ValueError(f"...; got z_chart.dtype={z_chart.dtype}. Pass z_chart.double().")
    with torch.no_grad():
        probe_dtype = decode_batch(z_chart[:1]).dtype
    if probe_dtype != torch.float64:
        raise ValueError(
            f"derivative_bridge: decode_batch produced {probe_dtype} output from a float64 "
            "input -- the underlying model is not float64. Call model.double() first."
        )
```
and add a regression test that constructs a float32 model, a float64 `z`, and asserts the
friendly `ValueError` (not a bare `RuntimeError`) is raised by each of the three functions.

### WR-02: `_agreement_stats`'s relative-error columns are dominated by near-zero reference entries

**File:** `notebooks/pu_manifold/derivative_bridge.py:369-385` (`scale = reference.abs()...clamp_min(1e-300)` at line 376)
**Issue:** `clamp_min(1e-300)` prevents an exact division by zero, but does nothing about a
reference entry that is merely *near* zero (a genuinely small-but-nonzero autodiff Hessian
component, common at points where a decoder is locally close to flat along some axis pair).
When that happens, `rel = diff / scale` at that one entry can be enormous even though the
absolute disagreement is tiny, and `rel.max()` (`max_abs_relative`) reports that single
outlier as if it were representative.

This is not hypothetical — it is already visible in this phase's own recorded PU bridge
table (`02.6-FINDINGS-02.md` §8b): `full_hess_max_abs_rel` reaches `1.1351e+00` (>100%) for
`cae_seed20260804`, chart 3, and `5.8313e-01` for chart 4 of the same seed, alongside many
rows well under 1%. A reader skimming the `*_max_abs_rel` column has no way to tell a
genuine large disagreement from a single near-zero-reference entry being divided by an
arbitrarily small (but not literally zero) denominator, and neither the module docstring nor
the runner's printed output caveats this the way `persistence_probe.py` explicitly caveats
its own thin-denominator and saturation cases.

**Fix:** Either (a) document the limitation plainly next to `max_abs_relative` in the
docstring (a one-sentence caveat mirroring `persistence_probe.max_persistence`'s "thin
denominator" note would suffice — this is a reporting-clarity fix, not a math fix, since D-18
already forbids applying any threshold here), or (b) report an additional diagnostic
alongside the relative stats — e.g. the count or fraction of entries where
`reference.abs() < some_floor`, or a version of `max_abs_relative` computed only over entries
above a floor — so a reader of the printed tables can distinguish "genuinely large relative
disagreement" from "one near-zero reference entry."

### WR-03: `calibrate_fd_step`'s autodiff Hessian is computed unchunked, unlike every other call site in this codebase

**File:** `notebooks/pu_manifold/derivative_bridge.py:317`
**Issue:** `autodiff_hess = vmap(hessian(decode_one))(z)` runs on the whole `z` batch in one
`vmap` call. Every other autodiff-Hessian call site in this codebase —
`chart_curvature.chart_mean_curvature`, `decoder_curvature.plain_decoder_curvature`, and
`derivative_agreement`'s own explicit Jacobian/Hessian loop two functions below this one in
the same file — chunks at the fixed `VMAP_CHUNK=32` width, both to bound peak memory
(`chart_curvature.py`'s own `VMAP_CHUNK` docstring: "sets peak memory, since the Hessian
dominates") and for bit-reproducibility across differing batch widths (documented in the
same place as a measured, non-hypothetical effect). `calibrate_fd_step` is the one place in
the module that differentiates a batch and skips that discipline.

This has not caused an observed failure because `notebooks/diagnostics/derivative_bridge_run.py`'s
`BRIDGE_N_POINTS=32` happens to equal `VMAP_CHUNK`, and the CAE's per-chart groups
(`_cae_chart_groups`) always partition that same 32-point budget, so no `z` reaching
`calibrate_fd_step` in the current runs ever exceeds 32 rows at the PU regime's `out_dim=768`.
That equality is a numeric coincidence in the runner's constants, not an invariant enforced
or even asserted anywhere in `derivative_bridge.py` itself. If `BRIDGE_N_POINTS` were raised
in a future PU-regime run (exactly the kind of scale change that produced the two defects
`02.6-FINDINGS-02.md` §12 already records), the unchunked Hessian computed here would again
approach the tens-of-millions-of-elements range that already broke `torch.quantile` once in
this same module — `vmap(hessian(...))` has no matching hard element cap, so it would not
necessarily crash the way `torch.quantile` did, but it would silently lose both the peak-memory
bound and the bit-reproducibility guarantee `VMAP_CHUNK` exists to provide, with no test to
catch the regression.

**Fix:** Reuse the same chunking loop `derivative_agreement` already has, factored into a
small helper (`_chunked_vmap_hessian(decode_one, z)`) called from both places, so
`calibrate_fd_step`'s comparison Hessian is computed under the identical discipline as the
Hessian it is being compared against for step selection. At minimum, assert
`z.shape[0] <= VMAP_CHUNK` or chunk defensively rather than relying on the caller's constants
never drifting.

**Issue:** `finite_difference_jacobian` is exercised by
`test_finite_difference_jacobian_matches_autodiff_sphere` but is never called from

worth naming: if it exists as public API for a future caller, its docstring should say so
explicitly; if it was scaffolding left over from building the Hessian stencil, it is dead
production code (a tested function nobody calls is still dead from the pipeline's point of
view).
**Fix:** Either document it as intentionally-standalone public API, or remove it if it was
scaffolding.

### IN-02: CAE latent-dimension confound is real but already self-disclosed

**File:** `notebooks/diagnostics/decoder_substrate_ph_screen_run.py:294`
**Issue:** `latent_dim = CAE_EMBED_DIM if candidate == "cae" else LATENT_DIM` scores the
CAE's latent persistence diagrams at 8 dimensions against the other two candidates' 2
dimensions — confirmed by direct reading, and it is a genuine dimensional-comparability
problem for any `latent|*` cell comparison across candidates. I am not raising it as a new

defect in detail ("a defect in the ratified design itself, found only by measurement"), and
correctly restricts its own cross-candidate reading to the one dimensionally-clean comparison

finding's own citation and that no further undisclosed instance of the same confound exists
elsewhere in the runner (checked: `decoder_image` space is always the shared `R^3`/`R^768`
ambient dimension regardless of candidate, so no other cell carries this problem).
