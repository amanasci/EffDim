## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - math-level test premise] Batch-split cross-split comparison corrected from exact `torch.equal` to `atol=1e-9`**
- **Found during:** Task 3 (`test_plain_decoder_curvature_batch_split_is_bit_identical`)
- **Issue:** The plan's own must-have truth and Task 3's `<behavior>` both specify that
  `plain_decoder_curvature`'s results must be exactly `torch.equal`-bit-identical across an
  arbitrary caller-side row split (e.g. one call on 70 rows vs. two calls on `z[:50]` and
  `z[50:]`), attributing this to `chart_curvature.VMAP_CHUNK`'s fixed autodiff width. Running
  the test as specified on a real trained `PlainAutoEncoder` (`hidden=(64,64,64)`) failed:
  measured max abs diff `~7.1e-14` at 7 of 70 rows. Traced the cause: the Jacobian and Hessian
  themselves agree across the two chunk compositions to `~2e-17` (~1 ULP, exactly what
  `VMAP_CHUNK`'s docstring is really evidencing), but `torch.linalg.solve`'s two chained calls
  amplify that by roughly `cond(g)^2` where `cond(g) ~ 470` at the affected rows, landing at
  the observed scale. Independently confirmed this is a property of the **sealed**
  `chart_curvature.chart_mean_curvature` itself (built a duck-typed decoder of matching hidden
  width and ran the identical split test against it directly) -- not a regression introduced by
  this plan's new module, and not fixable without editing the sealed file (prohibited).
  `VMAP_CHUNK`'s docstring claim ("bit-identical regardless of which other rows share its
  chunk") was measured true only at `chart_curvature.py`'s own tiny toy-decoder test scale
  (`hidden=[8]`) and does not transfer to production-sized hidden widths.
- **Fix:** Kept the test's intent (arbitrary caller-side split reproducibility) but split the
  assertion in two: (a) determinism -- calling `plain_decoder_curvature` twice on the identical
  `z` -- asserted as exact `torch.equal` (this module has no randomness, and it holds exactly);
  (b) the cross-split comparison asserted with `torch.allclose(atol=1e-9, rtol=0.0)`, a margin
  ~4 orders of magnitude above the measured `~7e-14`, tight enough to still catch a genuine
  row-reordering or re-widthing bug (which the sealed
  `test_chart_curvature_field_reassembles_in_row_order` precedent shows would produce
  differences at the `~5e-15`-and-up scale from width alone, let alone an actual bug).
- **Files modified:** `notebooks/pu_manifold/tests/test_decoder_curvature.py`
- **Verification:** All 10 tests pass; full suite 296 passed.
- **Committed in:** `751a6d8` (Task 3 commit)
- **Ledger:** Recorded in `.planning/WINDOWS.md` as a `deviation` (entry 4, phase 02.6, status

## Issues Encountered

**The correction the plan itself flagged, confirmed exactly as described.**
`chart_curvature.assert_c2_activation` was confirmed to hard-raise on a default
`cae.PlainAutoEncoder()` (`pytest.raises(ValueError)` around the call, in
`test_assert_c2_decoder_accepts_default_plain_autoencoder`), because
`PlainAutoEncoder.__init__` sets no `.activation` attribute
(`cae.py:584-594`). `02.6-RESEARCH.md` and `02.6-PATTERNS.md` both state the opposite ("Both
`PlainAutoEncoder` default constructions use `activation="silu"` by default so this passes").
`assert_c2_decoder(cae.PlainAutoEncoder(3, 2))` returns `"silu"` -- the module this plan builds
is precisely the fix for that gap. Downstream plans (`02.6-03`, `02.6-04`) inherit this
correction: they must call `decoder_curvature.assert_c2_decoder`, never the sealed
`chart_curvature.assert_c2_activation`, on a `PlainAutoEncoder`.
