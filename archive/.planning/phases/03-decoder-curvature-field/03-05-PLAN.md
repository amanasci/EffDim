<objective>
Add an opt-in forward-mode differentiation path to `chart_curvature.py` and prove it equal to the
existing reverse path, without moving a single bit of the reverse path.

For `F: R^d -> R^D`, reverse mode computes one Jacobian **row** per pass (about `D = 768` passes);
forward mode computes one **column** per pass (about `d = 20`). `torch.func.hessian` is
`jacfwd(jacrev(f))`, compounding it to roughly `d * D = 15,360` versus `d^2 = 400`. Same tensor, same
values, exact either way. The gap survived unnoticed because every execution to date has been Swiss
roll at `d=2, D=3`, where reverse costs 3 and forward costs 2. Official PyTorch guidance
independently confirms the direction (`M > N` outputs-versus-inputs favours `jacfwd`).

**The ~38x is an operation-count ceiling, not a measured speedup.** PyTorch's forward-mode path is
less optimized than its reverse path, `vmap` over dual numbers carries its own constants, and
forward-over-forward may hit an unimplemented batching rule and not run at all. That is exactly why
the default stays reverse and why this plan spikes the composition before designing anything around
it.

This is the first edit `chart_curvature.py` has ever received — `02.5-09` recorded that it "needed no
change" and ran unmodified on first attempt. The reverse path staying bit-identical is what preserves
the `-0.0604` reproduction, so the regression evidence is plan 03-01's and 03-02's own recorded roll
numbers, measured before this edit existed.

Purpose: make PU-scale curvature affordable without putting any recorded number at risk.
Output: a `mode` keyword, a spiked-and-proven forward path, and four regression tests.
</objective>

<assumption_delta_decision>
**Noun now primary:** the *differentiation mode*. `chart_curvature.py` currently has exactly one
differentiation path — reverse (`jacrev`, `jacfwd(jacrev)`) — hard-coded as a property of the module.
D-08 turns that constant into a parameter: `mode` becomes a selectable input with two legal values,
so a configuration fact becomes a modeling decision the caller owns.

**Decision:** `add-alongside`.

**Rationale:** the developer's instruction in `03-CONTEXT.md` is explicit — *"the forward-mode toggle
exists so it can be abandoned cheaply — just make it a toggle, so if it doesn't work we can go back
to reverse easily. Default reverse, opt in to forward. Do not make forward the default even after
equivalence passes."* That overrides the checkpoint's usual promote-by-default disposition. Reverse
stays the default so every existing call site, the `02.5-09` notebook, and the sealed roll numbers
reproduce untouched.

**Accepted debt:** two differentiation paths now exist where one did. Every future change to the
Jacobian or Hessian construction must be made twice or made in the shared helper, and the equivalence
test is the only thing keeping them honest. That is a real maintenance cost, accepted deliberately in
exchange for a cheap retreat.

**What would force a later promote:** a *measured* wall-clock speedup at the real regime
(`d = 20`, `D = 768`, the trained `cae.ChartAutoEncoder` decoder), together with forward-mode `vmap`
proven free of unimplemented-batching-rule errors on that same decoder across a full field
computation. Absent both, forward stays opt-in.
</assumption_delta_decision>
