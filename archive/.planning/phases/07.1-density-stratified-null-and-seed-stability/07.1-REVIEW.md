## Warnings

### WR-01: `run_positive_control` has no `--resume`/dedupe logic at all

**File:** `notebooks/diagnostics/07.1_density_stratified_null_run.py:401-480`
**Issue:** `run_null` and `run_seeds` both read the record file first, build an
`already_done_*` set gated on `args.resume`, and skip cells/seeds already recorded under a
matching `preregistration_commit`. `run_positive_control` does none of this: every invocation
of `--mode positive-control` unconditionally appends a fresh set of 18 `positive_control` rows
plus 1 `positive_control_summary` row, regardless of whether an identical sweep under the same
`preregistration_commit` already exists in the file. A retried or accidentally re-run
positive-control pass silently duplicates the entire sweep. `_read_positive_control_summary`
(consumed by both `run_null` and `run_seeds`) tolerates this only because it takes the *last*
matching `positive_control_summary` row — an implicit, unenforced "last-wins" contract rather
than a real invariant. In this checkout the record currently contains exactly one summary row
(no duplication has actually occurred), but nothing in the code prevents it on a future re-run.
**Fix:** Give `run_positive_control` the same shape `run_null`/`run_seeds` already use — scan
existing rows for a matching `(preregistration_commit)` positive-control summary and, when
`args.resume` is set (or unconditionally, to match D-04's "run once per commit" intent), skip
re-appending if one is already present:
```python
already_has_summary = False
if record_path.exists():
    with record_path.open() as fh:
        for line in fh:
            row = json.loads(line) if line.strip() else {}
            if (row.get("row_kind") == "positive_control_summary"
                    and row.get("preregistration_commit") == preregistration_commit):
                already_has_summary = True
if already_has_summary and args.resume:
    print("[resume] positive-control already recorded under this commit -- skipping.")
    return "positive-control already recorded"
```

### WR-02: Inconsistent dedupe gating between per-cell rows and summary/verdict rows

**File:** `notebooks/diagnostics/07.1_density_stratified_null_run.py:543-568, 610-628,
740-752, 781-792` (`run_null`) and `:861-887, 1129-1142` (`run_seeds`)
**Issue:** In both `run_null` and `run_seeds`, the per-cell / per-seed dedupe (`already_done_
cells`, `already_done_seeds`) is populated **only when `args.resume` is passed**. But the
diagnostic/verdict row dedupe (`has_null_mean_vs_strata`, `has_verdict`, `has_seed_verdict`) is
computed **unconditionally**, by scanning for a matching row under the same
`preregistration_commit` regardless of `args.resume`. The practical consequence: a plain re-run
of `--mode null` (or `--mode seeds`) under the same freeze commit *without* `--resume` will
recompute and append a full duplicate set of 9 `null_grid` rows (or 3 `seed` rows), but will
silently **not** re-append the `null_mean_vs_strata`/`verdict` (or `seed_verdict`) row, because
those checks fire whether or not `--resume` was requested. This is an inconsistent contract: a
"fresh run" either duplicates everything or duplicates nothing, and currently it does neither
consistently — it duplicates only the per-cell/per-seed rows. Anyone auditing the record file
after an accidental re-run would see 18 `null_grid` rows but still only 1 `verdict` row, which
is confusing and makes the file's row counts an unreliable signal for "how many times was this
run."
**Fix:** Gate the `has_null_mean_vs_strata`/`has_verdict`/`has_seed_verdict` checks on
`args.resume` too (so a non-resumed run always re-appends everything, matching the per-cell
behavior), or, symmetrically, make the per-cell/per-seed skip unconditional on existing-row
presence (so a non-resumed run never duplicates rows for a commit it has already fully
processed). Either direction is fine; the current mixed state is not.

### WR-03: `run_seeds` rewrites the entire multi-seed npz on every iteration, non-atomically

**File:** `notebooks/diagnostics/07.1_density_stratified_null_run.py:1054-1060`
**Issue:**
```python
seed_fields[seed] = h_norm
savez_kwargs: Dict[str, Any] = {f"h_norm_25_seed{seed}": h_norm}
if fields_path.exists():
    with np.load(fields_path) as existing_z:
        for key in existing_z.files:
            savez_kwargs.setdefault(key, existing_z[key])
np.savez(fields_path, **savez_kwargs)
```
On every seed's iteration, the code reads back whatever keys already exist in
`07.1_seed_fields_d25.npz` and rewrites the *entire* file with `np.savez`, which is not an
atomic write (no temp-file-plus-`os.replace`). The comment immediately above this block
("`--resume` treats correctly as 'not yet done'") reasons about the narrower window *between*
the `savez` call and the JSONL `append_record_row` call, but misses the more direct risk: if
the process is interrupted (killed, OOM, power loss) *during* the `np.savez` write itself on
seed 1's or seed 2's iteration, the file can be left truncated or corrupted, destroying the
*previously already-saved* seed(s)' fields along with the current one — even though those
earlier seeds' `seed` rows are still present in the JSONL and `--resume` will treat them as
"done," so a subsequent `--resume` run will never re-fit them, leaving the npz permanently
missing those fields.
**Fix:** Write to a temporary path and atomically replace:
```python
tmp_path = fields_path.with_suffix(".npz.tmp")
np.savez(tmp_path, **savez_kwargs)
os.replace(tmp_path, fields_path)
```
or store one `.npz` file per seed (`07.1_seed_fields_d25_seed{seed}.npz`) so a corrupted write
can only ever affect the seed currently being written, not the others.

### IN-01: `X_hsc` unpacked but never used at four call sites

**File:** `notebooks/diagnostics/07.1_density_stratified_null_run.py:324, 417, 574, 898`
**Issue:** `run_smoke`, `run_positive_control`, `run_null`, and `run_seeds` all destructure
`mknn_arr, density, X_hsc, X_ls, subsample_file = recompute_mknn_and_density()`, but none of
the four subsequently references `X_hsc` (MKNN and density are already computed inside
`recompute_mknn_and_density`; only `X_ls` is needed afterward, by `run_seeds` for the decoder
fit). Harmless, but it is dead binding repeated at four call sites.
**Fix:** Either use `_` for the unused position (`mknn_arr, density, _X_hsc, X_ls,
subsample_file = ...`) or narrow `recompute_mknn_and_density`'s return tuple/callers if `X_hsc`
turns out to have no remaining consumer at all.
