## Launch Instructions (the deliverable's whole purpose)

**To start the full grid:**
```bash
.venv/bin/python notebooks/diagnostics/template_benchmark_run.py
```
This runs the complete ratified 15-configuration x 4-template = 60-combination grid
(`n_ph=300`, `B=10`, `draws=3`, `k_values=[5,10,15,20,30]`, `D` in `{18,100,768}`, noise in
`{0.01,0.05,0.1}`, plus the `n`/density OFAT arms), writing an append-only JSON-lines record to
`notebooks/.cache/template_benchmark_run_record.jsonl` (gitignored, per `CLAUDE.md`'s milestone-
artifact convention) as each combination completes.

**Expected wall clock:** roughly **17 hours**, unattended — `02.7-SCREENING-RULE.md` Sec.9's own
ratified Option A projection (`02.7-BUDGET-CALIBRATION.md`'s worst-*measured*-template, `S2`,
figure), with `ball`'s own true cost still unmeasured and potentially higher were its timeout
fallback not in place. This project has precedent for unattended runs of this general order
(Phase 02.4 P03 ~10h30m, Phase 02.6 P12 ~8h25m); 17h is a new high but not a different order of
magnitude.

**To resume after an interruption** (crash, `Ctrl-C`, or a deliberately segmented run):
```bash
.venv/bin/python notebooks/diagnostics/template_benchmark_run.py --resume
```
Any `(configuration, template)` combination already present in the record file is skipped, not
recomputed. To run only a bounded number of combinations per invocation (segmenting the ~17h
grid across multiple sessions):
```bash
.venv/bin/python notebooks/diagnostics/template_benchmark_run.py --resume --max-combos 5
```

**To check the plan is well-formed before committing to a multi-hour run** (zero compute, zero
writes):
```bash
.venv/bin/python notebooks/diagnostics/template_benchmark_run.py --dry-run
```

**Where results land:** the JSON-lines record above, one line per completed combination, each
carrying every draw's Betti vectors (both metric arms, separately labelled), bands, the eight
estimators' values at every swept `k`, `d_hat` (or `None` plus reason), local dispersion (both
the D-12-amended gating subset and the full 8-estimator report), the decision, the outcome, and
per-combination wall clock. The runner also prints a running D-13 three-way tally
(`correct`/`wrong`/`abstained`/`total`, the three rates, `by_condition`) to stdout as it goes and
at the end of every invocation. **Writing `.planning/phases/.../02.7-BENCHMARK-RESULTS.md` from
that record is Task 2's own job, not automated by this runner** — Task 2 (a future continuation
of this plan) reads the completed JSON-lines record and assembles the markdown document the
plan's own acceptance criteria specify (the three-way tally, per-condition abstentions, both
metric arms separately, the `D` x noise cell grid, per-template results, excluded-cell count, and
the five assumption bounds).

Two implementation decisions were REQUIRED to make Task 1's own acceptance criteria executable,
because `02.7-SCREENING-RULE.md` ratifies the `k`-sweep parameters (`K_VALUES`, `MIN_RUN`) but
not a single winning `k` for the actual `D_geo`/local-dispersion build (neither
`geodesic_graph.contiguous_stable_range` nor `local_dimension.plateau_consensus` picks one for
their caller). Both are stated explicitly in the runner's own module docstring, exactly per
`02.7-SCREENING-RULE.md`'s own convention for judgment calls that are not calibration- or
ratification-grounded:

1. `_select_geodesic_k` — first `k` of `n_components`'s longest stable run (or largest swept `k`
   as fallback when no run reaches `MIN_RUN`; `k_stable_enough=False` recorded either way, never
   silently hidden).
2. `_select_dimension_k` — latest `start_index` among the winning `d_hat`'s own supporting
   estimators' runs (guaranteeing the chosen `k` sits inside every one of them), falling back to
   the largest swept `k` when there is no consensus (`decide` abstains via (d) before this choice
   matters in that case).

Neither is a ratified constant, a threshold, or a grid level — both are engineering choices about
which single measurement to report from an already-ratified sweep, made necessary by the ratified
rule's own explicit choice not to pin them down (`contiguous_stable_range`'s own docstring: that
decision is the caller's).
