<decisions_resolved_here>
**OQ-4 — import `topoae.py`'s R6 functions, or mirror them?** RESOLVED: **mirror**, into
`curvature_probe.py`, with 02.5-scoped stems. `write_topoae_verdict` hard-codes the stem
`topoae_verdict_{fit_key}` and `cfg["phase"] = "02.4"`; `write_topoae_handoff` hard-codes
`representation_id = "topoae"` and a payload schema built for a coordinate-producing model.
Neither is parameterized by phase or stem. Importing them would either write 02.5 results under
02.4-tagged stems — which is how a phase's record becomes unreadable — or require editing a
completed phase's artifact. Mirroring follows the precedent `topoae.py` itself set:
`write_topoae_verdict`'s own docstring (`topoae.py:692-693`) explains that it "mirrors
`cae.write_cae_verdict`'s shape but does not call it" for exactly this reason. `topoae.py` is not
edited, not generalized, and not called by this phase.

**OQ-5 (surfaced during planning, not in RESEARCH.md) — the delegation route into
`cae.verdict_from_metrics` is unavailable here, for two independent reasons.** First,
`topoae.py`'s `CAE_SLOT_ALIASES` remap asserts both tuples have exactly three entries
(`topoae.py:632-636`); stage 1 has one gating metric and stage 2 has two, so no positional remap
exists. Second, `cae.verdict_from_metrics` applies strict **less-than** to every gate, and stage
1's gate is a strict **greater-than** (Spearman must *exceed* its threshold). Delegating would
require sign-flipping the metric before handing it over, which puts a transformation between the
measurement and the tested comparison — precisely the opacity the delegation pattern exists to
avoid. RESOLVED: `curvature_probe.py` implements its own `_apply_gates` with an explicit
per-gate direction map, mirroring `cae.py:1077-1097`'s guard-then-compare discipline line for
line but not calling it. `cae.GATING_METRICS` is never monkeypatched and `cae.verdict_from_metrics`
is never called.
