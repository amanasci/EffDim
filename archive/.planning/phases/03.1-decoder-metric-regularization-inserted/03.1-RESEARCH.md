## User Constraints (from CONTEXT.md)

### Locked Decisions

#### Test bed and arm matrix

- **D-01:** **The `d=20` saddle is the only fixture.** It is the sole control that scores all
  four axes — its analytic `H` is varying and mixed-sign, so `rho` and `R²` are defined, where
  the sphere's constant `H` leaves both undefined by construction. It is also the cleanest
  failure on record to try to move: `rho = −0.0151`, `R² = 0.000002`, cosine `−0.000478`,
  magnitude ratio `9955`, `cond(g) ≈ 1.88e+08`, 4/4 charts. At `d=4` the identical fixture gives
  `rho = 0.989`, `R² = 0.980`, so the gap is the *fit's*, not the estimand's. The sphere is not
  run. — **Reversibility:** reversible — a sphere arm can be added later at the cost of its own
  fits; nothing in the runner's design forecloses it.

- **D-02:** **Three arms plus a baseline: `weight=0`, `scale` ladder, `christoffel` ladder, then
  one combination cell.** The combination arm is **best-of-each**: run the two single-mode
  ladders first, pick each mode's best weight on D-08's read-out, then run **one** cell at
  `(best_scale, best_christoffel)` × 3 seeds. Cost is additive, not multiplicative. **This cell
  is a post-hoc confirmation, not an independent measurement, and must be labelled as such in
  every table it appears in** — its weights were chosen after seeing the ladders.

- **D-03:** **3 seeds per cell, median *and* full spread always printed.** Matches Phase 3's own
  three-seed reporting unit so 03.1's numbers are directly comparable to the 52× spread that
  motivated this phase; reuse seeds `20260813 / 20260814 / 20260815` where the fixture allows.
  **Never report a single draw.** Stated limitation to carry into the write-up: 3 draws cannot
  separate a small real effect from seed noise, and the phase says so rather than implying
  otherwise. — **Reversibility:** costly — the seed count sizes the entire compute budget.

- **D-04:** **Ladder weights are calibrated per mode at init, not hand-picked in absolute
  units.** Measure each penalty's raw value at epoch 0 on the saddle, then set weights so the
  penalty contributes a **declared fraction of the base loss** (e.g. `{0.01, 0.1, 1.0} ×
  base_recon / base_penalty`). Rationale: the two penalties differ by ~2 decades in raw
  magnitude on real checkpoints — `scale` measured `62.09 / 346.05 / (seed 15)` against
  `christoffel`'s `2.34` — so one shared absolute ladder would spend roughly half its cells
  where one mode does nothing measurable. The calibration probe is nearly free. **The fractions
  are declared in the plan before the probe runs**; only the resulting absolute weights are
  data-derived.

- **D-05:** **The `weight=0` baseline is re-fit fresh inside 03.1, 3 seeds, under this phase's
  own protocol** — Phase 3's sealed `d=20` saddle row is *not* reused as the comparison point.
  Rationale: `03-NOTE-isometry-prior-spike.md` §5 flags exactly this trap — its own `weight=0`
  arm "is not comparable cell-for-cell to the sealed grid" because early stopping differed. Also
  follows Phase 3's D-10 (fresh fits only). At `weight == 0.0` `decoder_prior_active` installs
  nothing at all, so the baseline is **structurally**, not merely numerically, the untouched
  `cae.train_cae` code path.

#### Compute budget and the halt rule

- **D-06:** **Envelope is overnight, ~8–12 h, on CPU.** Sized to what the arm matrix actually
  costs rather than to a round number that must then be defended. Precedent: Phase 3's `03-07`
  PU sweep ran a ~5.6 h nine-cell grid against a 5 h envelope and was accepted. **This is the
  decision that killed the predecessor** — `03-NOTE-isometry-prior-spike.md` §3 recorded
  `BUDGET NOT MET` with **zero cells trained**, because the first-order prior tripled per-epoch
  cost (`3.685s → 10.699s`) and the cheapest candidate projected `3636s` against a `3000s`
  budget. `christoffel` at `chart_dim=20` costs roughly `chart_dim` times a Jacobian **on top of
  that**. — **Reversibility:** costly — the ladder, seed count and epoch budget all size off it.

  **CPU, not GPU:** every number this phase compares against — the sealed `03` rows, the exact
  anchor `rho_chart = -0.06041003026778113`, the spike's own timing — was measured on CPU, so
  nothing needs re-anchoring and reproduction stays exact. `chart_curvature` refuses anything but
  float64, where consumer-GPU throughput is poor anyway.

- **D-07:** **The pre-declared relief valve, if the timing probe still projects over the
  envelope, is to cut `CHRISTOFFEL_MAX_ROWS_PER_CHART`** (currently 8). This is legitimate
  because `decoder_priors.py` documents that constant as **a compute bound, not a tuning knob
  for the penalty's strength** — "the penalty is a batch mean either way, so a subsample
  estimates the same quantity with more variance rather than a different quantity." Declaring it
  up front means the fallback is a **stated variance cost on a term the module already
  sanctions**, not a redesign under time pressure — which is what the spike's own `--probe`
  docstring forbids. Consequence to report: wider error bars on the `christoffel` arm
  specifically. **Explicitly not the valve:** cutting the fixture's sample count (Phase 3's
  Amendment 1 raised `N_POINTS` 3000 → 12000 precisely because curvature is a second-derivative
  quantity), or cutting epochs (under-training is a confound Phase 3 spent a whole quick task
  on).

#### The read-out

- **D-08:** **Two-tier read-out, tiers never merged.**
  - **Tier 1 — mechanism.** Does the metric itself improve as weight rises? `λ_min`, `λ_max`,
    `det(g)`, `cond(g)` moving toward healthy.
  - **Tier 2 — estimand.** Do the four axes move toward 1? cosine / magnitude ratio / `R²` /
    `rho`, **scored separately, never collapsed** (milestone-standing rule: at seed 0 a decoder
    scored cosine `0.9706` while calibration slope was `−0.1856` at `R² 0.0533`).

  Tier 2 is the point; **Tier 1 is what tells a real null apart from a broken hookup.** A prior
  with no measurable effect on its own target quantity was never actually tested. The halted
  spike's runner already framed itself around a `MECHANISM DEMONSTRATED` verdict for this reason.
  The two tiers may disagree, and if they do, both are reported.

- **D-09:** **Held-out reconstruction is printed beside every cell as the bias guard.** Both
  penalties are parameterization-only by construction — `scale` is a function of `g` alone,
  `christoffel` is test-proven to penalize the tangential part of `D²F` and never the normal part
  — so neither can move `H = tr_g(II)`, which is a property of the decoder's *image*. But those
  tests prove the **penalty** is invariant, not that the **fitted surface** is unchanged: the
  remaining risk is the decoder fitting a different, easier surface, and on a fixture with fixed
  analytic truth that shows up directly as reconstruction degradation. **Stated rule: an
  improvement bought with materially worse reconstruction is not an improvement.** **No hard
  numeric threshold** — the last reconstruction threshold proposed in this milestone
  (`mse_per_dim < 2.5e-04`) was **deferred as circular**, anchored to the model's own measured
  ceiling, and that objection is unchanged.

- **D-10:** **Diagnostics table with the reading rule stated in the plan. No declared bar, no
  verdict artifact.** No `PREREGISTRATION.md`, no ratification commit, no git-ancestry proof, no
  verdict JSON, no threshold table. The plan states **before anything runs** which direction on
  which axis counts as the prior working, and that a null is a complete answer. Rationale:
  Phase 3's D-15 and the ROADMAP's own start-simple instruction; **03.1 selects nothing
  downstream on its own**, so there is nothing a gate would protect. Note for the planner: a
  floor on the estimand was considered and rejected — nothing in this milestone bounds what
  `rho` is achievable at `d=20` on a saddle, so any floor would be invented rather than
  calibrated. — **Reversibility:** reversible — machinery can be added to a later step if one
  turns out to need it.

- **D-11:** **If both arms are null, 03.1 reports the null plainly and stops.** Escalation is an
  **explicit user decision**, per `02-NOTE-phase-2-stage-on-hold.md` §5's rule that only a named
  user decision resumes a held phase. The phase does **not** pre-commit to a conclusion the data
  has not produced (e.g. "therefore the substrate is wrong"), and does **not** widen its own
  scope — more weights, a `d` sweep, the sphere fixture — to avoid reporting a negative result.
  Consequence, stated rather than hidden: **Phase 4 stays blocked** with no proposed route out.

  collapsed into one — which is exactly what the roadmap demands.** The signature is not

## Summary

This phase adds no new mechanism. `notebooks/pu_manifold/decoder_priors.py` already implements
all four prior modes (`isometry`, `conformal`, `scale`, `christoffel`) behind a tested,
restore-on-exit contextmanager that patches `cae.chart_loss` without touching the sealed
`cae.py`. What is missing is *measurement*: no `scale` or `christoffel` cell has ever been
trained — the one prior attempt (`03-NOTE-isometry-prior-spike.md`) halted at its own
pre-declared compute-budget gate with **zero cells trained**, and that halt is squarely the risk
D-06/D-07 exist to avoid repeating.

Read directly against source, this research finds the compute picture is **more constrained than
the predecessor's own halt suggests**, for a reason the predecessor never reached: the
predecessor's timing probe measured only *training* cost on the Swiss roll (`chart_dim=2`); it
never got far enough to measure *curvature-field evaluation* cost at the real target scale
(`chart_dim=20`, ambient `768`, `n=10000`). A directly-measured number already exists in this
repo's own sealed record (`notebooks/.cache/03_synthetic_controls.jsonl`, the exact row D-13's
anchor check must reproduce): the `d=20` saddle's curvature-field evaluation, on its own, costs
**~2,994s (~50 min) per cell**, independent of prior mode or weight, because it is a fixed
function of `(n=10000, chart_dim=20, ambient=768)`. Multiplied across the pre-declared 24-cell
grid implied by D-02/D-03 (`1 baseline + 3 scale rungs + 3 christoffel rungs + 1 combination`, ×
3 seeds), curvature evaluation *alone* costs **≥ 24 × ~2,994s ≈ 19.96 h** — already over the
12 h upper bound of D-06's envelope, before a single epoch of training is counted. This is the
single highest-priority planning risk in this phase and is detailed with full arithmetic below.

Everything else researched here is comparatively mechanical: the nested-contextmanager
composition in D-12 is correct by direct code reading (LIFO unwind through both levels, verified
against no live hazard); the `chart_mean_curvature`/`chart_curvature_field` integration point
for D-15's three new fields is exact, reuses the metric `g` already computed, and can be proven
against `torch.linalg.cond`/`torch.linalg.det` to float64 round-off (verified in this session);
the D-13 anchor value is `rho_spearman = -0.015106571347065712` at `config_id =
"control_saddle_nc4_d20_ep300"`; and D-04's calibration probe is genuinely free — both raw
penalty values and `base_recon` are one forward pass away, with no bespoke training run needed.

**Primary recommendation:** before committing to any epoch count or ladder size, run a **real
timing probe at the target architecture** (`chart_dim=20`, `hidden=[250,250,250]`,
`n_charts=4`) that separately measures (a) train-seconds-per-epoch under `weight=0`, `scale`,
and `christoffel`, and (b) curvature-field-evaluation-seconds-per-cell as a function of
evaluation sample size — then size the ladder against D-06's envelope using that measured
number, not an extrapolation from the Swiss roll. Treat the evaluation sample size for the 24
ladder cells (as opposed to the mandatory full-`n=10000` anchor-check cell) as a genuine, ratified
design decision, not a silent default — there is codebase precedent (`curvature_field_pu_run.py`'s
own selection grid evaluates curvature on the 2,000-row holdout only, reserving full-cloud
evaluation for the single deliverable field) for treating evaluation-set size as separable from
training-set size, which D-07 protects.

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Prior injection (scale/christoffel penalty into training loss) | Model / training loop (`decoder_priors.py` patching `cae.chart_loss`) | — | Pure in-process PyTorch training-time regularization; no service boundary |

| CURV-04 absolute-scale fields | Model / measurement (`chart_curvature.py`) | Every caller (runner, PU field, synthetic controls) | Central library function — one edit point, three downstream consumers inherit it (D-15's stated rationale) |
| Swiss roll prior check (D-14) | Notebook / presentation | Model / training loop (imports `decoder_priors`, `cae` unchanged) | Sanity-check layer per CLAUDE.md, never re-implements the model it tests |
| Nested-prior composition (D-12) | Model / training loop | — | Two context-manager entries around one `train_cae`/`train_blocked` call; no new module |

There is no browser, server, API, or CDN tier in this phase — it is entirely local Python
(PyTorch on CPU) plus notebook/script artifacts on disk. The map above exists mainly to confirm
that nothing in this phase's scope belongs anywhere but the model/training and
measurement/script tiers, which matches CONTEXT.md's "measurement, not implementation" framing.

### Pattern 1: Weight=0 as a structural no-op, not a numerical one
**What:** `decoder_prior_active` returns immediately at `weight == 0.0` without touching
`cae.chart_loss` at all (`decoder_priors.py` lines 381-383).
**When to use:** Every baseline cell in D-05, and the combination arm's degenerate single-mode
tests, should rely on this rather than special-casing "no prior" as separate code.
**Example:**
```python
# Source: notebooks/pu_manifold/decoder_priors.py, decoder_prior_active, lines 379-383
if mode not in PRIOR_MODES:
    raise ValueError(f"decoder_prior_active: mode must be one of {PRIOR_MODES}; got {mode!r}.")
if weight == 0.0:
    yield
    return
```

### Pattern 2: Nested contextmanager composition (D-12)
**What:** `decoder_prior_active` captures `cae.chart_loss` *at its own entry time* into
`original_chart_loss`. Nesting a second `decoder_prior_active` inside an already-active one
therefore captures the OUTER's patched function as the inner's "original," and the inner's
wrapper calls it before adding its own penalty — additive composition falls out of the existing
code with no new logic.
**Verified in this session by direct reading** (not assumed): entering `scale` (outer) rebinds
`cae.chart_loss` from `L0` (real) to `L1 = L0 + scale_penalty`. Entering `christoffel` (inner)
then captures `original_chart_loss = L1` and rebinds to `L2 = L1 + christoffel_penalty = L0 +
scale_penalty + christoffel_penalty`. On exit, the inner's `finally` restores `cae.chart_loss`
to `L1` (not `L0`) — the outer's own patched state — and only when the outer's `finally` fires
does it restore to the true original `L0`. This is standard Python `with A: with B:` semantics
and requires no new code; the requirement is a **test**, not an implementation:
```python
# Sketch for the required D-12 test, mirroring the existing pattern at
# notebooks/pu_manifold/tests/test_decoder_priors.py:156 (restores_on_exit_by_exception)
model = _tiny_cae()
original = cae.chart_loss
with dp.decoder_prior_active(model, weight=1e-2, mode="scale"):
    after_outer = cae.chart_loss
    assert after_outer is not original
    with dp.decoder_prior_active(model, weight=1e-2, mode="christoffel"):
        assert cae.chart_loss is not after_outer   # composed, did not replace
        # both penalties present in `total`: assert against chart_loss(...)["total"]
    assert cae.chart_loss is after_outer            # unwound to the OUTER's patch
assert cae.chart_loss is original                    # unwound to the TRUE original
```
**No ordering hazard found.** The only thing that must be encoded correctly is entry order
(`scale` outer / `christoffel` inner per D-12's text) — reversing it would still compose
additively (addition commutes) but would not match the decision as written, so the test should
assert the declared order is what the combination-arm runner actually uses.

### Anti-Patterns to Avoid
- **Extrapolating training cost from the Swiss roll to the `d=20` saddle:** the two fixtures
  differ on three axes at once — `chart_dim` (2 → 20), hidden width (`[64,64]` → `[250,250,250]`,
  i.e. 2 layers of 64 → 3 layers of 250), and `n_points` (12,000 → 10,000, roughly comparable).
  The spike's own measured `~2.9×` per-epoch multiplier for the first-order prior was measured
  at `chart_dim=2` only; `torch.func.jacfwd`'s cost scales with the number of tangent directions
  it differentiates (`chart_dim`), so the real multiplier at `chart_dim=20` is very likely
  larger, not the same. Do not reuse the roll's `3.685s`/`10.699s` numbers as `d=20` estimates —
  they are useful only as a *qualitative* confirmation that `scale` (which reuses
  `isometry_penalty`'s exact code path, differing only in the O(1) deviation formula) triples-or-
  worse per-epoch cost, never as a quantitative one.
- **Treating curvature-field evaluation as free or as scaling with epoch count.** It does
  neither — see "Common Pitfalls" below.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| First/second-order metric regularization | A new penalty function or a fork of `cae.train_cae` | `decoder_priors.metric_deviation`, `christoffel_penalty`, `decoder_prior_active` | Already implemented, tested (23 existing tests), and proven not to bias the curvature estimand — a fresh implementation would have to re-derive and re-prove the tangential/normal decomposition from scratch |
| Combination of two priors | A new `PRIOR_MODES` entry, e.g. `"scale_christoffel"` | Two nested `with decoder_prior_active(...)` blocks | D-12 explicitly forecloses signature extension; nesting already composes correctly by construction (see Pattern 2 above) |
| Absolute metric scale | A second eigendecomposition or a separate `det`/`eig` call site | Reuse the `g` already computed at `chart_curvature.py:433`, replacing the `torch.linalg.cond(g)` call at line 448 with one `torch.linalg.eigvalsh(g)` call that supplies `λ_min`, `λ_max`, `cond = λ_max/λ_min`, and `det = eigs.prod(-1)` all at once | Verified in this session: `eigvalsh`-derived `cond` and `det` agree with `torch.linalg.cond`/`torch.linalg.det` to float64 round-off (`~1e-13` relative) on a realistic `(out_dim=60, chart_dim=20)` PSD test matrix; a second decomposition would cost extra wall-clock for no numerical benefit |
| Chart-decoder Jacobian/Hessian for the prior | A custom autodiff pass | `decoder_priors.chart_decoder_jacobian` / `chart_decoder_hessian` (already differentiate through `chart_decoders[i]` + `embedding_decoder`, verified to carry a live autograd graph) | Re-deriving this is exactly the "unfaithful translation" failure mode this project has already paid for once (per the module's own docstring) |

**Key insight:** this phase's don't-hand-roll list is short because the phase itself is a
measurement exercise over already-built machinery — the risk here is not reinventing something,
it is mis-costing the measurement (see Common Pitfalls).

## Common Pitfalls

### Pitfall 1: The curvature-field evaluation cost, not training cost, is the dominant and
hardest-to-move part of the budget

**What goes wrong:** A plan sized only around D-06/D-07's training-cost relief valve
(`CHRISTOFFEL_MAX_ROWS_PER_CHART`) will still blow the envelope, because curvature-field
evaluation is a **separate, fixed, mode-independent cost paid once per trained cell**, and it is
large at this scale.

**Measured, not estimated** (from the repo's own sealed record,
`notebooks/.cache/03_synthetic_controls.jsonl`, `config_id = "control_saddle_nc4_d20_ep300"`):
a single `chart_curvature.chart_curvature_field(model, x64, mode="reverse")` call over the full
`n=10000` saddle cloud at `chart_dim=20`, `ambient=768`, `n_charts_used=4` costs
**`curv_wallclock_s = 2993.912286339997`** — independent of how the model was trained, because
curvature evaluation runs *after* training and its cost is a pure function of `(n, chart_dim,
ambient_dim, n_charts_used)`. The same row's `train_wallclock_s = 6253.836718825012` at
`max_epochs=300` gives `~20.85s/epoch`, corroborated independently by the Phase 3 nine-cell PU
grid (`nc4_seed20260813`: `epochs_run=30`, `train_wallclock_s=646.6931414349965` →
`~21.56s/epoch`, same architecture).

**Why it happens:** the predecessor's spike (`03-NOTE-isometry-prior-spike.md`) never reached
curvature evaluation at all — it halted at the *training-cost* probe on the Swiss roll, which is
orders of magnitude cheaper (`chart_dim=2`, `hidden=[64,64]`, `n≤12000`). No prior artifact in
this codebase has ever measured curvature-evaluation cost at the `d=20`/`D=768` scale as an
explicit, separable line item — it has only ever been reported bundled into total wall-clock.

**How to avoid:** treat curvature-field evaluation cost as its own probe target, separate from
training cost, before committing to a ladder size. The arithmetic, using only measured numbers:

- **24 cells implied by D-02/D-03** (baseline + 3 scale rungs + 3 christoffel rungs + 1
  combination, × 3 seeds — rung count is Claude's discretion; 3 is D-04's own illustrative
  example).
- **If every cell evaluates curvature on the full `n=10000` cloud** (matching
  `synthetic_control_run.py`'s own protocol, which D-13 is told to copy): `24 × ~2994s ≈
  71,856s ≈ 19.96h` for curvature evaluation *alone* — already over D-06's 12h upper bound with
  **zero** training time counted.
- **If every cell trains for the full 300 `CONVERGE_MAX_EPOCHS` matching Phase 3's "converged"
  protocol** at even the conservatively-measured baseline rate (`~21s/epoch`, ignoring any prior
  overhead): `24 × 300 × 21s ≈ 151,200s ≈ 42h` for training alone, before any prior-mode
  multiplier is applied.
- Combined, a naive "copy Phase 3's protocol values directly" plan costs on the order of `19.96h
  + 42h+ ≈ 62h+` — roughly 5-8× D-06's envelope.

**Recommended relief, distinct from D-07's named valve:** evaluate curvature on a documented
subsample for the 24 ladder cells, reserving full-`n=10000` evaluation for the mandatory D-13
anchor-check cell (which must reproduce the sealed value exactly and therefore cannot deviate
from the sealed protocol) and, optionally, a final full-cloud pass on the single winning cell if
the plan wants one. **This has direct precedent in the same codebase**: `curvature_field_pu_run.py`
computes curvature on `x_holdout64` (the 2,000-row, 20%-holdout split) for every cell of its own
nine-cell *selection* grid (lines 730, 1372), and reserves the expensive full-cloud evaluation
(line 1627, `x64`, all 10,000 rows) for the single deliverable PU field. Applying the same ratio
(`2000/10000`) to the measured `~2994s` full-cloud cost projects `~599s/cell` — `24 × 599s ≈
14,376s ≈ 3.99h`, which fits comfortably inside D-06's envelope alongside a correspondingly
reduced epoch budget. **This is not a locked decision** — CONTEXT.md does not address evaluation
sample size as distinct from training sample size — so the planner should either ratify it
explicitly in the plan text (following D-10's "state the reading rule before anything runs"
spirit) or flag it back to the user as a genuinely new design choice this research surfaced.

**Warning signs:** if the plan's timing probe measures only `train_wallclock_s` and multiplies
it by cell count without a *separate* line for curvature evaluation, the projection will
undercount total cost by the amount shown above and the plan will repeat the predecessor's
`BUDGET NOT MET` outcome, but later and after real compute has been spent.

### Pitfall 2: `scale` and `isometry` share one code path — cost evidence for one is (weak)
evidence for the other, but not for `christoffel`

**What goes wrong:** treating the roll spike's numbers as uninformative for `scale` because
`scale` itself was never in that spike (added 2026-08-18, after the spike).

**Why it happens:** `decoder_priors.isometry_penalty(model, x, weight, mode)` is the single
function that computes `chart_decoder_jacobian` for *all three* first-order modes (`isometry`,
`conformal`, `scale` — `FIRST_ORDER_MODES`); `mode` only selects which O(1) deviation formula
(`metric_deviation`) is applied to the already-computed `g`. The measured roll multiplier
(`3.685s → 10.699s`, `~2.9×`) is therefore a same-code-path proxy for `scale`'s *shape* of
overhead (dominated by the Jacobian computation, not the deviation formula), though — per
Pitfall in "Anti-Patterns" above — not a reliable *magnitude* at `chart_dim=20`.

**How to avoid:** cite this fact when justifying why the `scale` arm doesn't need its own
from-scratch mechanism-cost derivation, but still measure its per-epoch cost fresh at
`chart_dim=20` before sizing the ladder — do not skip the probe on the theory that "it's the
same as isometry, which was measured."

**Warning signs:** a plan that reuses the roll's `10.699s/epoch` figure directly for `scale` at
`d=20` without re-measurement.

### Pitfall 3: `christoffel`'s cost does not scale with batch size, but `scale`'s does — the
D-07 relief valve helps only one arm

**What goes wrong:** assuming `CHRISTOFFEL_MAX_ROWS_PER_CHART` (D-07's declared relief valve)
would also help if the `scale` arm runs over budget.

**Why it happens:** `christoffel_penalty` subsamples to `max_rows_per_chart` (default 8) rows
per chart *before* calling `chart_decoder_jacobian`/`chart_decoder_hessian`
(`decoder_priors.py` lines 295-304) — its cost is bounded by `n_charts_used ×
CHRISTOFFEL_MAX_ROWS_PER_CHART × O(chart_dim²)` (the module docstring's own estimate: "roughly
`chart_dim` times a Jacobian"), independent of the training batch size. `isometry_penalty` (used
for `scale` too) has **no such subsampling** — it loops over *every row in the batch assigned to
each chart* (`decoder_priors.py` lines 344-354, no truncation), so its cost scales with
`BATCH=64` (the project's fixed batch size) × `chart_dim`, and cutting
`CHRISTOFFEL_MAX_ROWS_PER_CHART` does nothing to it.

**How to avoid:** if the timing probe shows the `scale` arm over budget, the pre-declared D-07
valve does not apply to it; the plan needs its own pre-declared fallback for `scale`
specifically (e.g. a documented reduction in epoch count, since D-07 already rules out cutting
`N_POINTS`).

**Warning signs:** a plan that describes D-07's valve as covering "the prior-active arms" in
general rather than naming it as `christoffel`-specific.

### Pitfall 4: Continuous (unblocked) training diverges at this architecture — but only past
`~epoch 220`, and only measured on the flat fixture

**What goes wrong:** copying `synthetic_control_run.py`'s `train_blocked` machinery
mechanically without checking whether it is still necessary at whatever (likely much lower)
epoch budget the compute analysis above forces.

**Why it happens:** `CONTROL_EPOCH_BLOCK = 25`'s docstring records that a single continuous
300-epoch `train_cae` call diverges to non-finite weights at `~epoch 220` on the **flat**
fixture specifically (`linalg.svd` on a NaN weight inside `cae.lipschitz_penalty`), traced to
`train_cae` building a fresh Adam optimizer per call — blocking into 25-epoch segments
sidesteps this by restarting Adam's moment estimates. The **saddle** fixture's sealed row was
trained blocked too (`epoch_block: 25`, `n_blocks: 12`), but its own divergence point under
continuous training was never independently measured — blocking was applied as a blanket
protocol decision across all three fixtures, not a saddle-specific finding.

**How to avoid:** if Pitfall 1's compute analysis forces the epoch budget well below `~220`
(likely, given the arithmetic above), continuous (unblocked, `epoch_block=0`) training may be
simpler and slightly cheaper (no optimizer restarts) and has not been shown to diverge at low
epoch counts — but this is unverified for the saddle specifically. The mandatory D-13
anchor-check cell **must** use `epoch_block=25` regardless (it has to reproduce the sealed
protocol exactly); the ladder's own cells are free to choose, but the choice should be stated
and, if `epoch_block=0` is chosen, spot-checked for finite weights at the chosen epoch count.

**Warning signs:** NaN/Inf losses or a `LinAlgError` from `cae.lipschitz_penalty`'s spectral-norm
computation partway through a ladder cell.

### Pitfall 5: D-14's notebook needs multiple fits, in tension with CLAUDE.md's "two minutes"
line written for one

**What goes wrong:** either blowing the 2-minute CPU target by training 5 full-protocol
(300-epoch) fits in one notebook, or silently under-training every arm to make the wall-clock
number look good, which would make D-14's "pass" uninformative.

**Why it happens:** D-14 requires **all three modes** (`scale`, `christoffel`, nested
combination) in **one** notebook, plus (per CLAUDE.md's own baseline-comparison rule) a matched
`cae.PlainAutoEncoder`. Read literally, that is up to five CAE-family fits sharing one notebook,
where the reference notebook (`02.2_swiss_roll_cae_check.ipynb`) trains exactly one CAE plus one
plain AE (300 epochs each, `early_stop_patience=25`) and the "two minutes" language was written
against that single-model case.

**How to avoid:** at the roll's own scale (`chart_dim=2`, `hidden=[64,64]`, `n_points=3000` —
a quarter of the spike's `n_points=12000`), baseline per-epoch cost is small: extrapolating the
spike's own measured `3.685s/epoch` at `n_points=12000` down to `n_points=3000` by row-count
projects roughly `~0.9s/epoch` for `weight=0`. Even at a conservative `~3×` prior-mode
multiplier and a handful of fits, a modest epoch budget (well under the roll notebook's
300-epoch protocol) should keep the whole notebook well inside a couple of minutes — but this
must be measured inside the notebook itself, not assumed, since `christoffel` was never
timed on the roll at all (added after the spike halted). Recommend reading CLAUDE.md's "two
minutes" as a **whole-notebook** budget (matching its stated purpose — "cheap enough to re-run
on a whim") and sizing epochs down until a real run confirms it, rather than reading it as
"two minutes per fit."

**Warning signs:** the notebook takes noticeably longer than the 02.2 reference notebook to
execute end-to-end, or any individual fit is given the full 300-epoch protocol without checking
the aggregate wall-clock first.

### D-15's integration point — reuse the existing `g`, one eigendecomposition
```python
# Source: notebooks/pu_manifold/chart_curvature.py, chart_mean_curvature, lines 433-448
# CURRENT (per-chunk loop inside chart_mean_curvature):
g = torch.einsum("boi,boj->bij", J, J)
eye_d = _batched_eye(VMAP_CHUNK, chart_dim, g.dtype, g.device)
g_inv = torch.linalg.solve(g, eye_d)
# ... trace-first-then-project curvature computation (unchanged) ...
cond_parts.append(torch.linalg.cond(g)[:n_real].detach())

# PROPOSED, reusing one eigendecomposition instead of a second cond() call:
eigs = torch.linalg.eigvalsh(g)              # (chunk, chart_dim), ascending, g is symmetric PSD
lambda_min = eigs[..., 0]
lambda_max = eigs[..., -1]
cond = lambda_max / lambda_min                # verified == torch.linalg.cond(g) to ~1e-13 rel.
det_g = eigs.prod(dim=-1)                     # verified == torch.linalg.det(g) to ~1e-13 rel.
lambda_min_parts.append(lambda_min[:n_real].detach())
lambda_max_parts.append(lambda_max[:n_real].detach())
det_g_parts.append(det_g[:n_real].detach())
cond_parts.append(cond[:n_real].detach())
```
Both replacements were verified in this research session on a realistic-shaped
`(batch=5, out_dim=60, chart_dim=20)` PSD test matrix: `cond` max relative disagreement `~9.4e-14`,
`det` max relative disagreement `~4e-14` — float64 round-off, not a different quantity. The
mirrored change is needed in `chart_curvature_field`'s aggregation loop (lines 528-557): three
new pre-allocated `(n,)` arrays alongside the existing `H_norm`/`metric_cond`, populated per
chart-chunk the same way `metric_cond[target] = out["metric_condition_number"]` already is
(line 544), and added to both functions' return dicts.

   (epoch count, evaluation sample size)?**
   - What we know: the arithmetic above shows curvature evaluation alone, at full-cloud
     evaluation, already exceeds the envelope; training at Phase 3's 300-epoch "converged"
     protocol multiplies that by several times more.
   - What's unclear: the actual per-epoch cost of `scale` and `christoffel` at `chart_dim=20`
     (not measured in this session, only extrapolated) — the real feasible epoch count cannot be
     pinned down without a fresh probe at the target architecture.
   - Recommendation: the plan's first executable task should be exactly this probe — a
     `--probe` mode measuring (a) train-s/epoch for `weight=0`, a calibrated `scale` weight, and
     a calibrated `christoffel` weight at `n_charts=4`/`chart_dim=20`, and (b)
     curvature-eval-s/cell at both the full `n=10000` and a candidate reduced sample size — with
     the resulting numbers plugged into the same arithmetic shown in Pitfall 1 before any epoch
     count or evaluation-sample-size choice is locked into the plan text.

2. **Does D-07's "not the valve: cutting the fixture's sample count" fence cover the
   curvature-evaluation sample size, or only the training sample size?**
   - What we know: the cited precedent (Phase 3's Amendment 1, `N_POINTS` 3000 → 12000) was
     about the number of points the model is *trained on*, motivated by curvature needing dense
     sampling to be learned well.
   - What's unclear: whether reducing the number of points curvature is *evaluated on*, after
     training on the full set, falls under the same fence or is a distinct, unaddressed
     question. This research found direct in-repo precedent (`curvature_field_pu_run.py`'s
     holdout-only selection-grid evaluation) for treating them as distinct.
   - Recommendation: state this explicitly as a decision in the plan text (D-10's own "state the
     reading rule before anything runs" spirit applies equally to this budget-shaping choice),
     or escalate it to the user as a genuinely new design question this research surfaced rather
     than deciding it unilaterally.
